단답·약술 빈출 ★★★ 디자인패턴 · 모듈화 핵심 용어 35+ 암기카드 28 문제 18
✓ 이 영역의 공략법 SW공학은 순서 문제(결합도 약→강, 응집도 강→약)와 분류 문제(패턴 3종, 테스트 2종)가 반복됩니다. 순서는 두문자로, 분류는 "어느 그룹에 속하는가"로 외우세요. LOC 기반 개발기간 계산도 공식만 알면 득점입니다.
01

모듈화 — 결합도 · 응집도

SW공학 최대 빈출. "결합도는 약하게, 응집도는 강하게"가 좋은 모듈화의 핵심 원칙입니다.

CORE

모듈 독립성의 원칙

★★★

모듈의 독립성을 높이려면 결합도(Coupling)는 낮게, 응집도(Cohesion)는 높게 만들어야 합니다.

  • 결합도 — 모듈과 모듈 사이의 상호 의존 정도 (낮을수록 좋음)
  • 응집도 — 모듈 내부 구성요소의 기능적 집중 정도 (높을수록 좋음)
⚠ 단골 빈칸: "모듈 독립성을 높이려면 ( )는 약하게, ( )는 강하게" → 답: 결합도, 응집도. 순서 바꾸지 말 것.
COUPLING

결합도 6단계 (약 → 강)

★★★
◀ 약함 (좋은 품질)강함 (낮은 품질) ▶
1자료 결합도파라미터로 데이터만 전달 (Data)
2스탬프 결합도배열·구조체 등 자료구조 전달 (Stamp)
3제어 결합도제어 신호(플래그)를 전달 (Control)
4외부 결합도외부에 선언된 데이터를 다른 모듈이 참조 (External)
5공통 결합도여러 모듈이 공통(전역) 데이터 영역을 공유 (Common)
6내용 결합도다른 모듈 내부를 직접 참조 (Content)
🔑 자·스·제·외·공·내 (자료→스탬프→제어→외부→공통→내용). 위로 갈수록 좋은 결합. 순서 묻는 문제 단골.
COHESION

응집도 7단계 (강 → 약)

★★★
◀ 강함 (좋은 품질)약함 (낮은 품질) ▶
1기능적단일 기능 수행 (Functional)
2순차적출력이 다음 입력으로 (Sequential)
3교환(통신)적동일 입출력 데이터 사용 (Communication)
4절차적순서대로 실행 (Procedural)
5시간적특정 시점에 함께 실행 (Temporal)
6논리적유사 성격끼리 묶음 (Logical)
7우연적서로 관련 없음 (Coincidental)
🔑 기·순·교·절·시·논·우 (기능적이 최고, 우연적이 최악). "관련 없는 요소들" = 우연적 응집도.
SIGNAL

결합도·응집도 — 단계별 실전 구분법

★★★

순서 암기(자·스·제·외·공·내, 기·순·교·절·시·논·우)는 위 블록에서 끝. 실기는 시나리오 문장을 주고 "몇 단계인지"를 묻습니다.

문장 속 시그널 키워드를 잡으면 바로 답이 나옵니다. 결합도는 "모듈 사이에 무엇이 오가는가"를 봅니다:

자료 결합도낱개 값만 파라미터로 주고받음 — 시그널: 단순 매개변수(값)만 전달
스탬프 결합도구조체·배열·객체를 통째로 전달(받는 쪽은 일부 필드만 쓰기도) — 시그널: 자료 구조 전달
제어 결합도플래그·스위치를 넘겨 상대 모듈의 처리 흐름(논리)을 좌우 — 시그널: 제어 신호(플래그) 전달
외부 결합도다른 모듈에서 선언한 변수(데이터)를 참조 — 시그널: 외부에 선언된 데이터 참조
공통 결합도전역 변수(공통 데이터 영역)를 여러 모듈이 읽고 씀 — 시그널: 전역 변수 공유
내용 결합도다른 모듈 내부의 변수·기능을 직접 참조·수정 — 시그널: 내부 직접 접근·수정. 최악

응집도는 "모듈 안의 기능들이 무엇으로 묶였는가"를 봅니다:

기능적 응집도모든 요소가 단 하나의 기능 수행(예: 제곱근 계산만 하는 모듈) — 시그널: 단일 기능. 최선
순차적 응집도한 활동의 출력을 다음 활동이 입력으로 사용(예: 파일을 읽고 → 그 데이터를 가공) — 시그널: 출력→입력 연결
교환적 응집도같은 입출력 데이터를 여러 활동이 사용하되 순서는 무관(예: 같은 성적 데이터로 평균·최고점 산출) — 시그널: 동일 입출력 데이터 사용
절차적 응집도데이터 연결 없이 실행 순서만 공유(예: 접근 권한 확인 후 파일 열기) — 시그널: 순서대로 수행되기만 함
시간적 응집도같은 시점에 함께 실행될 것끼리 묶음(예: 초기화 모듈, 오류 발생 시 일괄 처리) — 시그널: 특정 시점·초기화
논리적 응집도비슷한 성격의 기능을 모아 인자로 골라 실행(예: 프린터/화면/파일 출력을 한 모듈이 case로 분기) — 시그널: 유사 기능 묶음+선택 인자
우연적 응집도서로 아무 관련 없는 기능들이 한 모듈에 — 시그널: 관련 없는 요소. 최악
⚠ 2대 혼동 포인트: ① 자료 vs 스탬프 — 낱개 값이면 자료, 구조체·배열 통째면 스탬프("전달받은 구조체의 일부만 사용"도 스탬프의 단서). ② 외부 vs 공통 — 특정 모듈이 선언한 데이터를 참조하면 외부, "전역 변수"가 보이면 공통.
📝 실기 이렇게 나온다: "모듈 A는 처리 결과에 따라 플래그 값을 모듈 B에 전달하고, B는 그 값에 따라 서로 다른 로직을 수행한다. 두 모듈 간의 결합도는?" → 답: 제어 결합도 (흐름을 조종하는 신호가 오감)
📝 실기 이렇게 나온다: "한 모듈 안의 여러 기능이 동일한 입력 자료를 사용하지만 수행 순서는 중요하지 않다. 이 모듈의 응집도는?" → 답: 교환적(통신적) 응집도 (출력이 다음 입력으로 이어지면 순차적)
FAN

팬인(Fan-In) · 팬아웃(Fan-Out)

★★☆

모듈 구조도를 주고 특정 모듈의 팬인·팬아웃 값을 계산시키는 문제가 나옵니다.

팬인 = 해당 모듈을 호출하는 상위 모듈의 수(들어오는 화살표), 팬아웃 = 해당 모듈이 호출하는 하위 모듈의 수(나가는 화살표). 구조도에서 화살표 방향만 세면 됩니다.

●●●module-tree.txt
            A
          / | \
         B  C  D        // 호출 관계: A→B·C·D / B→F / C→F / D→F·G
          \ | / \
            F    G

F: 팬인 3 (B·C·D가 호출) · 팬아웃 0
D: 팬인 1 (A) · 팬아웃 2 (F·G)
A: 팬인 0 · 팬아웃 3 (B·C·D)
팬인 높음여러 모듈이 공유하는 공통 모듈 — 재사용성·공유도가 높다는 신호. 단, 수정 시 파급이 커서 중점 관리·충분한 테스트 필요
팬아웃 높음한 모듈이 너무 많은 하위 모듈을 제어 — 제어 복잡도 증가. 3~4 이하 권장, 불필요한 호출인지 점검
🔑 외우기 팁: Fan-In은 "인기" — 팬(호출자)은 많을수록 좋다. 시스템 복잡도 최적화 원칙은 팬인은 높게, 팬아웃은 낮게.
📝 실기 이렇게 나온다: "위 구조도에서 모듈 F의 팬인과 팬아웃을 구하시오" → 답: 팬인 3, 팬아웃 0 (F로 들어오는 화살표 3개, 나가는 화살표 없음)
02

비용 산정 — LOC

계산 문제로 출제. 공식만 알면 확실한 득점원입니다.

CALC

LOC 기반 개발 기간 산정

★★☆

LOC(Line Of Code) 기법: 총 라인 수를 인력·생산성으로 나눠 기간을 구합니다.

●●●loc.calc
개발 기간 = 총 LOC ÷ (투입 인원 × 1인당 월 생산성)

# 예: LOC 30000, 개발자 5명, 1인당 월 300라인
30000 ÷ (5 × 300) = 30000 ÷ 1500 = 20개월

노력(인월) = 개발 기간 × 투입 인원
생산성 = 총 LOC ÷ 노력(인월)
🧮 계산식을 반드시 쓰세요. 답만 쓰면 감점될 수 있습니다. 단위(개월, 인월)도 정확히.
MODEL

COCOMO · Putnam · FP — 프로젝트 산정 모형

★★☆

LOC 계산과 함께 "설명 → 모형 이름"을 묻는 용어 문제로 나옵니다. 모형마다 고유 키워드가 답의 근거입니다.

산정 기법의 큰 분류: 하향식 = 경험 기반(전문가 감정, 그 주관적 편견을 조정자+여러 전문가 의견 종합으로 보완한 델파이) / 상향식 = 세부 단위 기반(LOC, 개발 단계별 인월수, 수학적 산정 모형 COCOMO·Putnam·FP).

COCOMO보헴(Boehm) 제안, LOC(원시 코드 라인 수) 기반. 개발 유형 3가지 구분이 단골 ↓
└ 조직형Organic — 5만 라인 이하 소규모. 사무 처리·업무·과학용 응용
└ 반분리형Semi-Detached — 30만 라인 이하, 조직형과 내장형의 중간. 트랜잭션 처리 시스템·운영체제 등
└ 내장형Embedded — 30만 라인 이상 초대형. 신호기 제어 같은 실시간·임베디드 시스템
└ 모형 종류기본형(Basic, LOC만)·중간형(Intermediate, +15개 특성)·발전형(Detailed, 단계별 세분화 적용)
Putnam생명주기 전 과정의 노력(인력) 분포를 가정·예측. Rayleigh-Norden 곡선 기반, 대형 프로젝트용. 자동화 도구 SLIM
FP알브레히트(Albrecht) 제안, 라인 수 대신 기능 증대 요인별 가중치 합산(입력·출력·질의·파일·외부 인터페이스 수). 자동화 도구 ESTIMACS
⚠ 함정: COCOMO·Putnam은 LOC 기반, FP는 기능 기반 — "라인 수" 없이 "기능별 가중치"가 보이면 FP. 도구 짝(SLIM↔Putnam, ESTIMACS↔FP)을 서로 바꿔 놓는 문제도 나옵니다.
🔑 외우기 팁: 조직형→반분리형→내장형 순으로 조(5만)·반(30만)·내(그 이상) 규모가 커진다. "슬림한 퍼트남" — SLIM은 Putnam의 도구.
📝 실기 이렇게 나온다: "소프트웨어 생명주기 전 과정에 사용될 노력의 분포를 Rayleigh-Norden 곡선으로 가정하는 산정 모형은?" → 답: Putnam 모형 (자동화 도구까지 물으면 SLIM)
📝 실기 이렇게 나온다: "COCOMO의 개발 유형 중 5만 라인 이하의 사무 처리·과학용 응용 등 소규모 소프트웨어에 적합한 유형은?" → 답: 조직형(Organic Mode) (30만 이하 중간은 반분리형, 그 이상은 내장형)
03

테스트 — 화이트박스 vs 블랙박스

테스트 기법 분류가 핵심. 내부 구조를 보느냐(화이트) 안 보느냐(블랙)로 구분.

TEST

화이트박스 vs 블랙박스

★★★
화이트박스내부 구조·코드를 보고 테스트 (구조 기반). 종류: 기초 경로, 조건/분기, 루프 검사
블랙박스내부를 모르고 입출력으로 테스트 (명세 기반). 종류: 동치 분할, 경계값 분석, 원인-결과, 결정 테이블, 상태 전이
⚠ 핵심: 화이트박스="투명해서 안이 보임"(코드 기반), 블랙박스="검은 상자, 안 안 보임"(명세 기반). 경계값 분석은 블랙박스 단골.
LEVEL

테스트 단계 (V-모델)

★★☆
  • 단위 테스트 — 모듈 하나 단위 검증
  • 통합 테스트 — 모듈 간 인터페이스 검증 (상향식/하향식)
  • 시스템 테스트 — 전체 시스템 요구사항 검증
  • 인수 테스트 — 사용자 관점 최종 검증 (알파/베타)
📊 통합 방식: 하향식(Top-down)은 스텁(Stub) 사용, 상향식(Bottom-up)은 드라이버(Driver) 사용.
분류: 비점진적=빅뱅(Big-Bang), 점진적=하향식·상향식·혼합식(샌드위치).
COVER

테스트 커버리지 6종

★★★

화이트박스의 "얼마나 훑었나" 기준. 정의를 주고 이름을 맞히게 하거나, 주어진 케이스가 어떤 커버리지를 만족하는지 묻습니다.

핵심 축은 전체 조건식(결정)을 보느냐 개별 조건식(조건)을 보느냐입니다. 각 커버리지가 "무엇을 100% 만족해야 하는지"로 구분하세요:

구문(문장)모든 문장을 최소 1회 실행 — 가장 약한 기준
결정(분기)전체 조건식의 결과가 참 1회·거짓 1회 이상 — 분기 방향을 모두 타 봄
조건개별 조건식 각각이 참 1회·거짓 1회 이상 — 전체 결과는 안 봄
조건/결정전체 조건식과 개별 조건식 모두 참·거짓 1회 이상

맥케이브 순환 복잡도 V(G)

★★★

제어 흐름 그래프를 주고 복잡도를 계산시키는 확실한 득점원. 공식 3개 중 무엇을 써도 같은 값이 나옵니다.

공식 ①V(G) = E − N + 2P (E=간선 수, N=노드 수, P=연결 요소 수 — 보통 1이라 E−N+2)
공식 ②V(G) = 폐(닫힌) 영역 수 + 1 — 화살표로 둘러싸인 영역을 센다
공식 ③V(G) = 단순 분기(조건) 수 + 1 — if·while 등 판단 노드를 센다
●●●cfg.example
       ┌───────────┐
       ▼           │
(1)──▶(2)──▶(3)──▶(5)──▶(6)
       │           ▲
       └──▶(4)─────┘

간선 E = 7 : 1→2, 2→3, 2→4, 3→5, 4→5, 5→2(루프), 5→6
노드 N = 6 / 분기 노드 2개: ②(3 또는 4로), ⑤(2 또는 6으로)

① E−N+2P = 7 − 6 + 2×1 = 3
② 폐영역 2개(3쪽·4쪽 경로 사이, 5→2 루프가 만드는 영역) + 1 = 3
③ 분기 2개 + 1 = 3

V(G)=3은 선형 독립 경로가 3개라는 뜻 — 화이트박스 기초 경로 검사(Basis Path Testing)에서 도출할 기본 경로 수이자 최소한 필요한 테스트 케이스 수입니다. 예: ① 1→2→3→5→6 ② 1→2→4→5→6 ③ 루프 5→2를 한 번 도는 경로. McCabe 기준 10 이하가 바람직하며, 초과하면 매우 복잡한 모듈로 봅니다.

⚠ 함정: 간선(E)이 앞! E−N+2인데 N−E+2로 뒤집어 계산하는 실수가 흔합니다. V(G)는 항상 1 이상 — 0이나 음수가 나오면 뒤집은 것. P는 그래프가 하나로 이어져 있으면 1입니다.
📝 실기 이렇게 나온다: "제어 흐름 그래프의 간선이 11개, 노드가 9개일 때 순환 복잡도 V(G)를 구하시오" → 답: 4 (11 − 9 + 2 = 4, 계산식까지 써야 안전)

정적 vs 동적 분석 · 결함 용어

★★☆

"실행하느냐"가 정적/동적의 전부. 검토 기법 3형제는 주도자·공식성으로 가릅니다.

정적 테스트는 프로그램을 실행하지 않고 명세·소스 코드를 검토(리뷰, 정적 분석 도구), 동적 테스트는 실행하면서 오류를 찾습니다 — 화이트박스·블랙박스 모두 동적입니다.

인스펙션가장 공식적 — 작성자가 아닌 훈련된 전문 검토자(중재자 진행)가 체크리스트 기반 공식 절차로 결함 발견

동료 검토2~3명의 소규모 — 작성자가 설명하고 동료들이 결함 발견

결함 용어는 "누구/어디에 있느냐"의 전이 순서로 구분합니다:

에러(오류)사람(개발자)의 실수 — 결함의 원인
결함(폴트·버그)에러의 결과로 제품(코드·문서)에 존재하는 것 — 제거하지 않으면 고장을 유발

🔑 테스트 원리 빈출 3: 결함 집중(결함의 대부분은 소수 모듈에 집중 — 파레토 법칙 80:20) / 살충제 패러독스(같은 케이스만 반복하면 새 결함을 못 찾음 → 케이스 지속 개선) / 오류-부재의 궤변(결함이 없어도 요구사항을 만족 못 하면 품질이 높다고 할 수 없음).
⚠ 함정: "작성자 주도 + 사전 배포" = 워크스루, "중재자·공식 절차" = 인스펙션 — 주도자를 바꿔서 냅니다. 에러/결함/고장은 사람 → 코드 → 실행 증상 순서: "실행 중 요구사항 미충족"이면 고장(Failure)입니다.
📝 실기 이렇게 나온다: "검토 회의 전에 명세서를 미리 배포하여 사전 검토하고, 작성자가 주도하는 짧은 회의로 결함을 발견하는 검토 기법은?" → 답: 워크스루(Walkthrough) (전문 검토팀이 공식 절차로 하면 인스펙션)
📝 실기 이렇게 나온다: "결함을 모두 제거했더라도 사용자의 요구사항을 만족하지 못하면 품질이 높다고 볼 수 없다는 테스트 원리는?" → 답: 오류-부재의 궤변 (같은 케이스 반복의 한계는 살충제 패러독스)

REL

UML 관계 6종 — 기호로 구분

★★★

관계 이름 나열만으론 못 풉니다. 실기는 "기호 설명 → 관계명"으로 냅니다.

구분 축은 3개뿐입니다. ① 선(실선/점선) ② 속 빈 삼각형(상속 계열) ③ 마름모(포함 계열). 조합하면: 실선+삼각형=일반화, 점선+삼각형=실체화, 빈 마름모=집합, 채운 마름모=복합, 그냥 실선=연관, 그냥 점선 화살표=의존.

연관(Association) 실선 — 코드로 치면 멤버 변수로 다른 객체를 오래 참조. 화살표를 붙이면 참조 방향이 있는 연관
의존(Dependency) 점선 화살표 — 코드로 치면 메서드 파라미터·지역 변수·리턴 타입으로 잠깐 사용하는 일시적 관계
일반화(Generalization) 실선 + 속 빈 삼각형 — 상속. 코드로 치면 extends. 화살촉은 자식 → 부모 방향
실체화(Realization) 점선 + 속 빈 삼각형 — 인터페이스 구현. 코드로 치면 implements. 일반화와 삼각형은 같고 선만 점선
집합(Aggregation) 속 빈 마름모 — 약한 포함. 부분이 전체와 독립적으로 존재 가능(생명주기 따로). 마름모는 전체(whole) 쪽에 붙임
복합(Composition) 속이 채워진 마름모 — 강한 포함. 전체가 소멸하면 부분도 함께 소멸(생명주기 공유)
●●●aggregation_vs_composition.java
// 집합(Aggregation) — 부분을 밖에서 받아 참조: 팀이 해체돼도 선수 객체는 남는다
class Team {
    private Player p;
    Team(Player p) { this.p = p; }   // 외부에서 주입 = 생명주기 독립
}

// 복합(Composition) — 부분을 내부에서 직접 생성: 건물이 철거되면 방도 같이 소멸
class Building {
    private Room r = new Room();   // 내부에서 생성·소유 = 생명주기 공유
}
// (Player·Room 클래스 선언은 생략)
⚠ 집합 vs 복합 함정: 부분이 전체 없이도 존재할 수 있으면 집합(빈 마름모), 전체가 사라질 때 부분도 사라지면 복합(채운 마름모). 예: 팀-선수=집합, 건물-방=복합. 마름모 위치도 함정 — 부분이 아니라 전체 쪽에 그립니다.
📝 실기 이렇게 나온다: "클래스 다이어그램에서 속이 채워진 마름모로 표기하며, 전체 객체가 소멸하면 부분 객체도 함께 소멸하는 관계를 쓰시오." → 답: 복합(Composition) 관계 (마름모 속이 비어 있으면 집합 관계)
USECASE

유스케이스 — include vs extend

★★★

유스케이스 다이어그램에서 실기가 노리는 곳은 정해져 있습니다 — include/extend 구분과 화살표 방향.

유스케이스 다이어그램은 시스템이 제공하는 기능(유스케이스)과 외부 사용자(액터)의 관계를 표현합니다. 시험은 지문 속 "반드시/항상 실행"이면 include, "특정 조건에서만/선택적으로 실행"이면 extend로 구별시키고, 여기에 화살표 방향을 얹어 함정을 팝니다.

액터시스템 외부에서 상호작용하는 사람·외부 시스템. 스틱맨으로 표기
유스케이스시스템이 제공해야 하는 기능 단위. 타원으로 표기
시스템 경계시스템의 범위를 나타내는 사각형. 유스케이스는 안쪽, 액터는 바깥쪽
<<include>>반드시 함께 실행되는 공통 기능 호출. 점선 화살표가 기본 → 포함되는 기능 방향
<<extend>>특정 조건에서만 덧붙는 확장 기능. 점선 화살표가 확장 기능 → 기본 방향 (include와 반대!)
일반화액터·유스케이스 간 상속. 속 빈 삼각형 실선 — 예: 관리자 액터 → 회원 액터(자식→부모)

전형 시나리오: "게시글 등록"은 실행될 때마다 항상 "로그인 확인"을 거친다 → include. "게시글 등록" 도중 원할 때만 "파일 첨부"가 붙는다 → extend.

●●●usecase_arrows.txt
// 화살표 방향 암기용 — 둘 다 점선, 방향이 서로 반대다
(주문) ──<<include>>──▶ (결제 승인)    // 기본 → 포함: 항상 실행
(쿠폰 적용) ──<<extend>>──▶ (주문)     // 확장 → 기본: 조건부 실행

// include = 기본이 공통 부품을 "가져다 쓴다" / extend = 옵션이 기본에 "끼어든다"
⚠ 최대 함정 — 화살표 방향: include는 기본 유스케이스가 포함할 기능을 가리키고(기본→포함), extend는 확장 기능이 기본 유스케이스를 가리킵니다(확장→기본). "extend니까 기본에서 뻗어나간다"고 그리면 틀립니다. 둘 다 점선 화살표라 스테레오타입과 방향만이 구분 포인트.
📝 실기 이렇게 나온다: "'주문' 유스케이스는 어떤 경우에도 '결제 승인' 유스케이스를 반드시 실행한다. 두 유스케이스를 잇는 점선 화살표 위에 표기할 스테레오타입을 쓰시오." → 답: <<include>> (조건부로만 실행되면 <<extend>>, 화살표 방향도 반대)
SEQ

시퀀스 다이어그램 구성요소

★★☆

지문에 "시간의 흐름", "메시지 순서"가 보이면 답은 시퀀스 다이어그램입니다.

시퀀스 다이어그램은 객체 간 상호작용을 시간 순서에 따라 메시지로 표현하는 행위(동적) 다이어그램입니다. 시험은 ① 다이어그램 이름 맞히기 ② 구성요소 이름 맞히기(생명선·활성 상자) ③ 화살표 종류 구분(동기/비동기/응답), 세 갈래로 냅니다.

액터·객체상호작용의 주체. 다이어그램 맨 위에 가로로 배치
생명선(Lifeline) 객체 아래로 수직으로 뻗은 점선 — 객체가 존재하는 기간을 표현
활성 상자(Activation) 생명선 위의 가늘고 긴 직사각형 — 객체가 연산을 실행 중인 구간. 실행 상자라고도 함
동기 메시지실선 + 채운(속이 찬) 화살촉 — 보낸 뒤 응답을 기다림
비동기 메시지실선 + 열린(빈) 화살촉 — 응답을 기다리지 않고 진행
응답 메시지(Return) 점선 화살표 — 처리 결과를 되돌려줌
자체 호출(Self-Message) 화살표가 자신의 생명선으로 되돌아옴 — 내부 메서드 호출·재귀

// 로그인 시퀀스 — 위에서 아래가 시간 순서
회원 ──로그인 요청──▶ 로그인화면            // 실선+채운 화살촉 = 동기
로그인화면 ──정보 조회──▶ 회원정보(DB)
회원정보(DB) ---조회 결과---▶ 로그인화면    // 점선 = 응답(반환)
로그인화면 ---로그인 결과---▶ 회원
⚠ 혼동 포인트: 커뮤니케이션 다이어그램도 객체 간 상호작용을 그리지만 시간 축 없이 객체 간 연결(링크) 중심입니다. "시간의 흐름에 따라"가 있으면 시퀀스. 화살촉도 바꿔치기해 출제 — 채움=동기, 열림=비동기, 점선=응답을 세트로.
📝 실기 이렇게 나온다: "객체 간의 상호작용을 시간의 흐름에 따라 표현하며, 생명선·활성 상자·메시지 등으로 구성되는 UML 다이어그램을 쓰시오." → 답: 시퀀스(Sequence) 다이어그램 (구성요소 변형: 객체 아래 수직 점선 = 생명선)

OMT

럼바우 OMT + 객체지향 방법론 계보

★★★

객체지향 분석 방법론은 "학자 이름 ↔ 키워드" 매칭 게임입니다. 럼바우는 순서까지 묻습니다.

럼바우(Rumbaugh) 객체 모델링 기법(OMT)은 소프트웨어 구성요소를 그래픽 표기법으로 모델링하는 분석 기법입니다. 시험은 ① 3가지 모델링의 수행 순서 ② 각 모델링이 사용하는 다이어그램을 짝지어 구별시킵니다.

1객체 모델링(Object) 객체·클래스와 그 관계를 식별 — 객체 다이어그램. 가장 먼저 수행, 가장 중요
2동적 모델링(Dynamic) 시간 흐름에 따른 객체의 상태·동작·제어 흐름 — 상태 다이어그램(상태도)
3기능 모델링(Functional) 입력에 대해 어떤 처리·출력이 일어나는지 — 자료 흐름도(DFD)
🔑 객·동·기 (객체 → 동적 → 기능). 다이어그램까지 세트로: 객체=객체 다이어그램, 동적=상태 다이어그램, 기능=DFD.

객체지향 방법론 계보 — 학자 이름과 키워드만 매칭하면 됩니다.

Booch(부치) 미시적(Micro) + 거시적(Macro) 개발 프로세스를 모두 사용. 클래스·객체 식별과 속성·연산 정의
Jacobson(제이콥슨) 유스케이스(Use Case)를 강조하여 사용하는 방법론 — OOSE
Coad-Yourdon(코드-요든) E-R 다이어그램으로 객체의 행위를 모델링. 객체 식별 → 구조 식별 → 주제 정의 → 속성·연산 정의 순
Wirfs-Brock(워프스-브록) 분석과 설계의 구분이 없음 — 고객 명세서 평가에서 설계 작업까지 연속적으로 수행
⚠ 키워드 즉답표: "유스케이스"=Jacobson, "E-R 다이어그램"=Coad-Yourdon, "미시·거시"=Booch, "분석·설계 구분 없음"=Wirfs-Brock, "3가지 모델링"=럼바우. 럼바우 안에서는 동적=상태 다이어그램과 기능=DFD를 서로 바꿔치기한 선지가 단골.
📝 실기 이렇게 나온다: "객체지향 분석 방법론 중 유스케이스를 강조하여 사용하는 방법론을 쓰시오." → 답: Jacobson(제이콥슨) 방법론 (OOSE)
📝 실기 이렇게 나온다: "럼바우 분석 기법의 3가지 모델링을 순서대로 쓰시오." → 답: 객체 모델링 → 동적 모델링 → 기능 모델링 (두문자 '객동기')
CMMI

CMMI 5단계 + SPICE

★★☆

둘 다 "프로세스가 얼마나 성숙한가"를 평가하는 모델. 단계 설명을 주고 단계명을 맞히게 합니다.

CMMI(능력 성숙도 모델 통합)는 조직의 프로세스 성숙도를 1~5의 5단계로, SPICE(ISO/IEC 15504)는 프로세스 수행 능력을 0~5의 6수준으로 평가합니다. 시험은 단계 개수(5 vs 6), 표준 번호(15504), 각 단계의 핵심 키워드로 둘을 구별시킵니다.

◀ 1단계 (미성숙)5단계 (최적화) ▶
1초기(Initial) 정의된 프로세스 없음 — 성공이 개인의 역량에 좌우
2관리(Managed) 프로젝트 단위로 프로세스를 계획·관리 — 반복 가능한 수준
3정의(Defined) 조직 표준 프로세스를 확립·문서화하고 프로젝트가 이를 따름
4정량적 관리(Quantitatively Managed) 프로세스를 정량적으로 측정·통제
5최적화(Optimizing) 측정 결과를 바탕으로 지속적으로 프로세스 개선

SPICE(ISO/IEC 15504) 수행 능력 6수준 — 0부터 시작하는 것이 CMMI와 다른 점.

0 불완전(Incomplete) 프로세스가 구현되지 않거나 목적을 달성하지 못함
1 수행(Performed) 프로세스가 수행되고 목적이 달성됨
2 관리(Managed) 정해진 절차에 따라 계획·관리되어 작업 산출물을 냄
3 확립(Established) 표준(정의된) 프로세스를 기반으로 수행
4 예측(Predictable) 정량적 측정·통제로 일관되게 수행
5 최적화(Optimizing) 비즈니스 목표에 맞춰 지속적으로 개선
⚠ 혼동 포인트: CMMI는 1~5 (5단계), SPICE는 0~5 (6수준) — "0 불완전"이 보이면 SPICE. 지문에 ISO/IEC 15504가 있어도 SPICE. 둘 다 최상위가 "최적화"라 마지막 단계로는 구분이 안 되니 단계 수와 시작 번호로 구분하세요.
🔑 외우기 팁: CMMI는 초 → 관 → 정 → 정량 → 최 (초기·관리·정의·정량적 관리·최적화) — 앞 글자 순서로.
📝 실기 이렇게 나온다: "CMMI 성숙도 단계 중 조직의 표준 프로세스가 확립·문서화되어 있고 프로젝트가 이를 테일러링하여 사용하는 단계를 쓰시오." → 답: 3단계 정의(Defined) 단계 (프로젝트 단위 관리에 그치면 2단계 관리)
GOF

GoF 패턴 — 설명 보고 이름 맞히기 (빈출 시그널 사전)

★★★

실기 최다 빈출 유형: 패턴의 "정의 문장"을 주고 이름을 쓰게 한다. 문장 속 시그널 단어만 잡으면 즉답 가능.

GoF 23개는 생성(5)·구조(7)·행위(11)로 나뉜다. 시험은 분류 자체보다 설명 → 패턴명(국문/영문)을 쓰게 하므로, 패턴마다 결정적 시그널 단어를 1:1로 매칭해 두는 것이 득점 포인트다.

생성(Creational) — 객체를 어떻게 만들 것인가

싱글턴Singleton — 인스턴스 1개만 생성됨을 보장 + 전역 접근점 제공
팩토리 메서드Factory Method — 생성 인터페이스는 상위에, 실제 생성은 서브클래스에 위임(가상 생성자)
추상 팩토리Abstract Factory — 구체 클래스 지정 없이 관련 객체들의 '군(family)'을 묶어 생성
빌더Builder — 복잡한 객체를 단계적으로 조립, 생성 과정과 표현을 분리
프로토타입Prototype — 원본을 복제(clone)해 새 객체 생성, 생성 비용이 클 때

구조(Structural) — 클래스·객체를 어떻게 조합할 것인가

어댑터Adapter — 인터페이스를 변환해 호환되지 않는 클래스들을 연결(변환기)
브리지Bridge — 추상과 구현을 분리해 각각 독립적으로 확장 가능하게
컴포지트Composite — 트리 구조로 구성, 부분-전체(개별·복합 객체)를 동일하게 취급
데코레이터Decorator — 객체에 동적으로 기능(책임)을 추가, 상속의 대안으로 포장
퍼사드Facade — 복잡한 서브시스템에 단순화된 단일 창구(통합 인터페이스) 제공
플라이웨이트Flyweight — 인스턴스를 공유해 다수의 유사 객체에서 메모리 절약
프록시Proxy — 대리인 객체를 두어 실제 객체로의 접근을 제어(지연 로딩·권한)

행위(Behavioral) — 상호작용과 책임을 어떻게 분배할 것인가

옵서버Observer — 한 객체의 상태 변화를 의존 객체들에 자동 통지·갱신, 1:N 의존 관계
전략Strategy — 알고리즘군을 각각 캡슐화해 클라이언트가 교체(상호 교환) 가능하게
템플릿 메서드Template Method — 골격(뼈대)은 상위 클래스에 정의, 일부 단계만 하위에서 재정의
커맨드Command — 요청 자체를 객체로 캡슐화 — 큐 저장·로깅·취소(undo) 지원
상태State — 내부 상태에 따라 행위가 바뀜, 상태를 객체화해 클래스가 바뀌는 듯 동작
책임 연쇄Chain of Responsibility — 요청을 처리자 사슬(체인)을 따라 전달, 처리자를 미리 지정 안 함
이터레이터Iterator — 내부 구조를 노출하지 않고 집합의 원소를 순차 접근(순회)
중재자Mediator — 객체 간 복잡한 상호작용을 중재자 하나로 집중시켜 결합도 감소
메멘토Memento — 객체 상태를 저장해 두었다가 복원 — undo(되돌리기) 시그널
방문자Visitor — 자료 구조와 연산(처리)을 분리, 구조 변경 없이 새 연산 추가
인터프리터Interpreter — 언어의 문법 규칙을 클래스로 표현해 문장을 해석·실행
⚠ 단골 혼동 4쌍: ① 전략 vs 상태 — 전략은 클라이언트가 알고리즘을 골라 끼움, 상태는 내부 상태 변화가 스스로 행위를 바꿈. ② 데코레이터 vs 프록시 — 둘 다 감싸지만 데코레이터는 기능 추가, 프록시는 접근 제어. ③ 팩토리 메서드 vs 추상 팩토리 — 생성을 서브클래스에 위임 vs 관련 객체 '군'을 생성. ④ 어댑터 vs 퍼사드 — 인터페이스 변환 vs 복잡한 것을 단순 창구로 통합.
📝 실기 이렇게 나온다: "클래스의 인스턴스가 하나만 생성되도록 보장하고, 그 인스턴스에 대한 전역적인 접근점을 제공하는 디자인 패턴은?" → 답: 싱글턴(Singleton) ("하나만"+"전역 접근점"이 고정 시그널)
📝 실기 이렇게 나온다: "한 객체의 상태가 변하면 그 객체에 의존하는 다른 객체들에게 자동으로 통지되어 갱신되도록 일대다(1:N) 의존 관계를 정의한 패턴은?" → 답: 옵서버(Observer) (통지·1:N이 보이면 무조건 옵서버)
📝 실기 이렇게 나온다: "알고리즘의 골격을 상위 클래스에서 정의하고, 일부 단계는 하위 클래스에서 재정의하도록 하는 패턴은?" → 답: 템플릿 메서드(Template Method) (골격=상위, 일부 재정의=하위)
SCM

형상 관리(SCM) — 절차·베이스라인·도구

★★☆

"변경 사항을 체계적으로 추적·통제"가 보이면 형상 관리. 정의 서술형·절차 빈칸형·도구 분류형 세 방향으로 나온다.

형상 관리(SCM, Software Configuration Management)는 소프트웨어 개발 과정에서 발생하는 산출물의 변경 사항을 체계적으로 추적·통제하여 무결성을 보장하는 활동이다. 소스 코드만이 아니라 요구사항 명세서·설계서 등 전 단계 산출물이 대상이라는 점이 서술형 채점 포인트다.

1형상 식별관리 대상(형상 항목)을 정의·식별하고 기준선을 정함
2형상 통제변경 요청을 검토·승인해 반영 — 형상통제위원회(CCB)가 결정
3형상 감사베이스라인 변경이 제대로 됐는지 무결성을 검증·평가
4형상 기록형상·변경 이력을 기록·보고(상태 보고)

베이스라인(Baseline, 기준선): 공식적으로 검토·합의된 시점의 산출물 기준선. 이후 변경은 반드시 공식 형상 통제 절차를 거쳐야 한다 — "개발 기준점", "변경 통제의 기준"이 시그널.

도구는 저장소가 어디에 있느냐로 구분하고, 조작 용어 3개는 세트로 외운다.

체크아웃Check-Out — 저장소에서 파일(버전) 사본을 받아오기
체크인Check-In — 수정한 파일을 저장소에 새 버전으로 갱신
커밋Commit — 체크인 시 충돌(conflict)이 있으면 알리고, diff로 수정 후 최종 반영
중앙집중형서버 한 곳에 저장소 — SVN, CVS. 서버 장애 시 전체 작업 영향
분산형개발자마다 로컬 저장소를 복제 — Git(원격+로컬 이중 저장소)
🔑 두문자: 절차는 "식통감기" — 형상 식별 → 형상 통제 → 형상 감사 → 형상 기록.
⚠ 함정: Git을 중앙집중형이라고 쓰면 오답 — Git은 분산형, SVN·CVS가 중앙집중형이다. 또 승인·반영은 '통제', 검증·평가는 '감사'로 갈라 써야 하며, 버전 관리는 형상 관리의 일부이지 동의어가 아니다.
📝 실기 이렇게 나온다: "소프트웨어 개발 과정에서 발생하는 산출물의 변경 사항을 버전별로 관리하여 무결성을 유지하는 활동을 쓰시오." → 답: 형상 관리 (절차 빈칸형 "식별 → ( ) → 감사 → 기록"이면 답은 형상 통제)
MW

미들웨어 종류 — 설명 보고 이름 맞히기

★★☆

미들웨어 = 응용 프로그램과 운영 환경(OS·네트워크·DB) 사이에서 연결·통신을 중개하는 소프트웨어.

실기에서는 6종의 정의 문장을 주고 이름을 쓰게 한다. 결정적 시그널: 프로시저 호출=RPC, 메시지·비동기=MOM, 트랜잭션·예약 업무=TP 모니터, 객체·CORBA=ORB, 동적 콘텐츠·웹=WAS.

RPCRemote Procedure Call — 원격 프로시저를 마치 로컬(자기 것) 프로시저처럼 호출
MOMMessage Oriented Middleware — 메시지 기반 비동기(Asynchronous) 전달, 이기종 분산 시스템의 데이터 동기화에 사용
TP 모니터Transaction Processing Monitor — 온라인 트랜잭션을 처리·감시, 항공기·철도 예약처럼 다수 동시 요청 업무
ORBObject Request Broker — 객체 지향 미들웨어, CORBA 표준 스펙 구현
WASWeb Application Server — 웹 서버와 달리 동적 콘텐츠를 처리, DB 연동·트랜잭션 처리
DB 미들웨어클라이언트에서 원격 데이터베이스와 연결해 주는 접속 소프트웨어(ODBC 등) — 보통 2-Tier 구조

구별 1순위 축은 동기 vs 비동기다.

동기RPC — 호출하고 결과가 올 때까지 기다리는 방식이 기본
비동기MOM — 메시지를 맡겨두고 기다리지 않음, 느슨한 연계

대표 제품 예: TP 모니터 = Tuxedo·Tmax / WAS = Tomcat·JEUS·WebLogic — 제품명을 주고 종류를 묻기도 한다.

⚠ 함정: "비동기"가 보이면 무조건 MOM(RPC로 쓰면 오답). 또 WAS와 웹 서버를 혼동하지 말 것 — 웹 서버는 정적 콘텐츠, WAS는 동적 콘텐츠 처리다.
📝 실기 이렇게 나온다: "항공기나 철도 예약 업무처럼 온라인 트랜잭션 업무에서 트랜잭션을 처리·감시하는 미들웨어는?" → 답: TP 모니터(트랜잭션 처리 모니터) ("예약 업무"가 고정 시그널)
📝 실기 이렇게 나온다: "메시지 기반의 비동기형 메시지 전달 방식으로, 이기종 분산 시스템 간 데이터 동기화에 주로 사용되는 미들웨어는?" → 답: MOM(Message Oriented Middleware) (비동기+메시지 = MOM)
EAI

인터페이스 구현 — EAI 4유형 · ESB

★★★

토폴로지 그림을 주고 유형명을 쓰게 하는 단골 문제 — 연결 모양만 보면 즉답 가능.

EAI(Enterprise Application Integration)는 기업 내 상호 연동이 필요한 애플리케이션·플랫폼을 통합하는 솔루션이다. 실기는 구축 유형 4가지를 그림 또는 설명으로 구별시킨다.

●●●EAI 4유형 토폴로지
Point-to-Point       Hub & Spoke        Message Bus
  A ──── B             A       B         A    B    C
  │ ╲  ╱ │              ╲     ╱          │    │    │
  │  ╳   │              [ Hub ]       ═══╪════╪════╪═══ Bus
  │ ╱  ╲ │              ╱     ╲          │    │    │
  C ──── D             C       D         D    E    F
Point-to-Point애플리케이션을 1:1로 직접 연결 — 가장 기본, 저렴하지만 변경·재사용 어려움(N개면 연결 폭증)
Hub & Spoke중앙 허브 시스템에 집중 연결 — 확장·유지보수 용이, 단 허브 장애 시 전체 영향
Message Bus애플리케이션 사이에 미들웨어(버스)를 두고 처리 — 뛰어난 확장성·대용량 처리, 'ESB 방식'이라고도 부름
Hybrid혼합형 — 그룹 내부는 Hub & Spoke, 그룹 간에는 Message Bus, 데이터 병목 최소화

ESB(Enterprise Service Bus): 애플리케이션보다 서비스 중심의 통합을 지향하는 아키텍처. Bus 방식을 서비스 지향으로 확장한 개념으로, 특정 서비스에 국한되지 않도록 결합도를 약하게(Loosely Coupled) 유지한다는 문구가 고정 시그널이다.

JSON속성-값 쌍으로 이루어진 경량 데이터 포맷 — AJAX에서 XML을 대체해 널리 사용
XML태그 기반 마크업 언어 — 특수 목적 마크업 언어를 만드는 다목적 언어, 송수신 데이터 표현
AJAXJavaScript로 서버와 비동기 통신 — 화면 전체 새로고침 없이 일부 데이터만 갱신
⚠ 함정: Hub & Spoke와 Message Bus 구별 — 허브는 중앙 시스템 집중(허브 장애 = 전체 마비), 버스는 미들웨어 경유(뛰어난 확장성). 유형명을 물으면 Message Bus로 쓰는 게 안전하고, ESB는 4유형이 아니라 서비스 중심 통합 아키텍처로 별도 출제된다.

ISO/IEC 25010 — 제품 품질 특성 8가지

★★☆

ISO/IEC 9126을 대체한 소프트웨어 제품 품질 국제 표준. "9126의 6개 → 25010의 8개" 재편이 출제 포인트.

ISO/IEC 25010은 기존 ISO/IEC 9126(기능성·신뢰성·사용성·효율성·유지보수성·이식성 6개)을 대체하면서, 9126에서 부특성이던 보안성과 호환성이 별도 특성으로 승격되어 8개가 되었다. 실기는 특성의 정의 문장 → 특성명으로 구별시킨다.

기능 적합성명시된 요구 기능을 충족하는 정도 — 부특성: 기능 완전성·정확성·적절성
성능 효율성사용 자원 대비 성능 정도 — 부특성: 시간 반응성·자원 활용률·용량
호환성다른 제품과 공존하며 정보를 교환하는 능력 — 부특성: 공존성·상호운용성
사용성배우기 쉽고 사용하기 편한 정도 — 부특성: 학습성·운용성·접근성 등
신뢰성정해진 조건·시간에서 기능 수준을 유지하는 능력 — 부특성: 성숙성·가용성·결함 허용성·회복성
보안성정보·데이터를 보호하고 권한에 따라 접근을 허용하는 능력 — 부특성: 기밀성·무결성·부인 방지·인증성
유지보수성수정·개선이 쉬운 정도 — 부특성: 모듈성·재사용성·분석성·수정 가능성·시험 가능성
이식성다른 환경으로 이전·설치하기 쉬운 정도 — 부특성: 적응성·설치성·대체성

부특성이 어느 특성 소속인지 묻는 각도도 있다 — 아래 3개가 특히 헷갈리는 매칭이다.

가용성신뢰성의 부특성 (별도 특성 아님)
상호운용성호환성의 부특성 (정보 교환 능력)
학습성사용성의 부특성 (배우기 쉬운 정도)
🔑 외우기 팁: 9126 6개는 앞 글자 "기신사효유이"(기능성·신뢰성·사용성·효율성·유지보수성·이식성). 25010은 여기서 효율성→성능 효율성, 기능성→기능 적합성으로 이름이 바뀌고 보안성·호환성 2개가 추가된 8개.
⚠ 함정: 9126을 물으면 6개(보안성·호환성 없음, 명칭은 "효율성"), 25010이면 8개("성능 효율성"). "가용성"을 8특성 중 하나로 쓰면 오답 — 가용성은 신뢰성의 부특성이다.
📝 실기 이렇게 나온다: "ISO/IEC 25010 품질 특성 중, 소프트웨어를 다른 하드웨어·소프트웨어 환경으로 옮겨 설치하거나 적응시키기 쉬운 정도를 뜻하는 것은?" → 답: 이식성(Portability) ("다른 환경으로"가 시그널)
📝 실기 이렇게 나온다: "두 개 이상의 시스템이 같은 환경을 공유하며 서로 정보를 교환하여 사용할 수 있는 정도를 뜻하는 특성은?" → 답: 호환성(Compatibility) (교환만 콕 집으면 부특성인 상호운용성)

요구공학 — 기능 vs 비기능, 프로세스, 명세 기법

★★☆

요구사항 문장을 주고 "기능/비기능"을 고르게 하거나, 개발 프로세스의 빈칸을 채우게 한다.

기능 요구사항은 시스템이 "무엇을 하는가"(제공할 서비스·동작 자체)이고, 비기능 요구사항은 품질·제약 조건(얼마나 잘, 어떤 조건에서)이다. 문장에 숫자·품질 단어(초, %, 명, 보안, 가용성)가 보이면 대부분 비기능이다.

기능"사용자는 ID/PW로 로그인할 수 있어야 한다" — 시스템이 하는 일 자체
비기능(성능)"모든 조회 화면은 3초 이내에 응답해야 한다" — 속도 제약
비기능(성능·용량)"동시 사용자 1,000명을 수용해야 한다" — 처리 규모 제약
비기능(가용성)"시스템은 연중 99.9% 가동되어야 한다" — 품질 수준 제약

요구사항 개발 프로세스 — 순서 빈칸형이 단골이다.

1도출(Elicitation)이해관계자에게서 수집 — 인터뷰·브레인스토밍·워크숍·설문
2분석(Analysis)상충 조정, 타당성·우선순위 분석
3명세(Specification)SRS(요구사항 명세서)로 문서화
4확인(Validation)명세서가 요구를 제대로 담았는지 검증
정형 명세수학·논리 기반 표기 — Z, VDM, Petri-Net. 모호성 없음, 작성 어려움
비정형 명세자연어·다이어그램 중심 — 이해 쉬움, 모호성 발생 가능
확인 기법요구사항 리뷰(검토), 프로토타이핑, 모델 검증, 인수 테스트
🔑 외우기 팁: 프로세스는 "도분명확" — 도출 → 분석 → 명세 → 확인 (요구를 "더 분명확하게" 만드는 순서).
⚠ 함정: "로그인 기능은 3초 이내에 완료되어야 한다"처럼 한 문장에 섞이면, 동작 자체(로그인)는 기능, 3초 제약은 비기능으로 갈라 봐야 한다. 또 Z·VDM을 비정형이라고 쓰면 오답 — 수학 기호 기반은 무조건 정형 명세다.
📝 실기 이렇게 나온다: "'시스템은 동시 접속자 1,000명까지 3초 이내로 응답해야 한다'는 기능/비기능 요구사항 중 무엇인가?" → 답: 비기능 요구사항 (성능·용량이라는 품질 제약이므로)
📝 실기 이렇게 나온다: "요구사항 개발 프로세스의 빈칸을 채우시오: 도출 → 분석 → ( ) → 확인" → 답: 명세(Specification) (SRS 요구사항 명세서를 작성하는 단계)
