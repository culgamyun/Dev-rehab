부록 E. 시스템 설계 면접 — 확장·캐시·신뢰성·단골 문제

경력·복귀 면접의 합격을 가르는 관문은 "정의 암기"가 아니라 "이 상황에서 무엇을, 왜, 어떤 순서로"를 설명하는 설계 감각입니다. 부록 B(CS 단골)의 설계 "개요"를 실제 면접에서 끝까지 밀어붙일 수 있는 깊이로 끌어올립니다. 모든 예시는 가상 의류 쇼핑몰 Rehab Fashion 도메인으로 이어집니다.

🧭 이 부록 사용법

각 질문은 면접 답변 스크립트처럼 읽으세요. 비유로 큰 그림을 잡고 → 표/코드로 근거를 채우고 → 면접 꼬리 질문으로 한 단계 더 들어갑니다. 마지막 자가 진단 퀴즈는 풀면 대시보드 "오늘의 복습"에 자동 편입되어 간격 반복으로 굳습니다.

🪜 A. 확장의 사다리 (Scalability)

Q1. 사용자가 100배 늘면 무엇부터 터지고, 어떤 순서로 막나요?

설계 면접의 1번 타자입니다. 핵심은 "가장 싸고 효과 큰 것부터, 병목을 따라" 확장한다는 순서 감각입니다. 무작정 "샤딩하겠습니다"는 감점, "먼저 측정해 병목을 찾고 캐시→복제→비동기 순으로 가겠다"가 가점입니다.

💡 비유로 이해하기: Rehab Fashion 오픈런 세일

한정판 후드 세일에 손님이 몰립니다. 먼저 계산대(앱 서버)를 늘립니다(수평 확장). 그런데 계산대를 아무리 늘려도 창고 직원(DB) 한 명이 모든 재고 조회를 처리하면 거기서 줄이 막힙니다. 그래서 인기 상품을 매대 앞(캐시)에 미리 깔고, 재고 조회 사본(읽기 복제본)을 여러 개 두며, 영수증 발송 같은 일은 나중에 처리(비동기 큐)로 미룹니다.

확장 순서 — 비용 대비 효과 순:

단계 수단 막는 병목
1. 수직 확장 서버 스펙 업(CPU/RAM) 초기 단순 부하 (한계·비용 급증)
2. 무상태 + 수평 확장 + LB 서버 여러 대 + 로드밸런서(L4/L7) 앱 서버 CPU 병목
3. 캐시 Redis (Look-aside) 반복 읽기 DB 부하
4. 읽기 복제본 Replica + 읽기/쓰기 분리 읽기 트래픽 (읽기 99% 서비스)
5. 비동기 / 메시지 큐 Kafka로 무거운 작업 분리 느린 후처리(메일·집계)가 응답 지연
6. 샤딩 데이터 자체를 분할 단일 DB 쓰기/용량 한계 (최후의 수단)

💡 면접 꼬리 질문: "세션을 서버 메모리에 두면 왜 수평 확장이 깨지나요?" → 로드밸런서가 다음 요청을 다른 서버로 보내면 그 서버엔 세션이 없어 로그인이 풀립니다. 그래서 서버를 무상태(stateless)로 만들고 세션/토큰을 외부 저장소(Redis)에 둡니다 — 앞서 본 Redis 기반 JWT 세션(Ch4)가 바로 이 이유입니다.

⚡ B. 캐시 계층 (Caching)

Q2. 캐시 전략 3종과 '캐시 스탬피드'를 설명하세요

캐시는 "한 번 비싸게 구한 답을 잠깐 보관해 재사용"하는 계층입니다. 면접에선 쓰기 시 정합성과 대량 만료 시 폭주를 어떻게 다루는지를 봅니다.

💡 비유로 이해하기: 인기 매대와 '우르르 창고 돌진'

잘 나가는 후드를 매장 앞 매대(캐시)에 미리 깔면 손님이 창고(DB)까지 안 갑니다. 그런데 그 매대가 동시에 텅 비는 순간(TTL 만료), 수천 명이 한꺼번에 창고로 돌진해 창고 직원이 깔립니다 — 이것이 캐시 스탬피드(thundering herd)입니다.

3대 전략:

① Look-aside (Cache-Aside)

앱이 캐시를 먼저 보고, 없으면(miss) DB에서 읽어 캐시에 채움. 가장 흔함. 쓰기 시 DB 먼저 → 캐시 삭제가 정석.

② Write-through

쓰기를 캐시와 DB에 동시에. 캐시가 항상 최신이지만 쓰기 지연 증가.

③ Write-back

캐시에 먼저 쓰고 DB는 나중에 일괄. 가장 빠르지만 캐시 장애 시 데이터 유실 위험.

Look-aside 캐시 의사코드 (Spring @Cacheable과 동일한 흐름) 
// 상품 상세 조회 — 캐시 우선, 미스 시 DB 적재
public Product getProduct(Long id) {
    String key = "product:" + id;
    Product cached = redis.get(key);          // 1. 캐시 확인
    if (cached != null) return cached;         //    HIT → 즉시 반환

    Product p = productRepository.findById(id) // 2. MISS → DB 조회
                    .orElseThrow();
    redis.set(key, p, Duration.ofMinutes(10)); // 3. 캐시에 적재 (TTL)
    return p;
}

// 상품 수정 시 — DB 먼저 쓰고 캐시는 '삭제'(갱신 X) 가 안전
public void updateProduct(Product p) {
    productRepository.save(p);                  // DB 진실의 원천 갱신
    redis.delete("product:" + p.getId());       // 다음 읽기 때 자연히 재적재
}

캐시 스탬피드 방어 4종:

기법 핵심
분산 락 / Mutex만료 시 한 요청만 DB 재조회·재적재, 나머지는 대기 후 캐시 사용
TTL Jitter만료 시각에 랜덤 ±를 더해 동시 만료를 분산
Refresh-ahead만료 전 미리 백그라운드 갱신
논리적 만료물리 TTL은 길게, 값 안에 만료 플래그를 두고 비동기 갱신

캐시 교체(eviction) 알고리즘: LRU(가장 오래 안 쓴 것 제거 — 가장 흔함) · LFU(가장 적게 쓴 것) · FIFO(먼저 들어온 것). Redis maxmemory-policy로 설정합니다.

💡 면접 꼬리 질문: "캐시와 DB 정합성 — 수정 시 캐시를 먼저 지우나, DB를 먼저 쓰나요?" → Cache-Aside에서는 DB를 먼저 쓰고 캐시를 삭제합니다. 캐시를 먼저 지우면 그 찰나에 다른 요청이 옛 DB값을 다시 캐싱해 stale이 남을 수 있습니다(완벽하진 않아 짧은 TTL을 병행).

🗄️ C. 데이터 계층 확장 (Replication · Sharding)

Q3. DB가 한계입니다 — 복제 / 파티셔닝 / 샤딩의 차이는?

"인덱스(Ch3)와 캐시로도 안 될 때" 비로소 데이터 계층을 쪼갭니다. 셋을 혼동하면 감점이니 목적으로 구분하세요.

기법 무엇을 주로 해결 대표 함정
복제 (Replication) 같은 데이터를 사본으로 읽기 부하·가용성 복제 지연(쓰고 바로 읽으면 옛값)
파티셔닝 (Partitioning) 한 DB 안에서 테이블 분할 큰 테이블 스캔·관리 파티션 키 안 타면 전체 스캔
샤딩 (Sharding) 데이터를 여러 DB로 수평 분할 쓰기·용량 한계 핫스팟·교차 샤드 조인/트랜잭션

💡 비유로 이해하기: 창고 전략

복제 = 같은 재고 목록을 여러 창고에 복사해 조회를 분산(단, 본점이 막 입고한 건 지점에 늦게 반영 = 복제 지연). 샤딩 = 아예 지역별 창고로 나눠 서울 고객은 서울 창고만 — 쓰기까지 분산되지만, "전국 통합 매출 정렬"은 모든 창고를 뒤져 합쳐야 해 어려워집니다.

샤드 키 선택이 전부입니다. user_id 해시로 잡으면 특정 유저 데이터가 한 샤드에 모여 골고루 분산되지만(핫스팟 완화), 여러 유저에 걸친 집계·조인이 어려워집니다. 노드 증감 시 재분배를 줄이려 Consistent Hashing을 씁니다.

💡 면접 꼬리 질문: "방금 주문을 넣고 바로 '내 주문 목록'을 조회했는데 안 보입니다. 왜죠?" → 쓰기는 마스터, 읽기는 복제본으로 갔는데 복제 지연으로 아직 반영 전입니다. 해결: 쓰기 직후 일정 시간은 마스터에서 읽기(read-your-writes), 또는 캐시에 방금 쓴 값을 함께 반영.

🛡️ D. 신뢰성 패턴 (면접 빈출)

Q4. 멱등성(Idempotency) — 중복 결제/주문을 어떻게 막나요?

네트워크는 언제든 끊기고, 클라이언트는 재시도합니다. "같은 요청을 여러 번 보내도 결과가 한 번과 같다"는 성질이 멱등성입니다. GET/PUT/DELETE는 본래 멱등, POST(주문 생성)는 비멱등이라 별도 장치가 필요합니다.

💡 비유로 이해하기: 엘리베이터 버튼

엘리베이터 버튼을 열 번 눌러도 한 번 부른 것과 같습니다. 주문도 "결제하기"를 따닥 두 번 눌러도 한 건만 생성되어야 합니다.

Idempotency-Key 헤더로 중복 주문 1회 보장 (Redis SETNX) 
// 클라이언트가 요청마다 고유 키를 헤더에 동봉: Idempotency-Key: 5f3a-...
@PostMapping("/api/orders")
public ResponseEntity<OrderRes> create(
        @RequestHeader("Idempotency-Key") String key,
        @RequestBody OrderReq req) {

    // SETNX: 키가 없을 때만 저장 → '첫 요청'만 true
    boolean first = redis.setIfAbsent("idem:" + key, "1", Duration.ofHours(24));
    if (!first) {
        // 이미 처리된 요청 → 저장해 둔 결과를 그대로 반환 (중복 생성 X)
        return ResponseEntity.ok(orderService.findByIdemKey(key));
    }
    OrderRes res = orderService.place(req, key);
    return ResponseEntity.ok(res);
}

💡 면접 꼬리 질문: "재시도는 어떻게 안전하게 하나요?" → 지수 백오프(exponential backoff) + 지터로 간격을 늘려 재시도하되, 서버는 멱등성 키로 중복을 흡수합니다. 둘은 짝꿍입니다 — 재시도만 있고 멱등성이 없으면 중복, 멱등성만 있고 재시도가 없으면 유실.

Q5. Rate Limiting — 폭주·어뷰징으로부터 서버를 어떻게 보호하나요?

"초당 N회"를 넘는 요청을 거절(429 Too Many Requests)해 서버와 비용을 지킵니다. 알고리즘 선택이 단골 질문입니다.

💡 비유로 이해하기: 놀이공원 시간당 입장 제한

인기 어트랙션은 시간당 정원이 있습니다. 토큰(입장권)이 일정 속도로 보충되고, 토큰이 있으면 입장, 없으면 다음 보충까지 대기 — 이것이 Token Bucket입니다.

알고리즘 특징
Token Bucket토큰을 일정 속도 보충, 순간 버스트 허용. 가장 널리 쓰임
Leaky Bucket고정 속도로 처리(누수). 출력이 매끄럽지만 버스트 흡수 약함
Fixed Window1분 단위 카운트. 단순하나 경계(59초/0초)에서 2배 폭주
Sliding Window이동 구간으로 경계 문제 완화. 정확하지만 비용↑

분산 환경에선 카운터를 Redis에 두어 모든 서버가 같은 한도를 공유합니다. INCR 자체는 원자적이지만, 첫 키 생성 시 INCR과 EXPIRE 사이 틈에 TTL이 안 붙을 수 있어 실무에선 Lua 스크립트나 SET ... EX NX로 원자화합니다.

💡 면접 꼬리 질문: "한도를 IP 기준으로 잡을지, 사용자 기준으로 잡을지?" → 로그인 전 API는 IP, 로그인 후는 사용자(또는 API 키) 기준이 일반적이며, 공용 NAT/회사망의 다수 사용자가 한 IP를 공유하는 경우를 고려해야 합니다.

🧩 E. 설계 면접 워크북 (단골 문제)

설계 면접을 푸는 7단계 프레임

백지 앞에서 얼지 않으려면 틀을 외워두세요. 면접관은 답이 아니라 접근 과정을 봅니다.

1. 요구사항 명확화

기능/비기능 구분. "읽기 많나 쓰기 많나? 일관성 vs 가용성 어디 무게?"를 먼저 질문.

2. 용량 추정

DAU → QPS, 저장 용량, 대역폭을 어림. 읽기:쓰기 비율 산출.

3. API 설계

핵심 엔드포인트 몇 개를 시그니처로(Ch4 REST).

4. 데이터 모델

엔티티·관계·인덱스(Ch3). SQL vs NoSQL 선택 근거.

5. 하이레벨 구조

클라 → LB → 앱 → 캐시/DB/큐 큰 그림.

6. 병목 & 심화

Q1~Q5(확장·캐시·샤딩·멱등·rate limit)를 여기서 투입.

7. 트레이드오프

"이래서 이걸 택했고, 대신 이걸 포기"를 말로. CAP·정합성 vs 지연.

단골 설계 문제 4종 — 압축 풀이

① URL 단축기

긴 URL → 짧은 키. 카운터+Base62 또는 해시(충돌 처리). 읽기가 압도적이라 리다이렉트 캐시(Redis)가 핵심. 301 vs 302(통계 원하면 302).

② 뉴스피드

Push(fan-out on write) vs Pull(on read). 팔로워 많은 셀럽은 push가 폭발 → 하이브리드. 타임라인 캐시.

③ 실시간 채팅

WebSocket 상시 연결(Ch7). 메시지 영속·순서(시퀀스), 미수신 보관, 다중 서버는 pub/sub으로 팬아웃.

④ 이커머스 주문/재고

동시 차감 정합성 — DB 비관/낙관 락 vs Redis 분산락 vs 큐 직렬화. 결제·배송 분산 트랜잭션은 Saga(Ch8) + 멱등성(Q4).

🔗 각 문제는 본 부록의 패턴으로 풀립니다: 읽기 폭주→캐시(Q2), 쓰기 한계→샤딩(Q3), 중복→멱등성(Q4), 폭주→rate limit(Q5).

🎤 모의 면접 — 시스템 설계

실제 면접처럼 꼬리에 꼬리를 무는 흐름입니다. 면접관 질문 → 답변 뼈대 → 이어지는 꼬리 질문 순으로, 소리 내어 답해 보세요.

🗣️ "초당 1만 건 주문이 들어오는 이커머스, 어디서 먼저 터지고 어떤 순서로 막을지 설계해 보세요."

답변 뼈대: "먼저 측정으로 병목을 찾겠다"를 전제로 → 앱을 무상태로 만들어 수평 확장 + 로드밸런서 → 읽기는 Redis 캐시 · 읽기 복제본 → 재고 차감은 동시성 제어(분산락 또는 큐 직렬화) → 결제·알림 등 후처리는 비동기 큐로 분리. 무작정 샤딩은 최후의 수단.

↪️ 꼬리: "재고 차감을 동시성 안전하게 하려면?" → 비관/낙관 락 vs Redis 분산락 vs 큐 직렬화의 트레이드오프(정합성↔처리량)로 답합니다.

🗣️ "캐시를 도입했는데 특정 시점에 DB가 폭주합니다. 원인과 대책은?"

답변 뼈대: 대량 키가 동시에 만료되어 한꺼번에 DB로 몰리는 캐시 스탬피드가 의심됩니다. 대책은 TTL 지터(만료 분산) · 분산 락/뮤텍스(한 요청만 재적재) · refresh-ahead · 논리적 만료.

↪️ 꼬리: "캐시와 DB 정합성은 어떻게?" → Cache-Aside에서는 DB 먼저 쓰고 캐시 삭제, 짧은 TTL을 병행해 stale을 줄입니다.

🗣️ "결제 중복이 보고됐습니다. 어떻게 진단하고 막겠어요?"

답변 뼈대: 네트워크 타임아웃 재시도로 인한 중복이 흔합니다. Idempotency-Key를 받아(Redis SETNX) 첫 요청만 처리하고 재시도는 저장된 결과를 반환합니다. 지수 백오프 재시도 + 멱등성은 짝꿍.

↪️ 꼬리: "결제·재고·배송에 걸친 분산 트랜잭션은?" → 2PC 대신 Saga + 보상 트랜잭션, 각 단계는 멱등하게(Ch8).

Q6. 회복탄력성 — 타임아웃·재시도·서킷 브레이커·벌크헤드

MSA에서 하나의 느린 서비스는 호출 스레드를 점유한 채 줄줄이 장애를 전파시킵니다(연쇄 장애, cascading failure). 회복탄력성 패턴은 "실패는 어차피 일어난다"는 전제 아래 장애를 격리하고 빠르게 실패(fail-fast)시키는 기술이며, 면접에서는 네 패턴을 언제·어떤 조합으로 쓰는지가 핵심 포인트입니다.

💡 비유로 이해하기: 배의 격벽과 두꺼비집

옛 범선은 선체를 여러 격벽(bulkhead)으로 나눠, 한 칸에 물이 차도 나머지 칸이 멀쩡해 배가 가라앉지 않습니다 → 벌크헤드(자원 격리).
전기 합선이 나면 두꺼비집(차단기)이 회로를 끊어 집 전체로 불이 번지는 걸 막습니다. 잠시 후 살짝 올려 보고(Half-Open) 괜찮으면 복구합니다 → 서킷 브레이커.
택배가 안 오면 무한정 기다리지 않고(타임아웃), 잠시 뒤 다시 시켜 보되(재시도) 점점 간격을 늘려(백오프) 가게에 주문 폭주를 일으키지 않습니다.

장애 전파를 막는 4대 패턴:

⏱️ 타임아웃 (Timeout)

응답을 무한정 기다리지 않고 상한 시간을 넘기면 끊습니다. 타임아웃이 없으면 느린 응답 하나가 호출 스레드를 점유해 스레드 풀 고갈 → 연쇄 장애로 번집니다. connect/read 타임아웃을 모두 설정하는 것이 정석입니다.

🔁 재시도 (Retry)

일시적 오류(네트워크 순단, 502/503)는 다시 시도하면 성공할 수 있습니다. 단 지수 백오프(exponential backoff)로 간격을 늘리고 지터(jitter, 무작위 흔들기)를 더해, 모든 클라이언트가 동시에 재시도하는 재시도 폭풍·thundering herd를 막아야 합니다.

⚡ 서킷 브레이커 (Circuit Breaker)

실패율이 임계치를 넘으면 회로를 Open해 일정 시간 호출 자체를 차단(즉시 fail-fast)합니다. 이미 죽은 서비스를 계속 두드려 부하를 가중시키는 것을 막고, 호출 측 자원을 보호합니다.

🚪 벌크헤드 (Bulkhead)

서비스별로 스레드 풀·세마포어(동시 호출 수)를 격리합니다. 결제 API가 느려져도 그 자원만 소진될 뿐, 상품 조회용 자원은 멀쩡해 전체 마비를 막습니다(자원 격리).

서킷 브레이커 상태 전이 (Closed → Open → Half-Open):

  • Closed(닫힘, 정상): 요청을 정상적으로 흘려보내며 성공·실패 통계를 집계합니다. 실패율이 임계치(예: 최근 호출의 50%) 이상이면(최소 호출 수 충족 후) → Open으로 전이.
  • Open(열림, 차단): 실제 호출 없이 즉시 예외를 반환(fail-fast)하고, 미리 준비한 폴백(fallback)으로 응답합니다. 대기 시간(wait duration)이 지나면 → Half-Open으로 전이.
  • Half-Open(반열림, 탐색): 소수의 시험 호출만 통과시켜 회복 여부를 확인합니다. 성공하면 → Closed로 복구, 여전히 실패하면 → 다시 Open.

재시도의 철칙 — 멱등 작업에만, 백오프는 필수:

  • 재시도는 멱등(idempotent)한 작업에만 안전합니다. 조회(GET)는 여러 번 보내도 서버 상태를 바꾸지 않지만, "결제 승인"·"주문 생성" 같은 비멱등 작업을 무턱대고 재시도하면 중복 결제·이중 주문이 발생합니다.
  • 백오프가 없으면 재시도 폭풍: 서버가 잠깐 흔들릴 때 모든 클라이언트가 즉시·동시에 재시도하면, 회복 중인 서버에 트래픽이 몰려 오히려 완전히 무너집니다. 그래서 간격을 1s → 2s → 4s로 늘리고(지수 백오프) 거기에 무작위 흔들림(지터)을 더해 재시도 시점을 분산시킵니다.
  • 조합 순서: Resilience4j 기본 aspect 순서상 Retry가 CircuitBreaker를 바깥에서 감쌉니다. 다만 회로가 Open이면 CallNotPermittedException이 Retry로 전달되므로, 이 예외를 ignoreExceptions로 재시도 대상에서 빼서 차단된 호출을 헛되이 재시도하지 않도록 명시해야 합니다.
Resilience4j — 결제 호출에 4대 패턴 선언적 적용 (Spring Boot) 
// Resilience4j 기본 aspect 순서로 바깥→안쪽으로 적용된다(소스의 어노테이션 나열 순서와 무관):
// Retry( CircuitBreaker( RateLimiter( TimeLimiter( Bulkhead( 실제 호출 ) ) ) ) )
@Retry(name = "payment")                              // 일시 오류 시 재시도(백오프는 yml에서 설정)
@CircuitBreaker(name = "payment", fallbackMethod = "payFallback") // 실패율↑ → Open, 폴백 호출
@Bulkhead(name = "payment", type = Bulkhead.Type.SEMAPHORE)       // 동시 호출 수 격리
@TimeLimiter(name = "payment")                        // 비동기 호출의 응답 시간 상한
public CompletableFuture<PayResult> pay(Long orderId) {
    // 외부 결제 PG사 호출 — 멱등키(idempotencyKey)로 중복 결제 방지
    return paymentClient.requestAsync(orderId, idempotencyKeyOf(orderId));
}

// 폴백: 회로가 Open이거나 예외 발생 시 호출됨 (예외 타입을 마지막 인자로 받음)
public CompletableFuture<PayResult> payFallback(Long orderId, Throwable t) {
    log.warn("결제 폴백 동작 — orderId={}, cause={}", orderId, t.toString());
    // 즉시 실패시키되, 사용자에겐 "잠시 후 다시 시도" 같은 graceful한 응답을 반환
    return CompletableFuture.completedFuture(PayResult.pending(orderId));
}
application.yml — 지수 백오프 + 지터 + 임계치 설정 
resilience4j:
  retry:
    instances:
      payment:
        max-attempts: 3                  # 최초 1회 + 재시도 2회
        wait-duration: 1s                # 기본 대기
        enable-exponential-backoff: true # 재시도 대기 1s → 2s (max-attempts=3이면 재시도는 2회)
        exponential-backoff-multiplier: 2
        enable-randomized-wait: true     # 지터: 대기 시간에 무작위 흔들림 추가 → 재시도 폭풍 방지
        retry-exceptions:                # 멱등하게 재시도해도 되는 예외만 지정
          - java.io.IOException
  circuitbreaker:
    instances:
      payment:
        failure-rate-threshold: 50       # 최소 호출 수 충족 후 실패율 50% 이상이면 Open
        sliding-window-size: 10          # 최근 10건 기준으로 실패율 계산
        wait-duration-in-open-state: 10s # Open 유지 10초 후 Half-Open으로 전이
        permitted-number-of-calls-in-half-open-state: 3 # Half-Open에서 시험 호출 3건

💡 면접 꼬리 질문: "재시도와 멱등성은 무슨 관계인가요? 비멱등 작업은 어떻게 안전하게 재시도하나요?" → 재시도는 같은 요청을 여러 번 보낼 수 있으므로, "여러 번 실행해도 결과가 한 번 실행한 것과 같다"는 멱등성이 전제될 때만 안전합니다. GET·PUT·DELETE는 본래 멱등하지만 POST(결제·주문 생성)는 비멱등이라, 그냥 재시도하면 중복이 발생합니다. 비멱등 작업은 멱등키(Idempotency-Key)를 부여해 서버가 같은 키의 요청을 한 번만 처리(중복 키는 이전 결과를 그대로 반환)하도록 만들어 멱등성을 인위적으로 부여합니다. 또한 타임아웃으로 끊긴 요청은 서버에서 실제로 처리됐을 수 있어 결과가 불확실(in-doubt)하므로, 멱등키 없는 재시도는 특히 위험합니다.

Q7. CAP 정리와 일관성 모델 — Strong vs Eventual

분산 시스템에서 데이터를 여러 노드에 복제하면 "장애가 나도 잘 돌아가게(가용성)"와 "어디서 읽어도 같은 값(일관성)"을 동시에 100% 보장할 수 없습니다. CAP 정리는 이 한계를 정리한 명제이고, 면접에서는 "왜 둘 중 하나를 택해야 하는가"와 "우리 도메인엔 무엇이 맞나"를 함께 묻습니다.

💡 비유로 이해하기: 멀리 떨어진 두 지점장의 장부

서울 지점과 부산 지점이 같은 고객 장부를 각자 들고 있다고 합시다. 평소엔 전화로 실시간 동기화해서 문제가 없습니다.
그런데 두 지점을 잇는 전화선이 끊겼습니다(네트워크 분단, P). 이때 선택지는 두 가지입니다.
① "동기화 안 되면 입금 처리 거부" → 양쪽 장부가 항상 일치(일관성 C), 대신 손님은 거절당함(가용성 포기).
② "일단 각자 받아두고 나중에 맞추자" → 손님은 항상 처리됨(가용성 A), 대신 잠깐 두 장부가 다를 수 있음(일관성 포기).
전화선이 멀쩡할 땐 둘 다 가능합니다. 분단이 났을 때만 C냐 A냐를 고르는 것이 CAP의 핵심입니다.

CAP 정리의 정확한 의미 — 흔한 오해는 "C, A, P 셋 중 둘만 고른다"인데, P(Partition Tolerance, 분단 내성)는 네트워크가 분단될 수 있는 분산 시스템이라면 선택이 아니라 전제입니다. 따라서 실제 선택은 "분단이 발생한 순간 C를 포기할 것이냐, A를 포기할 것이냐"입니다.

C — Consistency

모든 노드가 같은 시점에 같은 데이터를 본다(여기서 C는 트랜잭션의 ACID 일관성이 아니라 선형성에 가까운 "최신값 보장"을 뜻함).

A — Availability

살아있는 모든 노드가 요청에 (에러가 아닌) 정상 응답을 돌려준다.

P — Partition Tolerance

노드 간 통신이 끊겨도 시스템이 계속 동작한다. 분산 시스템에선 사실상 필수 전제.

CP 시스템 vs AP 시스템 — 분단 시 C를 지키면 CP, A를 지키면 AP입니다.

구분CP (일관성 우선)AP (가용성 우선)
분단 시 동작소수파(minority) 노드는 응답 거부/대기 → 낡은 값 안 줌모든 노드가 응답 → 잠시 값이 어긋날 수 있음
대표 예시ZooKeeper, etcd, Consul, HBase, (단일 리더) RDBCassandra, DynamoDB, Riak, CouchDB
합의/복제 방식Raft/Paxos 등 과반수 쿼럼 합의다중 리더·gossip, 충돌은 사후 해결(LWW, 벡터 클록 등)
전형적 용도리더 선출, 분산 락, 설정/메타데이터, 서비스 디스커버리대규모 쓰기, 로그/이벤트, 세션, 피드, 카탈로그

강한 일관성(Strong) vs 최종 일관성(Eventual)과 사용자 체감 — 강한 일관성은 "쓰기가 끝나면 그 이후의 모든 읽기는 반드시 새 값을 본다"를 보장합니다. 최종 일관성은 "쓰기를 멈추면 언젠가는 모든 복제본이 같은 값으로 수렴한다"만 보장하고, 그 사이엔 노드마다 다른 값을 줄 수 있습니다. 이 틈이 사용자 체감으로 드러나는 대표 사례가 "방금 내가 쓴 댓글이 새로고침하면 사라지는" 문제입니다. 쓰기는 리더(또는 노드 A)에 갔는데, 이어진 읽기가 아직 복제가 안 된 노드 B로 라우팅되면 자기 글이 안 보입니다.

해결책 — Read-Your-Writes(RYW) 일관성: 시스템 전체를 강한 일관성으로 만들지 않고, "최소한 자기 자신이 쓴 것은 항상 보이게" 하는 세션 단위 보장입니다. 구현 방법은 다음과 같습니다.

  • 리더에서 읽기(read from leader): 사용자가 방금 수정한 데이터(예: 본인 프로필)는 일정 시간 동안 복제본이 아닌 리더에서 읽도록 라우팅한다.
  • 버전/타임스탬프 기준 읽기: 클라이언트가 마지막으로 쓴 시점(또는 로그 위치)을 들고 다니며, 그 시점 이상으로 복제가 끝난 복제본에서만 읽는다.
  • 세션 고정(sticky session): 같은 사용자의 읽기/쓰기를 같은 노드로 보내 본인 쓰기를 항상 보게 한다.
Read-Your-Writes: 방금 쓴 사용자는 리더에서 읽기
// 사용자가 최근에 글을 쓴 직후라면, 복제 지연으로 자기 글이 안 보일 수 있다.
// 그래서 "최근 쓰기 후 X초 동안"은 리더에서 읽는 간단한 휴리스틱이다.
// (주의: 복제 지연이 그 시간보다 길면 깨질 수 있어, 엄밀한 보장은
//  복제 위치(LSN)·버전을 확인하는 아래 "버전 기준 읽기"가 필요하다.)
public Post getMyPost(long userId, long postId) {
    long lastWriteAt = session.getLastWriteTimestamp(userId); // 이 사용자의 마지막 쓰기 시각(ms)
    long now = System.currentTimeMillis();

    // 마지막 쓰기로부터 1초가 안 지났으면 복제가 아직 안 끝났을 수 있다고 보고 리더에서 읽음
    if (now - lastWriteAt < 1000) {
        return leaderDb.findPost(postId);   // 항상 최신값 → 내 글이 보임(강한 읽기)
    }
    // 충분히 지났으면 복제본에서 읽어 리더 부하를 덜어줌(최종 일관성 허용)
    return replicaDb.findPost(postId);
}

// 쓰기 시점에 타임스탬프를 세션에 기록해 두는 것이 핵심이다.
public void writePost(long userId, Post post) {
    leaderDb.insert(post);
    session.setLastWriteTimestamp(userId, System.currentTimeMillis());
}

PACELC — CAP의 빈칸을 채우는 보강: CAP은 "분단(P)일 때 C냐 A냐"만 말하지, 평상시 트레이드오프는 설명하지 않습니다. PACELC는 이를 보강합니다 — 분단(P)이면 A와 C 중 택1, 그렇지 않다면(Else, L과 C 사이 택1). 즉 네트워크가 멀쩡할 때조차 강한 일관성을 지키려면 여러 복제본의 동기 확인을 기다려야 하므로 지연(Latency)이 늘어납니다. Dynamo·Cassandra는 보통 PA/EL(가용성·낮은 지연 우선), 강한 일관성 RDB는 PC/EC로 분류됩니다.

💡 면접 꼬리 질문: "쇼핑몰에서 장바구니와 계좌 잔액(결제)에는 각각 어떤 일관성을 쓰겠습니까?" → 둘은 정답이 다릅니다. 장바구니는 AP/최종 일관성이 적합합니다 — 잠깐 항목이 어긋나도 비즈니스 손상이 작고, 오히려 "담기가 항상 성공"하는 가용성이 더 중요하며, 충돌은 병합(여러 기기에서 담은 항목 합치기, 삭제는 tombstone으로 표시)으로 사용자에게 유리하게 해결할 수 있습니다. 반면 잔액·재고 차감·결제는 강한 일관성(CP)이 필요합니다 — 이중 차감이나 마이너스 잔액은 직접적 금전 손실이라, 분단 시엔 차라리 거래를 거절(가용성 희생)하더라도 정확성을 지켜야 하고, 보통 단일 리더 + 트랜잭션(또는 합의 기반)으로 처리합니다. 핵심 답변은 "일관성을 시스템 전체가 아니라 도메인·데이터별로 차등 적용한다"는 것입니다.

Q8. CDN — 엣지 캐시·Cache-Control·캐시 무효화

CDN은 정적 자산 배포와 전역 서비스 성능의 핵심입니다. 면접에서는 "왜 빨라지는가"를 넘어 Cache-Control 헤더의 정확한 의미와 배포 후 캐시 무효화 전략을 정량적으로 설명할 수 있는지를 봅니다.

💡 비유로 이해하기: 동네마다 들어선 편의점 물류 창고

본사 창고(오리진 서버)가 서울에 하나뿐이라면, 부산 손님은 매번 서울까지 택배를 받아야 해 느립니다. 대신 전국 동네마다 작은 물류 창고(엣지 PoP)를 두고 잘 팔리는 물건(정적 자산)을 미리 채워두면, 손님은 가장 가까운 창고에서 즉시 받습니다.
본사는 주문 폭주(오리진 부하)에서 벗어나고, 손님은 거리(지연)가 짧아집니다. 단, 창고에 옛날 재고가 남아 있으면 신상품이 안 보이는 문제(캐시 무효화)가 생깁니다.

CDN이 빠른 이유 — 엣지 캐시의 원리:

지리적 근접 (Edge PoP)

전 세계 수백 개 PoP(Point of Presence) 중 사용자와 가장 가까운 노드가 응답. RTT(왕복 지연)가 줄어 TTFB가 짧아집니다.

오리진 오프로드

엣지에 캐시된 자산은 오리진까지 가지 않습니다. 트래픽의 대부분을 엣지가 흡수해 오리진 부하·대역폭 비용이 급감합니다.

캐시 HIT / MISS

HIT면 엣지가 즉시 응답, MISS면 오리진에서 받아온 뒤 저장(채우기)하고 응답. 이후 동일 요청은 HIT가 됩니다.

연결 재사용·TLS 종단

엣지가 사용자와 가까운 곳에서 TLS 핸드셰이크를 끝내고, 오리진까지는 유지되는 백본 커넥션을 재사용해 핸드셰이크 비용을 절감합니다.

Cache-Control — 캐시 수명을 결정하는 핵심 헤더: 무엇을, 얼마나, 누가 캐시할 수 있는지를 서버가 지시합니다.

디렉티브 의미 적용 대상
max-age=31536000 브라우저 캐시 유효 시간(초). 이 시간 내엔 네트워크 요청 자체를 생략(fresh). 해시된 정적 자산(1년)
s-maxage CDN(공유 캐시) 전용 수명. 공유 캐시에서 max-age를 덮어씀. 브라우저는 짧게, CDN은 길게 분리 가능. CDN 캐시 정책 분리
no-store 어디에도 저장 금지. 매번 오리진에서 새로 받음. 결제·개인정보 응답
no-cache 저장은 하되 사용 전 반드시 재검증(304 조건부). no-store와 혼동 금지. HTML 문서
private / public private=브라우저만(개인화 응답), public=CDN 등 공유 캐시도 저장 허용. 로그인 사용자 / 공용 자산

ETag와 조건부 요청(304): 캐시가 만료되어도 내용이 안 바뀌었으면 본문을 다시 안 받는 재검증 메커니즘입니다.

  • 서버가 응답에 ETag: "a1b2c3"(콘텐츠 지문)를 실어 보냄.
  • 캐시 만료 후 브라우저는 If-None-Match: "a1b2c3"를 붙여 재요청.
  • 내용이 같으면 서버는 본문 없이 304 Not Modified만 반환 → 대역폭 절감. 바뀌었으면 200과 새 본문.
  • 유사 메커니즘으로 Last-Modified + If-Modified-Since(시간 기반)가 있습니다.

캐시 무효화(Invalidation) — 핵심 전략 비교:

전략 동작 장점 / 단점
파일명 해시
(content hashing)		 내용이 바뀌면 파일명이 바뀜: app.3f9a1c.js. URL이 달라지니 새 파일로 인식. 장점: 자산에 max-age=1년, immutable을 안전하게 부여, purge 불필요. 단점: 빌드 파이프라인 필요.
Purge
(강제 만료)		 같은 URL의 캐시를 CDN API로 즉시 무효화. 다음 요청은 MISS로 오리진 재조회. 장점: 긴급 롤백·핫픽스에 유용. 단점: 전파 지연, 대량 purge 시 오리진 부하 급증(thundering herd).

실무 정석은 해시 파일명 + 긴 immutable 캐시를 기본으로 하고, purge는 예외적 핫픽스용으로만 씁니다.

캐시 가능한 것 vs 아닌 것:

  • 캐시 가능(public): JS·CSS·이미지·폰트 등 모든 사용자에게 동일한 정적 자산, 공개 상품 목록 같은 비개인화 응답.
  • 캐시 금지/private: 로그인 사용자 이름이 박힌 페이지, 장바구니·주문 내역, Set-Cookie가 붙은 응답, 결제 정보 → private 또는 no-store. 개인화 응답을 public으로 캐시하면 다른 사용자에게 남의 데이터가 노출되는 치명적 사고로 이어집니다.
  • Vary 헤더: 동일 URL이라도 Vary: Accept-Encoding처럼 요청 헤더에 따라 응답이 갈리면 캐시 키를 분리해 잘못된 응답 재사용을 막습니다.
Spring — 자산 종류별 캐시 헤더 분기
// Rehab Fashion 쇼핑몰: 정적 자산과 개인화 응답의 캐시 정책을 분리
@RestController
public class AssetController {

    // 1) 해시된 정적 자산 → 1년 캐시 + immutable (재검증조차 생략)
    //    파일명이 바뀌면 URL이 바뀌므로 영구 캐시해도 안전
    @GetMapping("/static/{file}")
    public ResponseEntity<Resource> staticAsset(@PathVariable String file) {
        Resource res = loadHashedAsset(file);
        return ResponseEntity.ok()
            // public: CDN 같은 공유 캐시도 저장 허용
            // max-age 31536000초 = 1년, immutable: 만료 전 재검증 안 함
            .header("Cache-Control", "public, max-age=31536000, immutable")
            .body(res);
    }

    // 2) 로그인 사용자의 장바구니 → 절대 공유 캐시에 저장 금지
    @GetMapping("/cart")
    public ResponseEntity<CartDto> myCart(@AuthenticationPrincipal User user) {
        CartDto cart = cartService.findByUser(user.getId());
        return ResponseEntity.ok()
            // private: 브라우저(개인)만 저장, CDN은 저장 금지
            // no-store까지 쓰면 브라우저 캐시도 막아 더 안전
            .header("Cache-Control", "private, no-store")
            .body(cart);
    }

    // 3) 공개 상품 목록 → CDN은 길게(s-maxage), 브라우저는 짧게(max-age)
    @GetMapping("/products")
    public ResponseEntity<List<ProductDto>> products() {
        List<ProductDto> list = productService.findAll();
        return ResponseEntity.ok()
            // 브라우저 60초 fresh, CDN(s-maxage) 300초 fresh
            .header("Cache-Control", "public, max-age=60, s-maxage=300")
            .body(list);
    }
}

💡 면접 꼬리 질문: "배포를 새로 했는데 일부 사용자에게 여전히 옛날 JS가 보입니다. 원인과 해결책은?" → 원인은 옛 자산이 브라우저/CDN 캐시에 max-age로 남아 fresh 상태이기 때문입니다. 특히 고정된 파일명(예: app.js)에 긴 max-age를 걸면 새 코드가 배포돼도 캐시된 옛 파일이 그대로 쓰입니다. 해결은 ① 파일명 해시(app.3f9a1c.js)로 내용이 바뀌면 URL이 바뀌게 하고, 이 파일을 참조하는 HTML(엔트리)에는 no-cache를 걸어 항상 재검증하게 합니다. 그래야 새 HTML이 새 해시 파일을 가리켜 즉시 갱신됩니다. 긴급 상황이면 ② CDN purge로 강제 무효화합니다. 흔한 실수는 HTML까지 길게 캐시해 새 자산 참조가 영영 전파 안 되는 경우입니다.

Q9. 대용량 파일/이미지 업로드 — Presigned URL·S3·CDN

"수백 MB 동영상이나 고해상도 이미지를 어떻게 업로드하나요?"는 시스템 디자인 면접의 단골 질문입니다. 핵심은 파일 바이트가 앱 서버를 통과하지 않게 만드는 것이며, Presigned URL은 그 표준 해법입니다.

💡 비유로 이해하기: 택배 보관함 일회용 비밀번호

친구에게 큰 짐을 전달할 때 내가 직접 짐을 받아 다시 보관함에 넣어주면(앱 서버 경유) 내 팔도 아프고 시간도 오래 걸립니다.
대신 관리실(서버)에서 특정 보관함에만, 10분 동안만 유효한 일회용 비밀번호를 발급해주면, 친구가 직접 보관함(S3)에 짐을 넣습니다. 나는 비밀번호만 발급할 뿐 무거운 짐은 만지지 않습니다.

① 나쁜 방법: 앱 서버 경유 업로드의 3대 병목

대역폭 낭비

클라이언트 → 서버 → S3로 같은 바이트가 두 번 흐릅니다. 서버 네트워크 대역폭을 파일 크기만큼 그대로 소모해, 동시 업로드 100건이면 서버가 곧장 포화됩니다.

메모리·디스크 압박

멀티파트 바디를 메모리/임시 디스크에 버퍼링하면 큰 파일 몇 개로 OOM이 발생합니다. 스트리밍해도 스레드가 업로드 시간만큼 점유됩니다(블로킹).

타임아웃·확장 불가

느린 모바일 회선에서 300MB 업로드는 수 분이 걸려 로드밸런서/프록시 타임아웃에 걸립니다. 서버를 스케일아웃해도 대역폭 비용만 늘어납니다.

② Presigned URL 흐름 — 서버는 "권한을 위임하는 서명"만 하고, 실제 바이트 전송은 클라이언트와 S3가 직접 처리합니다.

  • 1. 권한 요청: 클라이언트가 인증 토큰과 함께 POST /uploads/presign으로 파일명·콘텐츠 타입·크기를 보냅니다.
  • 2. URL 발급: 서버가 AWS 자격증명으로 PUT용 presigned URL(만료시간 포함)을 서명해 발급합니다. 객체 키는 서버가 정합니다(예: uploads/{userId}/{uuid}.jpg) — 클라이언트가 임의 경로를 지정해 덮어쓰는 것을 막기 위함입니다.
  • 3. 직접 PUT: 클라이언트가 그 URL로 S3에 바이트를 직접 PUT합니다. 앱 서버를 전혀 거치지 않습니다.
  • 4. 콜백/메타 저장: 업로드 성공 후 클라이언트가 서버에 알리거나(또는 ⑤의 S3 이벤트로) 서버가 DB에 메타데이터(키, 크기, 상태=UPLOADED)를 기록합니다.
Presigned PUT URL 발급 (Spring + AWS SDK v2)
@Service
@RequiredArgsConstructor
public class UploadService {

    private final S3Presigner presigner;       // AWS SDK v2
    private final UploadRepository uploadRepo;

    // 허용 콘텐츠 타입 화이트리스트 (보안 ④)
    private static final Set<String> ALLOWED = Set.of("image/jpeg", "image/png", "image/webp");
    private static final long MAX_SIZE = 10 * 1024 * 1024; // 10MB

    public PresignResponse createPresignedPut(Long userId, String contentType, long size) {
        // 1) 서버에서 타입·크기를 먼저 검증 → 악성/거대 파일 차단
        if (!ALLOWED.contains(contentType)) throw new BadRequestException("허용되지 않은 타입");
        if (size > MAX_SIZE)               throw new BadRequestException("크기 초과");

        // 2) 키는 서버가 생성 (사용자가 경로를 조작하지 못하게)
        String key = "uploads/%d/%s".formatted(userId, UUID.randomUUID());

        PutObjectRequest objectRequest = PutObjectRequest.builder()
            .bucket("rehab-fashion-uploads")
            .key(key)
            .contentType(contentType)   // 서명에 포함 → 클라가 다른 타입으로 PUT하면 거부됨
            .build();

        PutObjectPresignRequest presignRequest = PutObjectPresignRequest.builder()
            .signatureDuration(Duration.ofMinutes(5))  // 3) 만료 5분 (보안 ④)
            .putObjectRequest(objectRequest)
            .build();

        String url = presigner.presignPutObject(presignRequest).url().toString();

        // 4) PENDING 상태로 메타 선저장 → 콜백/이벤트로 UPLOADED 전환
        uploadRepo.save(new UploadEntity(key, userId, UploadStatus.PENDING));

        return new PresignResponse(url, key);
    }
}

③ 업로드 후 비동기 후처리(큐 + 워커)와 CDN 서빙 — 썸네일 생성·동영상 트랜스코딩은 무겁고 느리므로 업로드 응답 경로와 분리합니다. 원본이 S3에 도착하면 메시지 큐(SQS·Kafka)에 작업을 넣고, 별도 워커가 이미지를 리사이즈(여러 해상도)하거나 영상을 HLS로 변환해 결과를 다시 S3에 저장합니다.

  • 읽기는 CDN(CloudFront)으로: 사용자는 S3 원본이 아니라 CDN 엣지에서 캐시된 파일을 받습니다. 전 세계 지연 시간 단축 + S3 트래픽 비용 절감 + 원본 버킷 비공개 유지(OAC로 CDN만 접근 허용).
  • 처리 상태 관리: DB 상태를 UPLOADED → PROCESSING → READY로 전이시키고, 완료 전에는 플레이스홀더/로딩 UI를 보여줍니다.

Q10. 알림/푸시 시스템 — 큐 + 워커 + 멱등 처리

알림 발송은 외부 채널(APNs/FCM, 이메일 게이트웨이, SMS)에 의존하기 때문에 느리고 불안정합니다. 면접에서는 "본 요청을 막지 않으면서, 어떻게 누락 없이, 그러나 중복 없이 보낼 것인가"를 큐·워커·멱등이라는 세 축으로 설명할 수 있는지를 봅니다.

💡 비유로 이해하기: 우체국 접수창구와 배달부

주문 확정 직후 손님에게 직접 알림을 들고 뛰어가면(동기 전송), 그 한 사람을 배달하는 동안 다음 손님 접수가 막힙니다.
대신 창구는 "발송 요청서"만 받아 우편함(큐)에 넣고 즉시 다음 손님을 받습니다. 뒤에서 여러 배달부(워커)가 우편함을 비우며 푸시·이메일·SMS로 나눠 보냅니다.
같은 요청서가 실수로 두 장 들어와도, 배달부는 "이 송장번호(멱등 키)는 이미 배달했음" 장부를 보고 두 번 보내지 않습니다.

1) 왜 동기 전송이 문제인가 — 비동기 큐로 분리

  • 주문 API가 푸시/이메일 발송을 직접 호출하면, 외부 API가 300ms~수 초 지연될 때 본 트랜잭션의 응답 시간이 그만큼 늘어납니다.
  • 외부 채널이 장애나면 본 요청까지 실패/타임아웃 — 부가 기능(알림)이 핵심 기능(주문)을 끌어내리는 결합이 생깁니다.
  • 해결: 본 요청은 "알림 보내달라"는 이벤트만 큐에 적재(enqueue)하고 즉시 반환. 실제 발송은 워커가 비동기로 처리해 본 응답 지연·장애 전파를 끊습니다.

2) 전체 구조: 생산자 → 큐 → 워커 → DLQ

생산자 (Producer)

도메인 이벤트 발행. 예: OrderPlaced 발생 시 "주문 완료 알림" 메시지를 큐에 넣음. DB 커밋과 발행을 함께 보장하려면 트랜잭셔널 아웃박스 패턴 사용.

메시지 큐

Kafka / RabbitMQ / SQS. 생산자와 워커를 시간적으로 분리(버퍼링). 트래픽 폭주 시 큐에 쌓아두고 워커가 자기 속도로 소비.

워커 (Consumer)

채널별로 분리: 푸시 워커, 이메일 워커, SMS 워커. 외부 API 호출·템플릿 렌더링·발송 결과 기록. 수평 확장으로 처리량 조절.

재시도 + DLQ

일시 오류(네트워크/5xx)는 지수 백오프로 재시도. N회 실패하면 DLQ(Dead Letter Queue)로 격리해 메인 큐 막힘을 방지하고 나중에 점검·재처리.

3) 팬아웃과 우선순위 · 속도 제한

  • 팬아웃(fan-out): "공지를 100만 명에게" 같은 다수 수신자 발송은 하나의 거대한 작업으로 처리하면 위험합니다. 분배 워커가 수신자 목록을 잘게 쪼개 개인별 메시지로 다시 큐에 적재하면, 일부 실패가 전체를 막지 않고 워커 추가만으로 선형 확장됩니다.
  • 우선순위: "결제 인증 코드"(즉시성 필수)와 "주간 추천 메일"(지연 허용)을 같은 큐에 두면 마케팅이 OTP를 밀어냅니다. 우선순위 큐 또는 큐 분리로 긴급 트래픽 경로를 확보합니다.
  • 속도 제한(rate limit): FCM/이메일 게이트웨이는 초당 한도가 있어, 초과 호출 시 차단되거나 스팸으로 분류됩니다. 워커 측 토큰 버킷으로 발송 속도를 채널 한도 이하로 통제합니다.

4) 중복 발송 방지 — 멱등 키 + dedup

대부분의 큐는 at-least-once(최소 한 번) 전달이라, 워커가 발송 후 ack 직전에 죽으면 같은 메시지가 재전달됩니다. 따라서 워커는 "여러 번 받아도 한 번만 발송"하도록 멱등하게 짜야 합니다. 핵심은 메시지마다 안정적인 멱등 키(예: userId + 이벤트ID + 채널)를 만들고, 발송 기록 테이블의 유니크 제약으로 중복을 막는 것입니다.

멱등 발송 워커 (의사 코드)
// 워커가 큐에서 알림 메시지 하나를 소비할 때 호출
public void handle(NotificationMessage msg) {
    // 1) 메시지 내용으로 결정적(deterministic) 멱등 키 생성
    //    같은 이벤트는 재전달돼도 항상 같은 키가 나와야 한다
    String idemKey = msg.userId() + ":" + msg.eventId() + ":" + msg.channel();

    // 2) "처리 시작"을 먼저 클레임 (claim-first)
    //    sent_notification(idem_key UNIQUE, status) 테이블에
    //    status=PENDING 으로 INSERT 시도
    ClaimResult claim = sentRepo.claim(idemKey); // NEW(신규) / SENT(이미 발송) / PENDING(클레임만 됨)

    if (claim == ClaimResult.SENT) {
        // 이미 발송 확정된 메시지 → 외부 API 재호출 없이 ack만
        log.info("dedup: 이미 발송됨 key={}", idemKey);
        return; // 멱등하게 무시
    }
    // NEW 또는 PENDING(이전 워커가 클레임 후 발송 확정 전에 죽은 경우)이면 발송을 (재)시도한다.
    // → 클레임만 되고 발송이 확인되지 않은 메시지는 유실하지 않고 다시 보낸다(누락 방지).

    try {
        // 3) 실제 외부 발송 (FCM/이메일/SMS) — DB 트랜잭션 밖의 외부 호출
        sender.send(msg);
        // 4) 발송 성공을 별도로 확정 기록 (PENDING → SENT)
        sentRepo.markSent(idemKey);
    } catch (TransientException e) {
        // 5) 일시 오류: 레코드는 PENDING 그대로 두고 재시도에 맡긴다
        //    (백오프 후 재전달 → 위 2)에서 PENDING으로 재진입해 재발송, 영구 실패 시 DLQ)
        throw e; // ack 하지 않음 → 큐가 다시 전달
    }
    // 6) status=SENT 커밋 후 메시지 ack (외부 발송은 트랜잭션에 묶이지 않음)
}

※ claim-first는 "클레임(PENDING)"과 "발송 확정(SENT)"을 분리해, 발송 확정 전에 워커가 하드 크래시해도 재전달 시 다시 보내 누락을 막습니다. 대신 외부 발송 직후 markSent 직전 크래시 시 재발송으로 중복이 날 수 있는데(at-least-once의 본질), 수신 측 멱등/dedup이 이를 흡수합니다. 또한 여러 워커가 같은 PENDING 메시지를 동시에 집어 중복 발송하지 않도록, 큐의 가시성 타임아웃(visibility timeout)·메시지 잠금이나 dedup 레코드의 소유권(lease) 처리로 동시 처리를 직렬화합니다. Rehab Fashion에서 "배송 출발" 알림을 푸시+이메일로 보낼 때도, 채널을 멱등 키에 포함해 푸시는 푸시대로 한 번, 이메일은 이메일대로 한 번만 가도록 분리해 dedup합니다. Redis SET NX(+TTL)로 빠르게 1차 거르고, DB 유니크 제약을 최종 방어선으로 두는 2단 구성도 흔합니다.

꼬리질문 핵심 — 전달 보장 등급 비교

보장 등급의미위험실무 선택
at-most-once최대 한 번 (보내고 잊음)알림 누락 가능중요 알림엔 부적합

💡 면접 꼬리 질문: "정확히 한 번(exactly-once) 전송은 왜 어렵고, 현업에서는 어떻게 절충하나요?" → 발송과 "발송 기록 저장"이 서로 다른 시스템(외부 API + 우리 DB)이라 둘을 하나의 원자적 트랜잭션으로 묶을 수 없기 때문입니다. 외부 API에 호출한 뒤 ack/기록 직전에 워커가 죽으면, "보냈는데 안 보낸 줄 알고" 재전달되어 중복이 생깁니다. 분산 환경에서 이 경계를 완벽히 없애는 진짜 exactly-once는 비현실적으로 비쌉니다. 그래서 현업은 at-least-once(누락은 절대 안 됨)로 메시지를 보장하고, 소비 측을 멱등하게 만들어 "결과적으로 한 번"(effectively-once)을 달성합니다. 멱등 키 + 유니크 제약/dedup 저장소가 중복을 흡수하고, 재시도와 DLQ가 누락을 막는 조합이 표준 해법입니다.

Q11. 실시간 랭킹 보드 — Redis Sorted Set(ZSET)

"실시간 인기 상품 TOP 100", "주간 베스트 리뷰어"처럼 점수가 계속 바뀌는 순위판을 만들 때 RDB로 매번 정렬하면 트래픽이 몰리는 순간 DB가 무너집니다. Redis의 Sorted Set(ZSET)을 왜 쓰는지, 어떤 명령이 어떤 시간복잡도로 동작하는지를 묻는 것이 면접의 핵심입니다.

💡 비유로 이해하기: 매번 다시 줄 세우기 vs 항상 정렬된 리더보드

점수표를 종이 한 장(RDB 테이블)에 적어두고 누가 1등인지 물어볼 때마다 전체를 처음부터 정렬한다면, 사람이 많아질수록 매번 줄 세우는 시간이 길어집니다.
ZSET은 점수가 바뀔 때마다 그 사람만 제자리에 끼워 넣는 항상 정렬된 게시판입니다. 1등이 누구냐, 내가 몇 등이냐를 물으면 이미 정렬돼 있으니 즉시 답이 나옵니다.

① 왜 RDB ORDER BY ... LIMIT로는 부족한가

  • SELECT user_id FROM scores ORDER BY point DESC LIMIT 100 — 점수 컬럼에 인덱스가 있어도, 점수가 초당 수천 번 갱신되면 인덱스 갱신 비용과 정렬·디스크 I/O가 누적됩니다.
  • "내 순위"를 구하려면 COUNT(*) WHERE point > ? 형태의 풀스캔성 집계가 필요해 유저가 많아질수록 O(N)으로 느려집니다.
  • 랭킹은 읽기·쓰기 모두 빈번한 데이터라 캐시 한 장으로 덮기도 어렵습니다. → 정렬 상태를 메모리에서 상시 유지하는 Redis ZSET이 정답.

② ZSET 핵심 명령과 복잡도 (조회 종류에 따라 O(1)~O(log N))

ZADD / ZINCRBY

점수 설정·증가. ZADD key 점수 member로 덮어쓰고, ZINCRBY key 1 member로 누적 증가. 삽입 위치를 스킵리스트로 찾아 O(log N).

ZREVRANGE

상위 N명 조회. ZREVRANGE key 0 99 WITHSCORES → 점수 내림차순 TOP 100. O(log N + M) (M = 가져올 개수).

ZREVRANK

내 순위 조회. ZREVRANK key member → 0부터 시작하는 등수. +1 해서 표시. O(log N). RDB의 COUNT(*) 집계를 대체.

ZSCORE / ZCARD

ZSCORE로 내 점수(O(1)), ZCARD로 전체 참가자 수(O(1)) 조회. "상위 몇 %" 계산에 활용.

※ ZSET 내부는 스킵리스트(정렬)와 해시테이블(member→score)을 함께 유지합니다. 그래서 점수로 정렬 조회도, member로 직접 조회도 빠릅니다. (요소 수가 적고 값이 짧을 땐 listpack으로 압축 저장되지만, 커지면 스킵리스트로 전환됩니다.)

③ 기간별 랭킹 키 분리 · TTL · 동점 처리

  • 키 분리: 날짜를 키에 넣어 rank:daily:20260608, rank:weekly:2026W23처럼 기간별로 별도 ZSET을 둡니다. 일간 키는 EXPIRE로 며칠 뒤 자동 삭제(TTL)해 메모리를 회수합니다.
  • 주간 = 일간 합산: ZUNIONSTORE로 그 주(월~일)의 일간 ZSET 7개를 합쳐 주간 랭킹을 만들 수 있습니다(WEIGHTS로 가중치, AGGREGATE로 합/최댓값 선택도 가능).
  • 동점 처리: ZSET은 점수가 같으면 member의 사전순(lexicographical, 바이트 단위)으로 정렬합니다. 이러면 "먼저 그 점수에 도달한 사람"이 표현되지 않으므로, 보통 점수 + (역타임스탬프를 소수부에 인코딩) 같은 복합 점수를 써서 "동점이면 먼저 달성한 사람이 위"가 되게 합니다. 단 ZSET 점수는 IEEE 754 double(유효자릿수 약 15~17자리)이라, 큰 정수 점수와 타임스탬프를 한 double에 욱여넣으면 정밀도가 깨질 수 있으니 자릿수를 신중히 설계해야 합니다.

@Service
@RequiredArgsConstructor
public class RankingService {

    private final StringRedisTemplate redis;

    private String dailyKey() {                       // 오늘 날짜로 키 생성
        String day = LocalDate.now().format(DateTimeFormatter.BASIC_ISO_DATE);
        return "rank:item:daily:" + day;              // 예: rank:item:daily:20260608
    }

    /** 상품 점수 +1 (조회/구매 이벤트). 키가 처음 만들어졌을 때만 TTL 부여 */
    public void increase(String itemId) {
        String key = dailyKey();
        ZSetOperations<String, String> zset = redis.opsForZSet();
        Double updated = zset.incrementScore(key, itemId, 1); // ZINCRBY — O(log N)

        // 키가 이번 호출로 새로 생성된 경우에만 TTL 설정.
        // expireAt을 무조건 호출하면 이벤트가 들어올 때마다 만료가 뒤로 밀려(슬라이딩 TTL)
        // 그날 키가 영원히 안 죽을 수 있으므로, '내일 자정 + 여유 1일'의 절대 시각으로 한 번만 고정한다.
        Boolean hasTtl = redis.getExpire(key, TimeUnit.SECONDS) > 0;
        if (Boolean.FALSE.equals(hasTtl)) {
            Instant expireAt = LocalDate.now().plusDays(2)
                .atStartOfDay(ZoneId.systemDefault()).toInstant(); // 모레 00:00
            redis.expireAt(key, expireAt);
        }
    }

    /** 상위 N개 — ZREVRANGE (점수 내림차순). 반환 Set은 순서를 보존하는 LinkedHashSet */
    public Set<ZSetOperations.TypedTuple<String>> topN(int n) {
        return redis.opsForZSet()
            .reverseRangeWithScores(dailyKey(), 0, n - 1);   // 0~n-1
    }

    /** 내 순위 — ZREVRANK. null이면 랭킹에 없음(미집계) */
    public Long myRank(String itemId) {
        Long rank = redis.opsForZSet().reverseRank(dailyKey(), itemId);
        return (rank == null) ? null : rank + 1;      // 0-based → 1-based
    }
}

💡 면접 꼬리 질문: "수백만 유저의 전체 순위를 다 보여줘야 한다면 ZSET만으로 충분한가요?" → 충분하지 않습니다. ZSET 자체는 빠르지만 전체를 한 번에 클라이언트로 내려보내는 것이 병목입니다. 세 가지로 대응합니다. ① 페이지네이션: ZREVRANGE key (page*size) ((page+1)*size-1)로 화면에 보이는 구간만 잘라 조회 — 각 페이지는 O(log N + M). ② 근사 순위: ZREVRANK는 O(log N)으로 정확한 등수를 주지만, 하위권 유저에게는 그 값을 "상위 약 7%", "12,300위권"처럼 ZREVRANK / ZCARD 비율로 뭉뚱그려 보여 주면 등수가 1칸 바뀔 때마다 정밀하게 갱신·표시할 필요가 줄어 UI·전송 비용이 내려갑니다. 조회 연산량까지 줄이려면 점수 구간을 버킷으로 미리 집계하거나(분포), 전체 인원 추정엔 HyperLogLog처럼 rank 조회 자체를 대체하는 근사 자료구조를 씁니다. ③ 상위권만 실시간, 나머지는 비실시간: TOP 100~1000만 ZSET으로 실시간 노출하고, 그 아래는 배치로 주기 스냅샷을 떠 캐시로 제공합니다. 핵심은 "전부 정확·실시간"을 포기하고, 사용자가 실제로 보는 구간에만 비용을 집중하는 것입니다.

Q12. 분산 고유 ID 생성 — UUID vs DB Sequence vs Snowflake

서비스가 단일 DB를 넘어 샤딩·다중 인스턴스로 확장되는 순간, "PK는 그냥 auto-increment 쓰면 되지" 라는 전제가 무너집니다. 어떤 ID 생성 전략을 왜 선택했는가는 시니어 백엔드 면접에서 시스템 설계 감각을 보는 단골 질문입니다.

💡 비유로 이해하기: 여러 창구에서 번호표를 뽑을 때

은행 한 곳이면 번호표 기계 한 대(auto-increment)로 1, 2, 3… 순서대로 발급해도 문제없습니다.
그런데 지점이 10개로 늘면, 모든 지점이 똑같이 "1번"을 발급해 버려 번호가 충돌합니다.
해결책은 세 가지입니다 — ① 아무도 안 겹치는 긴 난수를 찍기(UUID), ② 본사에 전화해 다음 번호를 받아오기(중앙 시퀀스/티켓서버), ③ 번호표에 지점코드 + 시각 + 그 지점 내 순번을 조합해 스스로 겹치지 않게 만들기(Snowflake).

왜 auto-increment는 분산/샤딩에서 깨지는가:

  • 충돌: 샤드 A와 샤드 B가 각자 1부터 증가시키면 동일 ID가 양쪽에서 생성됩니다. PK 유일성이 전역에서 보장되지 않습니다.
  • 중앙 조율 비용: 충돌을 피하려고 모든 INSERT를 한 DB로 모으면, 그 DB가 쓰기 병목(SPOF)이 됩니다 — 수평 확장의 의미가 사라집니다.
  • 운영 난점: 샤드별 step/offset(예: 1·11·21…, 2·12·22…)으로 우회할 수 있지만, 샤드 추가 시 재배치가 어렵고 이미 발급된 ID와의 정합성 관리가 까다롭습니다.
  • 채번 노출: 1씩 증가하는 ID는 외부에 노출되면 총 주문 수·증가 속도가 추측됩니다(enumeration 공격면).

세 가지 대표 전략:

UUIDv4 (랜덤)

122비트 난수. 조율 없이 어디서든 생성, 사실상 충돌無. 그러나 완전 랜덤이라 시간 정렬 불가하고, 인덱스에 무작위로 흩뿌려져 B-Tree 페이지 분할·단편화를 유발.

UUIDv7 (시간순)

앞부분에 Unix 밀리초 타임스탬프를 담아 생성 순서 ≈ 정렬 순서. UUID 호환(128bit)이면서 인덱스 친화적. 충돌無의 장점은 유지하되 v4의 단편화 문제를 해소(RFC 9562).

DB Sequence / 티켓서버

중앙에서 단조 증가 번호를 발급(예: MySQL auto_increment 전용 테이블, Flickr 티켓서버). 짧고 정렬되지만 단일 병목·SPOF. batch로 구간을 미리 떼와(예: 1000개씩) 완화.

Snowflake (분산 생성)

타임스탬프+머신ID+시퀀스를 조합한 64bit 정수. 중앙 조율 없이 각 노드가 직접 생성하면서도 거의 시간순으로 정렬. Twitter가 공개, 카카오·라인 등 국내 대규모 서비스도 변형 사용.

Snowflake 64bit 비트 구성 (Twitter 원본 기준):

  • 1 bit — 부호: 항상 0. 양수 BIGINT를 보장(음수 정렬·호환 문제 회피).
  • 41 bit — 타임스탬프: 기준 시각(epoch)으로부터의 밀리초. 약 2^41ms ≈ 69년치를 표현. 상위 비트라서 시간순 정렬의 핵심.
  • 10 bit — 머신 ID: 데이터센터 + 워커 노드 식별(2^10 = 1024개 노드). 노드끼리 안 겹치게 해 분산 생성 시 충돌 방지.
  • 12 bit — 시퀀스: 같은 노드·같은 ms 안에서 0~4095까지. 즉 한 노드가 1ms에 최대 4096개 ID 생성. 다 쓰면 다음 ms까지 대기.
Snowflake ID 생성 핵심 로직 (단순화 예시)
public class SnowflakeIdGenerator {
    // 비트 폭 정의: 41(시간) + 10(머신) + 12(시퀀스) = 63 + 부호 1 = 64bit
    private static final long EPOCH       = 1704067200000L; // 2024-01-01 기준 (밀리초)
    private static final long MACHINE_BITS  = 10L;
    private static final long SEQUENCE_BITS = 12L;

    // 자리수만큼 왼쪽으로 밀어 넣기 위한 시프트 값
    private static final long MACHINE_SHIFT   = SEQUENCE_BITS;                 // 12
    private static final long TIMESTAMP_SHIFT = SEQUENCE_BITS + MACHINE_BITS;  // 22

    // 시퀀스 최댓값 마스크: 12bit 전부 1 → 4095 (0b1111_1111_1111)
    private static final long SEQUENCE_MASK = (1L << SEQUENCE_BITS) - 1;

    private final long machineId;     // 0 ~ 1023, 노드마다 유일하게 주입
    private long lastTimestamp = -1L; // 마지막으로 ID를 만든 시각
    private long sequence = 0L;       // 같은 ms 안의 순번

    public SnowflakeIdGenerator(long machineId) {
        if (machineId < 0 || machineId > 1023)            // 10bit 범위 검증
            throw new IllegalArgumentException("machineId out of range");
        this.machineId = machineId;
    }

    // synchronized: 한 노드 안에서 멀티스레드가 동시에 들어와도 순번이 꼬이지 않게
    public synchronized long nextId() {
        long now = System.currentTimeMillis();

        // 시계 역행 감지: NTP 보정 등으로 시간이 과거로 가면 단조성이 깨지므로 거부
        if (now < lastTimestamp)
            throw new IllegalStateException("clock moved backwards");

        if (now == lastTimestamp) {
            // 같은 ms → 시퀀스 +1. 마스크로 4095를 넘으면 0이 되어 overflow 감지
            sequence = (sequence + 1) & SEQUENCE_MASK;
            if (sequence == 0) {
                // 이번 ms의 4096개를 다 썼다 → 다음 ms가 올 때까지 바쁜 대기
                while ((now = System.currentTimeMillis()) <= lastTimestamp) { /* spin */ }
            }
        } else {
            sequence = 0L; // 새로운 ms로 넘어오면 순번 리셋
        }
        lastTimestamp = now;

        // 세 구간을 비트로 합쳐 64bit 정수 하나로 조립
        return ((now - EPOCH) << TIMESTAMP_SHIFT)  // 41bit: 상위 → 시간순 정렬 보장
             | (machineId       << MACHINE_SHIFT)  // 10bit: 노드 식별
             |  sequence;                          // 12bit: ms 내 순번
    }
}

실무 선택 기준 (Rehab Fashion 같은 쇼핑몰 관점):

  • 단일 DB·중소 규모면 auto-increment/시퀀스로 충분 — 굳이 분산 ID로 복잡도를 올릴 이유가 없습니다.
  • 마이크로서비스·다중 인스턴스에서 충돌 없는 전역 PK가 필요하면 Snowflake(또는 UUIDv7)가 1순위. 둘 다 시간순이라 인덱스 친화적입니다.
  • 외부에 노출되는 ID(주문번호·결제키)는 정렬성보다 추측 불가능성이 중요 → 랜덤 UUID나 별도 공개용 식별자를 PK와 분리.

💡 면접 꼬리 질문: "정렬 가능한 ID가 왜 인덱스와 페이지네이션에 유리한가요?" → 첫째, 인덱스 측면: PK가 시간순으로 증가하면 B-Tree에 항상 오른쪽 끝(가장 큰 값)으로 순차 삽입되어 페이지 분할과 단편화가 거의 없고, 최근에 쓴 리프 페이지가 버퍼풀에 캐시돼 디스크 랜덤 I/O가 줄어듭니다. 반면 UUIDv4 같은 랜덤 PK는 매 INSERT마다 트리 중간에 끼어들어 페이지 분할·캐시 미스를 유발합니다(MySQL InnoDB는 PK가 클러스터드 인덱스라 영향이 특히 큼). 둘째, 페이지네이션 측면: ID가 시간순이면 WHERE id > :lastId ORDER BY id LIMIT 20 형태의 커서(키셋) 페이지네이션이 가능합니다. OFFSET 방식은 깊은 페이지에서 앞 N건을 모두 스캔해 버려야 해 느려지지만, 커서 방식은 인덱스를 타고 마지막 본 ID 다음부터 바로 읽어 일정한 성능을 냅니다. 게다가 ID 자체가 대략적인 생성 시각순이므로 별도 created_at 정렬 컬럼 없이도 "최신순" 정렬이 자연스럽게 됩니다.
