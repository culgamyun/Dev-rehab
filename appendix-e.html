부록 E. 시스템 설계 면접 — 확장·캐시·신뢰성·단골 문제

경력·복귀 면접의 합격을 가르는 관문은 "정의 암기"가 아니라 "이 상황에서 무엇을, 왜, 어떤 순서로"를 설명하는 설계 감각입니다. 부록 B(CS 단골)의 설계 "개요"를 실제 면접에서 끝까지 밀어붙일 수 있는 깊이로 끌어올립니다. 모든 예시는 가상 의류 쇼핑몰 Rehab Fashion 도메인으로 이어집니다.

🧭 이 부록 사용법

각 질문은 면접 답변 스크립트처럼 읽으세요. 비유로 큰 그림을 잡고 → 표/코드로 근거를 채우고 → 면접 꼬리 질문으로 한 단계 더 들어갑니다. 마지막 자가 진단 퀴즈는 풀면 대시보드 "오늘의 복습"에 자동 편입되어 간격 반복으로 굳습니다.

🪜 A. 확장의 사다리 (Scalability)

Q1. 사용자가 100배 늘면 무엇부터 터지고, 어떤 순서로 막나요?

설계 면접의 1번 타자입니다. 핵심은 "가장 싸고 효과 큰 것부터, 병목을 따라" 확장한다는 순서 감각입니다. 무작정 "샤딩하겠습니다"는 감점, "먼저 측정해 병목을 찾고 캐시→복제→비동기 순으로 가겠다"가 가점입니다.

💡 비유로 이해하기: Antigravity 오픈런 세일

한정판 후드 세일에 손님이 몰립니다. 먼저 계산대(앱 서버)를 늘립니다(수평 확장). 그런데 계산대를 아무리 늘려도 창고 직원(DB) 한 명이 모든 재고 조회를 처리하면 거기서 줄이 막힙니다. 그래서 인기 상품을 매대 앞(캐시)에 미리 깔고, 재고 조회 사본(읽기 복제본)을 여러 개 두며, 영수증 발송 같은 일은 나중에 처리(비동기 큐)로 미룹니다.

확장 순서 — 비용 대비 효과 순:

단계 수단 막는 병목
1. 수직 확장 서버 스펙 업(CPU/RAM) 초기 단순 부하 (한계·비용 급증)
2. 무상태 + 수평 확장 + LB 서버 여러 대 + 로드밸런서(L4/L7) 앱 서버 CPU 병목
3. 캐시 Redis (Look-aside) 반복 읽기 DB 부하
4. 읽기 복제본 Replica + 읽기/쓰기 분리 읽기 트래픽 (읽기 99% 서비스)
5. 비동기 / 메시지 큐 Kafka로 무거운 작업 분리 느린 후처리(메일·집계)가 응답 지연
6. 샤딩 데이터 자체를 분할 단일 DB 쓰기/용량 한계 (최후의 수단)

💡 면접 꼬리 질문: "세션을 서버 메모리에 두면 왜 수평 확장이 깨지나요?" → 로드밸런서가 다음 요청을 다른 서버로 보내면 그 서버엔 세션이 없어 로그인이 풀립니다. 그래서 서버를 무상태(stateless)로 만들고 세션/토큰을 외부 저장소(Redis)에 둡니다 — 부록 Antigravity의 Redis JWT(Ch4)가 바로 이 이유입니다.

⚡ B. 캐시 계층 (Caching)

Q2. 캐시 전략 3종과 '캐시 스탬피드'를 설명하세요

캐시는 "한 번 비싸게 구한 답을 잠깐 보관해 재사용"하는 계층입니다. 면접에선 쓰기 시 정합성과 대량 만료 시 폭주를 어떻게 다루는지를 봅니다.

💡 비유로 이해하기: 인기 매대와 '우르르 창고 돌진'

잘 나가는 후드를 매장 앞 매대(캐시)에 미리 깔면 손님이 창고(DB)까지 안 갑니다. 그런데 그 매대가 동시에 텅 비는 순간(TTL 만료), 수천 명이 한꺼번에 창고로 돌진해 창고 직원이 깔립니다 — 이것이 캐시 스탬피드(thundering herd)입니다.

3대 전략:

① Look-aside (Cache-Aside)

앱이 캐시를 먼저 보고, 없으면(miss) DB에서 읽어 캐시에 채움. 가장 흔함. 쓰기 시 DB 먼저 → 캐시 삭제가 정석.

② Write-through

쓰기를 캐시와 DB에 동시에. 캐시가 항상 최신이지만 쓰기 지연 증가.

③ Write-back

캐시에 먼저 쓰고 DB는 나중에 일괄. 가장 빠르지만 캐시 장애 시 데이터 유실 위험.

Look-aside 캐시 의사코드 (Spring @Cacheable과 동일한 흐름) 
// 상품 상세 조회 — 캐시 우선, 미스 시 DB 적재
public Product getProduct(Long id) {
    String key = "product:" + id;
    Product cached = redis.get(key);          // 1. 캐시 확인
    if (cached != null) return cached;         //    HIT → 즉시 반환

    Product p = productRepository.findById(id) // 2. MISS → DB 조회
                    .orElseThrow();
    redis.set(key, p, Duration.ofMinutes(10)); // 3. 캐시에 적재 (TTL)
    return p;
}

// 상품 수정 시 — DB 먼저 쓰고 캐시는 '삭제'(갱신 X) 가 안전
public void updateProduct(Product p) {
    productRepository.save(p);                  // DB 진실의 원천 갱신
    redis.delete("product:" + p.getId());       // 다음 읽기 때 자연히 재적재
}

캐시 스탬피드 방어 4종:

기법 핵심
분산 락 / Mutex만료 시 한 요청만 DB 재조회·재적재, 나머지는 대기 후 캐시 사용
TTL Jitter만료 시각에 랜덤 ±를 더해 동시 만료를 분산
Refresh-ahead만료 전 미리 백그라운드 갱신
논리적 만료물리 TTL은 길게, 값 안에 만료 플래그를 두고 비동기 갱신

캐시 교체(eviction) 알고리즘: LRU(가장 오래 안 쓴 것 제거 — 가장 흔함) · LFU(가장 적게 쓴 것) · FIFO(먼저 들어온 것). Redis maxmemory-policy로 설정합니다.

💡 면접 꼬리 질문: "캐시와 DB 정합성 — 수정 시 캐시를 먼저 지우나, DB를 먼저 쓰나요?" → Cache-Aside에서는 DB를 먼저 쓰고 캐시를 삭제합니다. 캐시를 먼저 지우면 그 찰나에 다른 요청이 옛 DB값을 다시 캐싱해 stale이 남을 수 있습니다(완벽하진 않아 짧은 TTL을 병행).

🗄️ C. 데이터 계층 확장 (Replication · Sharding)

Q3. DB가 한계입니다 — 복제 / 파티셔닝 / 샤딩의 차이는?

"인덱스(Ch3)와 캐시로도 안 될 때" 비로소 데이터 계층을 쪼갭니다. 셋을 혼동하면 감점이니 목적으로 구분하세요.

기법 무엇을 주로 해결 대표 함정
복제 (Replication) 같은 데이터를 사본으로 읽기 부하·가용성 복제 지연(쓰고 바로 읽으면 옛값)
파티셔닝 (Partitioning) 한 DB 안에서 테이블 분할 큰 테이블 스캔·관리 파티션 키 안 타면 전체 스캔
샤딩 (Sharding) 데이터를 여러 DB로 수평 분할 쓰기·용량 한계 핫스팟·교차 샤드 조인/트랜잭션

💡 비유로 이해하기: 창고 전략

복제 = 같은 재고 목록을 여러 창고에 복사해 조회를 분산(단, 본점이 막 입고한 건 지점에 늦게 반영 = 복제 지연). 샤딩 = 아예 지역별 창고로 나눠 서울 고객은 서울 창고만 — 쓰기까지 분산되지만, "전국 통합 매출 정렬"은 모든 창고를 뒤져 합쳐야 해 어려워집니다.

샤드 키 선택이 전부입니다. user_id 해시로 잡으면 특정 유저 데이터가 한 샤드에 모여 골고루 분산되지만(핫스팟 완화), 여러 유저에 걸친 집계·조인이 어려워집니다. 노드 증감 시 재분배를 줄이려 Consistent Hashing을 씁니다.

💡 면접 꼬리 질문: "방금 주문을 넣고 바로 '내 주문 목록'을 조회했는데 안 보입니다. 왜죠?" → 쓰기는 마스터, 읽기는 복제본으로 갔는데 복제 지연으로 아직 반영 전입니다. 해결: 쓰기 직후 일정 시간은 마스터에서 읽기(read-your-writes), 또는 캐시에 방금 쓴 값을 함께 반영.

🛡️ D. 신뢰성 패턴 (면접 빈출)

Q4. 멱등성(Idempotency) — 중복 결제/주문을 어떻게 막나요?

네트워크는 언제든 끊기고, 클라이언트는 재시도합니다. "같은 요청을 여러 번 보내도 결과가 한 번과 같다"는 성질이 멱등성입니다. GET/PUT/DELETE는 본래 멱등, POST(주문 생성)는 비멱등이라 별도 장치가 필요합니다.

💡 비유로 이해하기: 엘리베이터 버튼

엘리베이터 버튼을 열 번 눌러도 한 번 부른 것과 같습니다. 주문도 "결제하기"를 따닥 두 번 눌러도 한 건만 생성되어야 합니다.

Idempotency-Key 헤더로 중복 주문 1회 보장 (Redis SETNX) 
// 클라이언트가 요청마다 고유 키를 헤더에 동봉: Idempotency-Key: 5f3a-...
@PostMapping("/api/orders")
public ResponseEntity<OrderRes> create(
        @RequestHeader("Idempotency-Key") String key,
        @RequestBody OrderReq req) {

    // SETNX: 키가 없을 때만 저장 → '첫 요청'만 true
    boolean first = redis.setIfAbsent("idem:" + key, "1", Duration.ofHours(24));
    if (!first) {
        // 이미 처리된 요청 → 저장해 둔 결과를 그대로 반환 (중복 생성 X)
        return ResponseEntity.ok(orderService.findByIdemKey(key));
    }
    OrderRes res = orderService.place(req, key);
    return ResponseEntity.ok(res);
}

💡 면접 꼬리 질문: "재시도는 어떻게 안전하게 하나요?" → 지수 백오프(exponential backoff) + 지터로 간격을 늘려 재시도하되, 서버는 멱등성 키로 중복을 흡수합니다. 둘은 짝꿍입니다 — 재시도만 있고 멱등성이 없으면 중복, 멱등성만 있고 재시도가 없으면 유실.

Q5. Rate Limiting — 폭주·어뷰징으로부터 서버를 어떻게 보호하나요?

"초당 N회"를 넘는 요청을 거절(429 Too Many Requests)해 서버와 비용을 지킵니다. 알고리즘 선택이 단골 질문입니다.

💡 비유로 이해하기: 놀이공원 시간당 입장 제한

인기 어트랙션은 시간당 정원이 있습니다. 토큰(입장권)이 일정 속도로 보충되고, 토큰이 있으면 입장, 없으면 다음 보충까지 대기 — 이것이 Token Bucket입니다.

알고리즘 특징
Token Bucket토큰을 일정 속도 보충, 순간 버스트 허용. 가장 널리 쓰임
Leaky Bucket고정 속도로 처리(누수). 출력이 매끄럽지만 버스트 흡수 약함
Fixed Window1분 단위 카운트. 단순하나 경계(59초/0초)에서 2배 폭주
Sliding Window이동 구간으로 경계 문제 완화. 정확하지만 비용↑

분산 환경에선 카운터를 Redis에 두어 모든 서버가 같은 한도를 공유합니다. INCR 자체는 원자적이지만, 첫 키 생성 시 INCR과 EXPIRE 사이 틈에 TTL이 안 붙을 수 있어 실무에선 Lua 스크립트나 SET ... EX NX로 원자화합니다.

💡 면접 꼬리 질문: "한도를 IP 기준으로 잡을지, 사용자 기준으로 잡을지?" → 로그인 전 API는 IP, 로그인 후는 사용자(또는 API 키) 기준이 일반적이며, 공용 NAT/회사망의 다수 사용자가 한 IP를 공유하는 경우를 고려해야 합니다.

🧩 E. 설계 면접 워크북 (단골 문제)

설계 면접을 푸는 7단계 프레임

백지 앞에서 얼지 않으려면 틀을 외워두세요. 면접관은 답이 아니라 접근 과정을 봅니다.

1. 요구사항 명확화

기능/비기능 구분. "읽기 많나 쓰기 많나? 일관성 vs 가용성 어디 무게?"를 먼저 질문.

2. 용량 추정

DAU → QPS, 저장 용량, 대역폭을 어림. 읽기:쓰기 비율 산출.

3. API 설계

핵심 엔드포인트 몇 개를 시그니처로(Ch4 REST).

4. 데이터 모델

엔티티·관계·인덱스(Ch3). SQL vs NoSQL 선택 근거.

5. 하이레벨 구조

클라 → LB → 앱 → 캐시/DB/큐 큰 그림.

6. 병목 & 심화

Q1~Q5(확장·캐시·샤딩·멱등·rate limit)를 여기서 투입.

7. 트레이드오프

"이래서 이걸 택했고, 대신 이걸 포기"를 말로. CAP·정합성 vs 지연.

단골 설계 문제 4종 — 압축 풀이

① URL 단축기

긴 URL → 짧은 키. 카운터+Base62 또는 해시(충돌 처리). 읽기가 압도적이라 리다이렉트 캐시(Redis)가 핵심. 301 vs 302(통계 원하면 302).

② 뉴스피드

Push(fan-out on write) vs Pull(on read). 팔로워 많은 셀럽은 push가 폭발 → 하이브리드. 타임라인 캐시.

③ 실시간 채팅

WebSocket 상시 연결(Ch7). 메시지 영속·순서(시퀀스), 미수신 보관, 다중 서버는 pub/sub으로 팬아웃.

④ 이커머스 주문/재고

동시 차감 정합성 — DB 비관/낙관 락 vs Redis 분산락 vs 큐 직렬화. 결제·배송 분산 트랜잭션은 Saga(Ch8) + 멱등성(Q4).

🔗 각 문제는 본 부록의 패턴으로 풀립니다: 읽기 폭주→캐시(Q2), 쓰기 한계→샤딩(Q3), 중복→멱등성(Q4), 폭주→rate limit(Q5).

🎤 모의 면접 — 시스템 설계

실제 면접처럼 꼬리에 꼬리를 무는 흐름입니다. 면접관 질문 → 답변 뼈대 → 이어지는 꼬리 질문 순으로, 소리 내어 답해 보세요.

🗣️ "초당 1만 건 주문이 들어오는 이커머스, 어디서 먼저 터지고 어떤 순서로 막을지 설계해 보세요."

답변 뼈대: "먼저 측정으로 병목을 찾겠다"를 전제로 → 앱을 무상태로 만들어 수평 확장 + 로드밸런서 → 읽기는 Redis 캐시 · 읽기 복제본 → 재고 차감은 동시성 제어(분산락 또는 큐 직렬화) → 결제·알림 등 후처리는 비동기 큐로 분리. 무작정 샤딩은 최후의 수단.

↪️ 꼬리: "재고 차감을 동시성 안전하게 하려면?" → 비관/낙관 락 vs Redis 분산락 vs 큐 직렬화의 트레이드오프(정합성↔처리량)로 답합니다.

🗣️ "캐시를 도입했는데 특정 시점에 DB가 폭주합니다. 원인과 대책은?"

답변 뼈대: 대량 키가 동시에 만료되어 한꺼번에 DB로 몰리는 캐시 스탬피드가 의심됩니다. 대책은 TTL 지터(만료 분산) · 분산 락/뮤텍스(한 요청만 재적재) · refresh-ahead · 논리적 만료.

↪️ 꼬리: "캐시와 DB 정합성은 어떻게?" → Cache-Aside에서는 DB 먼저 쓰고 캐시 삭제, 짧은 TTL을 병행해 stale을 줄입니다.

🗣️ "결제 중복이 보고됐습니다. 어떻게 진단하고 막겠어요?"

답변 뼈대: 네트워크 타임아웃 재시도로 인한 중복이 흔합니다. Idempotency-Key를 받아(Redis SETNX) 첫 요청만 처리하고 재시도는 저장된 결과를 반환합니다. 지수 백오프 재시도 + 멱등성은 짝꿍.

↪️ 꼬리: "결제·재고·배송에 걸친 분산 트랜잭션은?" → 2PC 대신 Saga + 보상 트랜잭션, 각 단계는 멱등하게(Ch8).
