SQL은 손이 기억해야
시험장에서 나옵니다

눈으로 읽으면 60%, 손으로 쓰면 100%. 실기 SQL은 매회 출제되는 확정 득점원입니다. 개념을 빠르게 훑고, 카드로 키워드를 굳히고, 빈칸·작성형 문제로 손에 새기세요.

매회 출제 ★★★ 개념 11 암기카드 32 문제 20 예상 소요 3~4h
01

SELECT — 조회의 뼈대

모든 SQL 문제의 출발점. 절(clause)이 쓰이는 순서와 역할을 정확히 외우면 절반은 끝납니다.

SYNTAX

SELECT 절 작성 순서

★★★

작성 순서는 고정입니다. 이 순서가 곧 채점 기준이에요.

●●●query.sql
SELECT   [DISTINCT] 속성명, 집계함수
FROM     테이블명
WHERE    조건
GROUP BY 그룹기준 속성
HAVING   그룹조건
ORDER BY 정렬기준 [ASC|DESC];
💡 실행 순서는 다릅니다: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY. "어디서 거르느냐" 문제(WHERE vs HAVING)가 단골입니다.
CLAUSE

WHERE 조건 연산자

★★★
  • BETWEEN a AND b — a 이상 b 이하 (양끝 포함)
  • IN (값1, 값2) — 목록 중 하나와 일치
  • LIKE '김%' — % 는 0글자 이상, _ 는 1글자
  • IS NULL / IS NOT NULL — NULL은 =로 비교 불가, 반드시 IS
⚠ NULL 함정: WHERE 점수 = NULL 은 절대 동작 안 함. IS NULL 로 써야 0점을 면합니다.
TRACE

LIKE · BETWEEN · IN — 결과 행 추적

★★★

연산자 뜻은 앞에서 봤으니, 여기선 같은 데이터에 조건을 걸면 정확히 몇 행·누가 나오는지를 손으로 셉니다. 실기는 "결과 행 수"와 "출력되는 값"을 직접 적게 시킵니다.

●●●사원 (샘플)
이름      급여
김철수    3200
김영희    2800
박민수    4500
이수민    3500
최민아    5000
  • LIKE '김%' → 이름이 '김'으로 시작 → 김철수 · 김영희 (2행)
  • LIKE '%수' → 이름이 '수'로 끝 → 김철수 · 박민수 (2행) (영희→희, 수민→민, 민아→아 라 제외)
  • LIKE '_민%' → 2번째 글자가 '민' → 박민수 · 최민아 (2행)
  • 급여 BETWEEN 3000 AND 4500 → 양끝 포함 → 김철수(3200) · 이수민(3500) · 박민수(4500) (3행)
  • 급여 IN (2800, 5000) → 목록 값과 정확히 일치(= 급여=2800 OR 급여=5000) → 김영희 · 최민아 (2행)
⚠ 함정 ① _ 위치: '_민%'는 "민이 2번째 글자"라는 뜻이라 이수민(수-민, 민이 3번째)은 빠지고 박민수·최민아만 나옵니다. _=정확히 1글자, %=0글자 이상. 함정 ② 경계값: BETWEEN은 양끝값을 포함하므로 4500(박민수)도 결과에 들어갑니다("초과/미만"이면 제외).
📝 실기 이렇게 나온다: 위 <사원>에서 SELECT 이름 FROM 사원 WHERE 이름 LIKE '_민%'; 의 결과로 출력되는 이름을 모두 쓰시오. → 답: 박민수, 최민아 (2번째 글자가 '민'인 행만; 이수민은 제외)
02

집계함수 + GROUP BY

"부서별 평균", "과목별 최고점" 같은 문제는 100% 이 조합. HAVING과 짝으로 나옵니다.

FUNCTION

5대 집계함수

★★★
  • COUNT(*) — 행 개수 (NULL 포함), COUNT(컬럼) 은 NULL 제외
  • SUM / AVG — 합계 / 평균 (숫자만)
  • MAX / MIN — 최대 / 최소
●●●groupby.sql
-- 과목별 평균이 90 이상인 과목과 그 평균
SELECT 과목, AVG(점수) AS 평균
FROM   성적
GROUP BY 과목
HAVING AVG(점수) >= 90;
🎯 WHERE vs HAVING: 그룹으로 묶기 전 개별 행 조건은 WHERE, 묶은 후 그룹 조건(집계함수 포함)은 HAVING. 집계함수는 WHERE에 못 씁니다.
NULL

NULL 처리와 치환 함수

★★☆
  • NULL 연산 — NULL + 값 = NULL (NULL이 섞인 산술 결과는 NULL)
  • 집계와 NULL — SUM·AVG는 NULL을 제외하고 계산 (AVG는 NULL 행을 분모에서도 뺌)
  • NULL 비교 — = NULL 불가, 반드시 IS NULL / IS NOT NULL
🔁 NULL 치환 함수 (DBMS별 같은 기능): NVL(오라클) = COALESCE(표준 SQL) = ISNULL(SQL Server) = IFNULL(MySQL). 예: NVL(점수, 0) → 점수가 NULL이면 0으로 대체.
  • NVL2(식, A, B) — 식이 NULL이 아니면 A, NULL이면 B 반환
  • NULLIF(A, B) — A=B이면 NULL, 다르면 A 반환
  • COALESCE(a, b, c…) — 인자 중 처음으로 NULL이 아닌 값 반환
GROUP

GROUP BY + HAVING — 결과 추적 (NULL 분모 함정)

★★★

그룹으로 묶은 뒤 몇 행이 남고, 평균이 어떤 분모로 나뉘는지를 셉니다. 급여가 NULL인 사원이 섞이면 COUNT(*)와 AVG의 분모가 달라지는 게 최대 함정입니다.

●●●사원 (샘플)
부서    급여
영업    3000
영업    5000
개발    4000
개발    6000
개발    NULL
인사    4500
●●●groupby.sql
SELECT 부서, COUNT(*) AS 인원, AVG(급여) AS 평균급여
FROM   사원
GROUP BY 부서
HAVING COUNT(*) >= 2;

결과 — HAVING(>=2)으로 인사(1명)는 탈락:

●●●결과
부서    인원    평균급여
영업    2      4000     ← (3000+5000)/2
개발    3      5000     ← (4000+6000)/2, NULL은 분모에서 제외!

개발 부서 뜯어보기: 행은 3개(COUNT(*)=3)지만 평균은 NULL을 뺀 2명으로 나눠 5000. 분모를 COUNT(급여)로 확인하면 2가 나옵니다.

●●●분모 확인.sql
SELECT 부서, COUNT(*), COUNT(급여)
FROM 사원 GROUP BY 부서 HAVING COUNT(*) >= 2;
-- 개발 → 3, 2   |   영업 → 2, 2
⚠ 함정 — 순서와 분모: ① 개별 행 조건은 WHERE(그룹 전), 그룹·집계 조건은 HAVING(그룹 후) — 집계함수는 WHERE에 못 씀. ② AVG는 NULL을 분모에서 제외하므로 COUNT(*)와 분모가 다를 수 있음. "급여합 ÷ COUNT(*)"로 계산하면 오답.
📝 실기 이렇게 나온다: 위 <사원>에서 개발 부서의 COUNT(*)와 AVG(급여) 값을 각각 쓰시오. → 답: COUNT(*) = 3, AVG(급여) = 5000 (행은 3개지만 NULL 급여는 평균 분모에서 빠져 10000 / 2 = 5000)
03

JOIN — 테이블 연결

두 테이블에서 값을 가져오는 문제. INNER/OUTER 구분과 ON 조건 작성이 핵심.

JOIN

INNER vs OUTER

★★☆
  • INNER JOIN — 양쪽 모두 일치하는 행만
  • LEFT OUTER JOIN — 왼쪽 전부 + 오른쪽 일치분 (없으면 NULL)
  • RIGHT OUTER JOIN — 오른쪽 전부 + 왼쪽 일치분
●●●join.sql
SELECT 학생.이름, 학과.학과명
FROM   학생 INNER JOIN 학과
ON     학생.학과코드 = 학과.학과코드;

-- 묵시적(암시적) 조인 = 옛 방식(WHERE 절 조인), 아직 출제됨
SELECT 이름, 학과명
FROM   학생, 학과
WHERE  학생.학과코드 = 학과.학과코드;
📝 명칭 정리: 콤마+WHERE 방식은 묵시적(암시적) 조인(옛 방식). 한편 동등조인(equi-join)은 조인 조건을 등호(=)로 잇는 것을 가리키는 별개 분류로, INNER JOIN ... ON a=b 도 동등조인입니다. 즉 "옛 방식이냐(문법 분류)"와 "등호로 잇느냐(조건 분류)"는 다른 축입니다.
JOIN

JOIN 결과 행수 계산 (INNER · OUTER · CROSS)

★★★

조인 문제의 절반은 "결과가 몇 행이냐"입니다. 한쪽에만 있는 행과 NULL 외래키가 행 수를 가릅니다. 미매칭이 섞인 샘플로 직접 세어 봅니다.

●●●샘플
[사원 4행]
사번  이름    부서코드
 1    김사원   D1
 2    이사원   D2
 3    박사원   D2
 4    최사원   NULL    ← 부서코드가 NULL

[부서 3행]
부서코드  부서명
 D1      영업
 D2      개발
 D3      인사    ← 소속 사원 없음
  • INNER JOIN → 코드가 맞는 짝만: 김-영업, 이-개발, 박-개발 → 3행 (최사원·인사 제외)
  • LEFT OUTER JOIN(사원 기준) → 사원 4명 전부, 최사원의 부서명은 NULL → 4행
  • RIGHT OUTER JOIN(부서 기준) → 부서 3개 전부, 인사의 사원값 NULL → 4행 (영업1+개발2+인사1)
  • CROSS JOIN → 조건 없이 모든 조합 = 4 × 3 = 12행 (카티션 곱, m×n)
●●●left_join.sql
SELECT 사원.이름, COALESCE(부서.부서명, '없음') AS 부서명
FROM   사원 LEFT OUTER JOIN 부서
ON     사원.부서코드 = 부서.부서코드
ORDER BY 사원.사번;
-- 김사원 영업 / 이사원 개발 / 박사원 개발 / 최사원 없음  → 4행
⚠ 함정 — 행 수: INNER는 미매칭을 버려서 가장 적고(3행), OUTER는 기준 테이블 행을 전부 보존(4행)합니다. NULL 부서코드(최사원)는 INNER·RIGHT에선 사라지지만 LEFT에선 남습니다. CROSS는 조건이 없어 항상 두 테이블 행수의 곱(4×3=12)이라는 게 계산 문제로 단골.
📝 실기 이렇게 나온다: 사원 4행(1명은 부서코드 NULL), 부서 3행(1개는 소속 사원 없음)을 CROSS JOIN하면 결과는 몇 행인가? → 답: 12행 (4 × 3, 조인 조건이 없는 카티션 곱)
04

DDL — 구조 정의 + 제약조건

CREATE / ALTER / DROP. 특히 제약조건(constraint)을 빈칸으로 묻는 문제가 자주 나옵니다.

DDL

CREATE TABLE + 제약조건

★★★
●●●create.sql
CREATE TABLE 학생 (
  학번  CHAR(8)     PRIMARY KEY,
  이름  VARCHAR(20) NOT NULL,
  학과코드 CHAR(4),
  나이  INT     CHECK(나이 >= 18),
  이메일 VARCHAR(50) UNIQUE,
  FOREIGN KEY(학과코드) REFERENCES 학과(학과코드)
);
  • PRIMARY KEY — 기본키, NULL 불가 + 중복 불가
  • FOREIGN KEY — 외래키, 다른 테이블 참조 (참조 무결성)
  • UNIQUE — 중복 불가 (단, NULL은 허용)
  • NOT NULL — NULL 입력 금지
  • CHECK — 값 범위/조건 제한
  • DEFAULT — 기본값 지정
🔗 FK 참조 동작 (ON DELETE / ON UPDATE): 부모 행이 삭제·변경될 때 자식 행을 어떻게 처리할지 지정. CASCADE=연쇄 삭제·변경, SET NULL=자식의 외래키를 NULL로, SET DEFAULT=기본값으로, RESTRICT·NO ACTION=참조 중이면 거부. 예: FOREIGN KEY(학과코드) REFERENCES 학과(학과코드) ON DELETE CASCADE
📝 ALTER 빈출: 컬럼 추가 ALTER TABLE 학생 ADD 전화 VARCHAR(15); / 수정 MODIFY / 삭제 DROP COLUMN
DDL

ALTER TABLE + DROP … CASCADE vs RESTRICT

★★☆

CREATE로 만든 테이블의 구조를 바꾸는 ALTER, 그리고 삭제·회수 시 참조 관계를 어떻게 처리할지 정하는 CASCADE/RESTRICT. 앞의 REVOKE … CASCADE와 같은 결(연쇄 vs 거부)로 묶어 외우면 편합니다.

●●●alter.sql
-- 컬럼 추가 (ADD 뒤 COLUMN 없이 바로 컬럼명·타입)
ALTER TABLE 회원 ADD 등급 CHAR(1);
-- 자료형/제약 변경: Oracle은 MODIFY, 표준·SQL Server는 ALTER COLUMN
ALTER TABLE 회원 MODIFY 등급 VARCHAR(10);
-- 컬럼 삭제 (이때는 COLUMN 명시)
ALTER TABLE 회원 DROP COLUMN 등급;
-- 테이블 이름 변경
ALTER TABLE 회원 RENAME TO 고객;
●●●drop.sql
DROP TABLE 부서 CASCADE;   -- 부서를 참조하는 FK 등 종속 객체까지 연쇄 삭제
DROP TABLE 부서 RESTRICT;  -- 참조하는 객체가 있으면 삭제 거부(취소)
  • CASCADE — 삭제·회수 대상을 참조하는 것들까지 연쇄로 함께 처리
  • RESTRICT — 참조하는 객체가 하나라도 있으면 거부(안전장치)
  • 같은 짝: REVOKE … CASCADE=물려준 권한까지 연쇄 회수 / REVOKE … RESTRICT=물려준 게 있으면 거부
⚠ 함정 ① ADD/DROP 비대칭: 컬럼 추가는 ADD 컬럼 타입(COLUMN 생략), 컬럼 삭제는 DROP COLUMN 컬럼(COLUMN 명시). 함정 ② 방향: CASCADE=연쇄 삭제(공격적), RESTRICT=참조 있으면 거부(보수적) — 반대로 쓰면 오답. (외우기 팁: CASCADE=계단식으로 줄줄이, RESTRICT=제한·거부)
📝 실기 이렇게 나온다 ①: 회원 테이블에 VARCHAR(15) 타입의 '전화' 컬럼을 추가하는 SQL을 작성하시오. → 답: ALTER TABLE 회원 ADD 전화 VARCHAR(15);
📝 실기 이렇게 나온다 ②: DROP TABLE 시 삭제할 테이블을 참조하는 다른 객체가 있으면 삭제를 거부하는 옵션은? → 답: RESTRICT (연쇄 삭제는 CASCADE)
05

DML — 데이터 조작

INSERT / UPDATE / DELETE. SELECT 다음으로 손에 익혀야 할 기본기.

DML

INSERT · UPDATE · DELETE

★★☆
●●●dml.sql
-- 삽입
INSERT INTO 학생(학번, 이름) VALUES('20240001', '홍길동');

-- 수정 (WHERE 없으면 전체 변경! 주의)
UPDATE 학생 SET 학과코드 = 'CS01' WHERE 학번 = '20240001';

-- 삭제
DELETE FROM 학생 WHERE 학번 = '20240001';
⚠ WHERE 누락 사고: UPDATE/DELETE에 WHERE를 빼면 전체 행이 대상이 됩니다. 시험에선 "특정 조건만" 명시되어 있으니 WHERE를 꼭 붙이세요.
COMPARE

DELETE vs TRUNCATE vs DROP

★★★

"행만 지우기"와 "테이블 자체 없애기"를 구분하는 단골 비교. 어느 분류(DML/DDL)인지, 롤백이 되는지가 핵심입니다.

구분 DELETE TRUNCATE DROP
분류 DML DDL DDL
삭제 대상 조건(WHERE)에 맞는 행 선택 삭제 전체 행 삭제 테이블 구조까지 제거
테이블 구조 유지 유지 함께 삭제
롤백(ROLLBACK) 가능 불가 불가
🎯 한 줄 정리: DELETE=행 선택 삭제·롤백 가능(DML) / TRUNCATE=전체 행 삭제·구조는 유지·롤백 불가(DDL) / DROP=테이블 구조까지 제거(DDL).
06

DCL — 권한 제어

GRANT / REVOKE. 짧지만 거의 매회 단답으로 출제되는 효자 영역.

DCL

GRANT · REVOKE

★★★
●●●dcl.sql
-- 권한 부여 (WITH GRANT OPTION = 재부여 권한까지)
GRANT SELECT, UPDATE ON 학생 TO 사용자1 WITH GRANT OPTION;

-- 권한 회수 (CASCADE = 연쇄 회수)
REVOKE SELECT ON 학생 FROM 사용자1 CASCADE;
  • GRANT 권한 ON 객체 TO 사용자 — 부여
  • REVOKE 권한 ON 객체 FROM 사용자 — 회수
  • WITH GRANT OPTION — 받은 권한을 남에게 또 줄 수 있음
  • CASCADE — 권한을 물려받은 사용자들 것까지 연쇄 회수
07

TCL — 트랜잭션 제어

COMMIT / ROLLBACK / SAVEPOINT. 트랜잭션의 ACID 특성과 묶어서 외우세요.

TCL

트랜잭션 ACID 특성

★★★
  • 원자성 Atomicity — 전부 성공 or 전부 실패 (All or Nothing)
  • 일관성 Consistency — 실행 후에도 DB 일관성 유지
  • 격리성 Isolation — 동시 실행 트랜잭션끼리 간섭 불가
  • 영속성 Durability — 완료된 결과는 영구 반영
🔑 두문자: 원·일·격·영 (ACID). "All or Nothing = 원자성" 매칭 문제가 단골. COMMIT=확정, ROLLBACK=취소, SAVEPOINT=되돌릴 지점 지정.
08

절차형 SQL — 트리거·프로시저

난이도 높지만 배점이 큼. 트리거 구조(BEFORE/AFTER, FOR EACH ROW)를 빈칸으로 묻습니다.

PROC

트리거 (TRIGGER)

★★☆

특정 이벤트(INSERT/UPDATE/DELETE)가 발생하면 자동 실행되는 절차형 SQL.

●●●trigger.sql
CREATE [OR REPLACE] TRIGGER 트리거명
[BEFORE | AFTER] INSERT ON 테이블명
REFERENCING NEW AS new_row
FOR EACH ROW
WHEN (조건)
BEGIN
  -- 실행할 SQL
END;
  • BEFORE / AFTER — 이벤트 전/후 실행 시점
  • FOR EACH ROW — 행 단위 실행 (행 트리거)
  • NEW / OLD — 변경 후/전 값 참조
🧩 3총사 구분: 프로시저=쿼리 묶음 실행 / 사용자정의함수=단일 값 반환 / 트리거=이벤트 시 자동 실행.
09

VIEW + 기타 빈출

뷰, 정렬, 부속질의 등 자주 섞여 나오는 마무리 개념들.

VIEW

뷰 생성과 특징

★★☆
●●●view.sql
CREATE VIEW 우수학생 AS
SELECT 학번, 이름 FROM 학생 WHERE 학점 >= 4.0;
  • 가상 테이블 — 실제 데이터 저장 X, 정의만 저장
  • 독립성·보안성 향상 (필요한 컬럼만 노출)
  • 데이터 수정·삭제는 갱신 가능 뷰일 때만 가능 (단일 테이블 기반 + 기본키 포함, 집계함수·DISTINCT·GROUP BY 등이 없을 것)
  • 인덱스 생성 불가, 정의 변경 불가(DROP 후 재생성)
🔍 부속질의(서브쿼리): WHERE 점수 > (SELECT AVG(점수) FROM 성적) — 평균 이상 조회 같은 문제로 출제.
INDEX

인덱스(INDEX) — 문법과 장단점

★★☆

"검색을 빠르게 하는 객체"를 단답으로 묻거나, 왜 인덱스를 함부로 많이 걸면 안 되는지(쓰기 성능 저하)를 서술로 물어봅니다. 뷰가 "저장 안 하는 가상 테이블"이라면, 인덱스는 "검색을 돕는 별도 자료구조"라는 대비로 기억하세요.

●●●index.sql
-- 생성 (UNIQUE 붙이면 중복 방지 인덱스)
CREATE [UNIQUE] INDEX idx_사원_이름 ON 사원(이름);
-- 여러 컬럼을 묶는 복합 인덱스도 가능
CREATE INDEX idx_사원_부서 ON 사원(부서코드, 직급);
-- 삭제
DROP INDEX idx_사원_이름;
  • 대부분 B-트리(B-tree) 기반의 정렬된 자료구조 → 전체 스캔 대신 빠른 탐색
  • 장점 — WHERE·JOIN·ORDER BY의 검색 속도 향상
  • 단점 — INSERT/UPDATE/DELETE 때 인덱스도 같이 갱신 → 쓰기 성능 저하 + 저장 공간 추가

어디에 걸고, 어디는 피하나

  • 적합 — WHERE·조인 키로 자주 검색되는 컬럼, 값이 다양한(카디널리티 높은) 컬럼
  • 부적합 — 자주 변경(삽입·수정·삭제 잦은)되는 컬럼, 중복이 많은(카디널리티 낮은, 예: 성별) 컬럼
⚠ 함정: 인덱스는 SELECT는 빠르게, INSERT/UPDATE/DELETE는 느리게 만드는 트레이드오프입니다. "많이 걸수록 좋다"는 오답 — 갱신이 잦거나 성별처럼 값 종류가 적은 컬럼엔 오히려 비효율. 또 일반 뷰(VIEW)에는 인덱스를 만들 수 없습니다.
📝 실기 이렇게 나온다: 테이블의 특정 컬럼 검색 속도를 향상시키기 위해 만드는, B-트리 기반의 별도 정렬 자료구조는 무엇인가? → 답: 인덱스(INDEX) (대신 삽입·수정·삭제 성능은 저하됨)
10

순위함수 · 집합연산

최근 SQL 활용 영역에서 출제되는 심화. 순위함수 3종 구분과 집합연산 차이가 포인트입니다.

WINDOW

순위함수 RANK · DENSE_RANK · ROW_NUMBER

★★☆

동점 처리 방식이 셋 다 다릅니다. 점수 90, 90, 80을 예로 보면 차이가 분명합니다.

●●●rank.sql
SELECT 이름, 점수,
  RANK() OVER (ORDER BY 점수 DESC) AS 순위
FROM 성적;
  • RANK() — 동점은 같은 순위, 다음은 건너뜀 → 1, 1, 3
  • DENSE_RANK() — 동점은 같은 순위, 다음은 안 건너뜀 → 1, 1, 2
  • ROW_NUMBER() — 동점이어도 무조건 고유 순번 → 1, 2, 3
🎯 한 줄 구분: RANK는 "건너뛰는" 등수(올림픽 메달), DENSE_RANK는 "안 건너뛰는" 등수, ROW_NUMBER는 동점 없이 줄 세우기. OVER(ORDER BY …) 구조는 셋 다 동일.
SET

집합연산 UNION · INTERSECT · EXCEPT

★★☆
  • UNION — 합집합, 중복 제거
  • UNION ALL — 합집합, 중복 그대로 유지
  • INTERSECT — 교집합 (양쪽 공통)
  • EXCEPT (Oracle은 MINUS) — 차집합
●●●set.sql
SELECT 이름 FROM A
UNION
SELECT 이름 FROM B;
⚠ 함정: UNION은 중복을 없애지만 UNION ALL은 중복을 그대로 둡니다. "중복 포함/제거" 단서를 놓치면 오답. 양쪽 SELECT의 컬럼 수·자료형이 같아야 합니다.
WINDOW

순위 함수 — 동점(TIE) 결과표로 굳히기

★★☆

함수 정의는 앞 블록에서 봤으니, 같은 데이터에 세 함수를 돌린 결과 차이만 확실히.

점수 90, 90, 80, 70을 내림차순으로 순위 매기면 동점(90) 처리에서 세 함수가 갈립니다.

●●●rank_compare.sql
SELECT 점수,
  RANK()       OVER (ORDER BY 점수 DESC) AS r,
  DENSE_RANK() OVER (ORDER BY 점수 DESC) AS dr,
  ROW_NUMBER() OVER (ORDER BY 점수 DESC) AS rn
FROM 성적
ORDER BY 점수 DESC, 이름;
●●●result
 score  | RANK | DENSE_RANK | ROW_NUMBER
--------+------+------------+-----------
   90   |  1   |     1      |     1
   90   |  1   |     1      |     2
   80   |  3   |     2      |     3
   70   |  4   |     3      |     4

OVER에 PARTITION BY 반을 넣으면 그룹(반)별로 순위가 각각 1부터 다시 시작합니다.

⚠ RANK vs DENSE_RANK: RANK는 동점 수만큼 다음 순위를 건너뛰고(…1, 1, 3), DENSE_RANK는 건너뛰지 않습니다(…1, 1, 2). ROW_NUMBER는 동점이어도 항상 유일한 번호를 매깁니다.
📝 실기 이렇게 나온다: "점수가 90, 90, 80인 세 학생에게 순위를 매길 때 80점 학생의 순위는 RANK=( ㉠ ), DENSE_RANK=( ㉡ ), ROW_NUMBER=( ㉢ )이다." → 답: ㉠ 3 ㉡ 2 ㉢ 3
11

DB 이론 — 단답 빈출

SQL 작성과 별개로 단답형으로 나오는 DB 이론. 두문자로 외우면 효율적입니다. 코딩 난이도가 올라간 만큼 여기서 점수를 확보하세요.

KEY

정규화 단계 — 두문자 "도부이결다조"

★★★

중복을 제거해 이상현상(Anomaly)을 막는 무손실 분해 과정. 단계별 제거 대상이 곧 답입니다.

  • 1NF — 도메인이 원자값 (반복 그룹 제거)
  • 2NF — 부분 함수 종속 제거 (완전 함수 종속)
  • 3NF — 이행적 함수 종속 제거
  • BCNF — 결정자이면서 후보키가 아닌 것 제거
  • 4NF — 다치(다중값) 종속 제거
  • 5NF — 조인 종속성 이용 분해
🔑 "도부이결다조" 순서로 암기. 단계와 "제거하는 종속"을 짝지어 묻는 빈칸 문제가 단골입니다.
KEY

이상현상 + 무결성 제약

★★★

이상현상(Anomaly) 3종

  • 삽입 이상 — 원치 않는 값까지 함께 넣어야 삽입 가능
  • 갱신 이상 — 중복 데이터 일부만 수정돼 불일치 발생
  • 삭제 이상 — 한 행 삭제 시 필요한 정보까지 사라짐

무결성(Integrity) 제약

  • 개체 무결성 — 기본키는 NULL·중복 불가
  • 참조 무결성 — 외래키는 참조 불가능한 값 못 가짐
  • 도메인 무결성 — 속성값은 정의된 도메인(범위) 내
KEY

키(Key) 종류

★★☆
  • 후보키 — 유일성 + 최소성을 모두 만족
  • 기본키(PK) — 후보키 중 선택, NULL·중복 불가
  • 대체키 — 기본키로 선택되지 않은 나머지 후보키
  • 슈퍼키 — 유일성은 있으나 최소성은 없음
  • 외래키(FK) — 다른 테이블의 PK를 참조
🧩 유일성 vs 최소성: 슈퍼키는 유일성만, 후보키는 둘 다. 차이를 묻는 단답이 자주 나옵니다.
KEY

관계형 용어 + 스키마 3계층

★★☆

릴레이션 용어

  • 튜플(Tuple) — 행(row), 카디널리티 = 튜플의 개수
  • 속성(Attribute) — 열(column), 차수(Degree) = 속성의 개수
  • 도메인(Domain) — 속성이 가질 수 있는 값의 범위

스키마 3계층

  • 외부 스키마 — 사용자·응용 관점의 뷰
  • 개념 스키마 — 전체 논리적 구조 (기관 전체 관점)
  • 내부 스키마 — 물리적 저장 구조
⚠ 헷갈림 주의: 카디널리티=행 개수, 차수=열 개수. 서로 바꿔 쓰면 0점.
KEY

관계대수 — 순수 관계 연산자

★★☆

관계대수 연산자는 순수 관계 연산자 4종과 일반 집합 연산자 4종으로 나뉩니다. SQL과 대응시키는 문제가 단골입니다.

순수 관계 연산자 (4종)

  • SELECT (σ, 시그마) — 조건에 맞는 행(튜플) 선택 → SQL WHERE
  • PROJECT (π, 파이) — 원하는 속성(열)만 추출 → SQL SELECT 컬럼
  • JOIN (⋈) — 공통 속성으로 두 릴레이션 결합 → SQL JOIN
  • DIVISION (÷) — "모두 포함"하는 튜플을 골라내는 나누기 연산

일반 집합 연산자 (4종)

  • 합집합(UNION, ∪) · 교집합(INTERSECTION, ∩) · 차집합(DIFFERENCE, −) · 교차곱(CARTESIAN PRODUCT, ×)
🔑 기호 암기: σ↔행 선택(WHERE), π↔열 선택(SELECT), ⋈↔JOIN, ÷↔나누기. 순수 관계 연산자는 관계대수에만 있는 연산이고, 합·교·차·교차곱은 일반 집합 연산자입니다.
KEY

트랜잭션 — 회복 · 병행제어

★★☆

회복 기법

  • 지연 갱신 — 트랜잭션 완료 전까지 DB에 반영 안 함
  • 즉각 갱신 — 수행 중 변경을 바로 DB에 반영 (로그 필요)
  • REDO — 완료된 트랜잭션 재실행 / UNDO — 미완료 취소

병행제어(Concurrency) 기법

  • 로킹(Locking) — 데이터에 잠금을 걸어 직렬성 보장
  • 타임스탬프 — 시간 순서로 트랜잭션 실행 순서 결정
  • 낙관적 검증 — 일단 수행 후 종료 시점에 검증
🔒 로킹 단위: 단위가 작아지면 병행성(공유도)도, 관리 오버헤드도 함께 증가(단위↓ ⇒ 둘 다 ↑). 단위가 커지면 둘 다 감소(단위↑ ⇒ 둘 다 ↓). 공유도와 오버헤드가 같은 방향으로 움직인다는 점을 묻습니다.
DENORM

반정규화(De-normalization)

★★☆

정규화의 역과정 — 시험은 "정규화와 반대로, 왜 일부러 중복을 허용하나"를 묻습니다.

조회 성능 향상이나 개발 편의를 위해 의도적으로 정규화 원칙을 위배해 중복을 허용하는 설계 기법입니다. 정규화가 "중복 제거 → 이상현상 방지"라면, 반정규화는 "중복 허용 → 조인·집계 비용 감소"로 정반대 방향이라는 점이 핵심 구별 포인트입니다.

테이블 통합자주 함께 조회되는 두 테이블을 하나로 합침 — 조인 자체를 제거
테이블 분할수평 분할=행 기준(예: 연도별), 수직 분할=컬럼 기준(자주 쓰는 컬럼만 분리)
중복 테이블 추가집계·이력 등 목적에 맞춘 별도 사본 테이블을 추가
중복/파생 컬럼조인해야 얻는 값이나 계산 결과(합계 등)를 컬럼으로 미리 저장
⚠ 트레이드오프: 조회 성능은 오르지만 같은 데이터가 여러 곳에 중복돼 갱신 시 정합성이 깨질 위험(갱신 이상)과 저장 공간이 늘어납니다. "조인이 과도하거나 집계가 빈번"할 때 선택적으로 적용하는 것이지, 항상 좋은 것이 아닙니다.
📝 실기 이렇게 나온다: "시스템의 성능 향상과 개발·운영의 편의를 위해 정규화된 데이터 모델을 의도적으로 통합·중복·분리하는 데이터 모델링 기법은?" → 답: 반정규화(De-normalization) — 정규화의 역과정
DIST-DB

분산 데이터베이스 — 투명성(Transparency)

★★★

분산돼 있음을 사용자가 의식하지 못하게 숨기는 성질 — "무엇을 숨기느냐"가 곧 답입니다.

분산 DB는 여러 사이트에 데이터가 흩어져 있지만 사용자에게는 하나의 논리적 DB처럼 보여야 합니다. 그 목표를 이루는 4대 투명성은 각각 숨기는 대상이 다릅니다.

위치 투명성데이터가 어느 사이트에 있는지 몰라도 이름만으로 접근 — 물리적 저장 위치를 숨김
중복(복제) 투명성같은 데이터의 사본이 여러 개 있어도 하나처럼 사용 — 사본의 존재를 숨김
병행 투명성여러 트랜잭션이 동시에 수행돼도 서로 간섭 없이 일관된 결과 — 동시 실행을 숨김
장애 투명성일부 사이트·통신 장애가 나도 트랜잭션을 정확히(원자적으로) 처리 — 장애를 숨김

위 4가지에 분할(단편화) 투명성(데이터가 어떻게 나뉘어 저장됐는지 모름)과 지역사상(local mapping) 투명성(지역 DBMS 이름과 무관하게 접근)을 더하면 6대 투명성으로도 분류합니다.

🔑 외우기 팁: "무엇을 숨기나"로 묶기 — 위치=어디, 중복=사본, 병행=동시, 장애=고장.
📝 실기 이렇게 나온다: "분산 데이터베이스에서 사용자가 데이터의 물리적 저장 위치를 알지 못해도 접근할 수 있게 하는 투명성은?" → 답: 위치 투명성 (사본 존재를 숨기면 중복 투명성)
ERD

ER 모델 표기법 · 카디널리티 · 디그리

★★☆

피터 첸(Peter Chen) 표기의 기호와, 매번 헷갈리는 두 용어를 한 번에.

사각형 □개체(Entity) — 저장 대상(예: 학생, 과목)
타원 ○속성(Attribute). 이중 타원=다중값 속성, 속성명에 밑줄=기본키
마름모 ◇관계(Relationship) — 개체 간 연관(예: 수강)
선 —개체·속성·관계를 연결. 선 위에 1:1 / 1:N / M:N으로 대응 수(매핑 카디널리티)를 표시
⚠ 최다 함정 — 카디널리티 vs 디그리: 카디널리티(Cardinality)=릴레이션의 튜플(행) 수, 디그리(Degree, 차수)=속성(열) 수. 둘을 반대로 외우는 실수가 가장 많습니다.
🔑 외우기 팁: 릴레이션 학생(학번, 이름, 학과)에 튜플이 100개면 → 디그리=3(속성 수), 카디널리티=100(튜플 수).
📝 실기 이렇게 나온다: "ER 다이어그램에서 개체는 ( ㉠ ), 속성은 ( ㉡ ), 관계는 ( ㉢ ) 기호로 표현한다." → 답: ㉠ 사각형 ㉡ 타원 ㉢ 마름모
📝 실기 이렇게 나온다: "릴레이션에서 속성의 수를 ( ㉠ ), 튜플의 수를 ( ㉡ )(이)라 한다." → 답: ㉠ 디그리(차수) ㉡ 카디널리티
SUBQUERY

부속질의 심화 — IN · EXISTS · ANY · ALL

★★☆

서브쿼리가 여러 행을 돌려줄 때 쓰는 다중 행 연산자 구분.

단일 행 연산자(=, >, < …)는 서브쿼리 결과가 딱 1행일 때만 쓸 수 있습니다. 결과가 여러 행이면 아래 다중 행 연산자를 써야 하며, 각각 "집합을 어떻게 비교하는지"가 다릅니다.

IN집합에 포함되면 참. = ANY와 같은 의미
> ALL집합의 모든 값보다 커야 참 → 사실상 최댓값보다 큰
> ANY하나라도 만족하면 참(=SOME) → 사실상 최솟값보다 큰
EXISTS서브쿼리 결과가 한 행이라도 있으면 참. 상관(correlated) 서브쿼리와 궁합
●●●subquery.sql
-- 서울에 있는 부서 소속 사원 (IN + 부속질의)
SELECT 이름 FROM 사원
WHERE  부서 IN (SELECT 코드 FROM 부서 WHERE 지역='서울')
ORDER BY 사번;
-- 결과: 김철수, 이영희, 박민수
⚠ NOT IN + NULL 함정: 부속질의 결과에 NULL이 하나라도 섞이면 NOT IN은 어떤 행도 참이 될 수 없어 결과가 통째로 공집합이 됩니다. 이럴 땐 NOT EXISTS로 바꿔 쓰면 안전합니다.
📝 실기 이렇게 나온다: "서브쿼리가 반환한 값들 중 가장 큰 값보다 커야 참이 되는 다중 행 연산자는?" → 답: > ALL (반대로 > ANY는 최솟값보다 크면 참)
