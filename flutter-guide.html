Flutter란 무엇인가

overview

하나의 코드베이스로 iOS·Android·웹·데스크톱을 모두 그리는 UI 툴킷. 언어는 Dart.

Flutter의 가장 큰 특징은 네이티브 컴포넌트를 쓰지 않는다는 점입니다. React Native가 OS의 버튼을 빌려 쓰는 것과 달리, Flutter는 자체 렌더링 엔진으로 모든 픽셀을 직접 그립니다. 그래서 플랫폼이 달라도 디자인이 거의 동일하게(픽셀 일관성 높게) 나옵니다. (2026년 기준 모바일은 Impeller가 기본 — iOS는 Impeller 전용, Android는 Vulkan 지원 기기에서 기본이고 미지원 기기는 OpenGL로 폴백. 웹은 여전히 Skia(CanvasKit) 기반입니다.)

면접 한 줄: "Flutter는 OS 위젯을 쓰지 않고 자체 엔진(Skia/Impeller)으로 직접 그리기 때문에, 모든 플랫폼에서 픽셀 단위로 동일한 UI를 보장합니다."

Dart 언어 기초

part 1 · 기초

Flutter를 쓰려면 Dart를 알아야 합니다. JS/Java를 안다면 70%는 이미 아는 셈.

📦변수와 타입 — var · final · const · dynamic

Dart의 변수 선언은 이 다섯을 구분하면 끝입니다. 특히 dynamic은 편해 보여도 타입 검사를 통째로 꺼버려 런타임 사고의 주범이라, 언제 무엇을 쓰는지가 중요해요.

variables.dart
// ① 타입 명시 — 의도가 분명해 협업·유지보수에 가장 안전
int age = 30;
String name = '창한';

// ② var — 우변으로 타입을 '추론'(단, 타입은 고정됨)
var city = 'Seoul';       // String으로 고정 → city = 1; 은 컴파일 에러

// ③ final — 딱 한 번만 할당(값은 실행 중에 정해도 됨)
final now = DateTime.now();  // 실행 시점에 한 번 박힘, 재할당 불가

// ④ const — 컴파일 시점에 값이 '박제'(깊은 불변)
const pi = 3.14;            // 빌드 전에 이미 확정돼야 함
키워드재할당값이 정해지는 시점언제 쓰나
int·StringO—타입을 분명히 드러내고 싶을 때(권장 기본)
varO—우변만 봐도 타입이 뻔할 때(추론, 타입은 고정)
finalX런타임한 번 정하고 안 바꾸는 값(대부분의 지역변수·필드)
constX컴파일타임상수·const 위젯(빌드 최적화)

🔍 dynamic을 쓸 때 vs 안 쓸 때 — 같은 로직인데 한쪽은 런타임에 터지고, 한쪽은 컴파일에서 막힙니다.

❌ dynamic — 컴파일이 안 막아줌
dynamic value = '42';   // 사실은 String
int n = value + 1;     // 컴파일 통과!

// 💥 런타임에서야 폭발:
// type 'int' is not a
// subtype of type 'String'
✅ 타입 명시 — 컴파일에서 차단
int value = 42;
int n = value + 1;     // 43

// 잘못 쓰면 IDE가 빨간 줄로
// 즉시 알려줌(런타임까지 안 감)
차이: dynamic은 "타입 검사하지 마" 표시라 자동완성·컴파일 체크가 전부 꺼집니다. 위 ❌는 빌드는 되지만 결국 사용자 손에서 터지죠. dynamic은 JSON 파싱처럼 타입을 정말 모를 때만 쓰고, 받는 즉시 구체 타입으로 변환하세요(value as int, int.parse(...)).
final vs const — 가장 헷갈리는 함정: final은 "변수를 다시 할당 못 함", const는 "값 자체가 컴파일타임 상수"입니다. 그래서 내용 변경이 갈립니다 — final l = [1]; l.add(2); 는 OK([1, 2]), const l = [1]; l.add(2); 는 런타임 에러(UnsupportedError). Flutter의 const 위젯이 재빌드를 건너뛰는 것도 이 "깊은 불변" 덕분입니다.

❓Null Safety — ? · ?. · ?? · !

개념: Dart는 기본적으로 null을 허용하지 않습니다. 변수에 null이 들어올 수 있으면 타입 뒤에 ?를 붙여 "이건 비어 있을 수 있어"라고 컴파일러에 알려야 해요. 이렇게 nullable과 non-nullable을 타입으로 나눠두면, 다른 언어에서 런타임에 앱을 죽이던 NPE(Null Pointer Exception)를 컴파일 단계에서 미리 차단합니다. 즉 "실행해 봐야 아는 버그"를 "빌드하면 빨간 줄로 알려주는 버그"로 끌어올리는 장치입니다.

🥤 일상 비유 — "내용물 있음"이 보장된 컵: Dart에서 String은 "반드시 음료가 담긴 컵"입니다. 빈 컵(null)을 건네면 컴파일러가 거부해요. 비어 있을 수도 있으면 String?로 "빈 컵일 수 있음" 라벨을 붙여야 하고, 마시기 전(사용 전)에 비었는지 확인하도록 강제됩니다. "빈 컵인 줄 모르고 들이켜다 사레들리는"(런타임 NPE) 사고를 미리 막아주는 셈이죠.
null_safety.dart
String name = null;    // ❌ 컴파일 에러! non-nullable엔 null 불가
String? nickname = null; // ✅ ?를 붙이면 null 허용(nullable)

// ?. → 앞이 null이면 통째로 건너뛰고 결과는 null (JS의 ?. 와 동일)
int? len = nickname?.length;        // nickname이 null이면 len도 null

// ?? → 왼쪽이 null이면 오른쪽 기본값 사용
String display = nickname ?? '손님'; // null이면 '손님'

// ??= → 비어 있을 때만 채워 넣기(이미 값 있으면 그대로)
nickname ??= '익명';

// ! → "이건 절대 null 아님"이라고 개발자가 단언(틀리면 런타임 폭발, 신중히!)
String? raw = display.isEmpty ? null : display; // raw는 String?(nullable)
int sure = raw!.length;            // 값이 있다고 확신할 때만 !
연산자하는 일결과가 null일 수 있나대표 쓰임
? (타입 뒤)그 타입에 null 허용을 표시—String? name; 처럼 nullable 선언
?.앞이 null이면 호출 자체를 건너뜀O (null 반환 가능)user?.profile?.name 안전한 체이닝
??왼쪽이 null이면 오른쪽으로 대체X (기본값으로 메움)name ?? '손님' 기본값 제공
??=변수가 null일 때만 할당Xcache ??= load(); 지연 초기화
!"null 아님" 단언(검사 X)X (대신 틀리면 던짐)확실할 때만, 최소한으로

🔍 ? · ??를 쓸 때 vs 안 쓸 때 — 같은 "빈 값 처리"인데, 한쪽은 사용자 손에서 터지고 한쪽은 빌드 전에 막힙니다.

❌ ! 로 우격다짐 — 런타임에 폭발
final config = <String, String>{'host': 'api.io'};

// Map 조회는 String? (키 없으면 null)인데
// ! 로 "무조건 있다"고 우겨버림
String port = config['port']!;  // 컴파일은 통과!

// 💥 'port' 키가 없어 실제로는 null →
// Null check operator used on a
// null value (런타임 크래시)
print('포트: $port');
✅ ?. + ?? — 빈 값을 안전하게 흡수
final config = <String, String>{'host': 'api.io'};

// 없을 수 있음을 인정하고 기본값을 준비
String port = config['port'] ?? '8080';

// 체이닝도 ?. 로 중간 null을 자동 통과
int? hostLen = config['host']?.length;

// 키가 없어도 크래시 없이 '8080'
print('포트: $port');
차이: !는 "검사하지 말고 그냥 믿어"라는 뜻이라, 단언이 틀리면 그 줄에서 바로 앱이 죽습니다. 반면 ?.·??는 "null일 수도 있다"는 현실을 코드에 녹여 크래시 대신 기본값/통과로 흡수합니다. 실무 원칙: 외부에서 들어오는 값(JSON·Map·쿼리 결과·플랫폼 채널)은 거의 다 nullable로 보고 ?./??로 받으세요. !는 "바로 위에서 null 검사를 끝냈다"처럼 확실한 곳에만, 한 줄짜리로 씁니다.
함정 — ! 남용은 null safety를 무력화합니다: !를 습관처럼 붙이면 컴파일러의 보호를 스스로 꺼버리는 꼴이라, null safety 이전의 NPE 지옥으로 되돌아갑니다. 특히 a!.b!.c! 식 연쇄 단언은 "어디서 터졌는지"도 모호해 디버깅이 괴로워요. 값이 정말 있는지 모르면 if (x != null) { ... }로 좁히거나(이 블록 안에선 컴파일러가 x를 non-null로 승격해 줍니다), ?./??로 흘려보내세요. !는 "안전함을 내가 방금 증명했다"는 곳에서만 쓰는 예외 도구입니다.

🔧함수 — 화살표 · 명명/위치 파라미터 · 익명·클로저

개념: 함수는 "입력을 받아 결과를 돌려주는 작은 기계"입니다. Dart는 한 줄짜리 함수를 짧게 쓰는 화살표(=>), 인자를 이름으로 넘기는 명명 파라미터({}), 순서대로 넘기되 생략 가능한 선택 위치 파라미터([])를 제공합니다. 또 함수를 값처럼 변수에 담거나 콜백으로 넘길 수 있고(익명 함수), 바깥 변수를 기억하는 함수를 만들 수도 있어요(클로저). Flutter 위젯 생성자·이벤트 콜백·리스트 변환이 전부 이 문법 위에 서 있어, 손에 익히면 실전 코드가 크게 짧아집니다.

functions.dart
// ① 일반 함수 — 본문이 여러 줄이면 { } 와 return
int add(int a, int b) {
  return a + b;
}

// ② 화살표 함수 — 본문이 '단일 표현식'일 때만 (=> 식)
int square(int x) => x * x;

// ③ 명명 파라미터 {} — required는 필수, 나머지는 기본값/nullable
void greet({required String name, int age = 0}) {
  print('$name, $age살');
}
greet(name: '창한', age: 30); // 순서 무관, 이름으로 지정

// ④ 선택 위치 파라미터 [] — 순서대로, 생략 가능(nullable이거나 기본값)
String tag(String body, [String name = 'div']) => '<$name>$body';
tag('hi');          // '<div>hi' — name 생략
tag('hi', 'p');     // '<p>hi'

// ⑤ 익명 함수 — 이름 없이 값처럼 변수에 담거나 콜백으로 전달
final nums = <int>[1, 2, 3];
final evens = nums.where((n) => n.isEven).toList(); // [2]

// ⑥ 클로저 — 바깥 변수(count)를 '기억'하는 함수를 만들어 반환
int Function() makeCounter() {
  var count = 0;
  return () => ++count;   // count를 가둬(capture) 둠
}
final next = makeCounter();
print('${next()} ${next()}'); // 1 2 — 호출 사이에 상태 유지

🔍 명명 파라미터를 쓸 때 vs 안 쓸 때 — 위치로 넘기면 인자 순서를 사람이 외워야 하고, 명명으로 넘기면 컴파일러·IDE가 짝을 맞춰 줍니다.

❌ 위치 파라미터 — 순서 헷갈려 조용히 오작동

// width와 height를 바꿔 넣음
rect(0, 0, 200, 100); // 의도는 100×200?

// 💥 타입이 다 int라 컴파일은 통과 →
// 잘못된 크기로 그려져도 에러 없음
// (런타임에 눈으로 봐야 발견)
✅ 명명 파라미터 — 이름으로 짝이 명확
void rect({required int left,
           required int top,
           required int width,
           required int height}) {
  // ...
}

// 무엇이 무엇인지 호출부에서 바로 보임
rect(left: 0, top: 0,
     width: 100, height: 200);

// 이름을 빠뜨리면 컴파일 에러로 즉시 차단
차이: 위치 파라미터는 타입이 같은 인자가 여러 개일 때 순서를 바꿔 넣어도 컴파일러가 못 잡아, 화면을 봐야 아는 버그가 됩니다. 명명 파라미터는 left:·width:처럼 호출부에 의도가 그대로 드러나고, required를 빠뜨리면 빌드가 막히죠. 그래서 Flutter 위젯 생성자는 대부분 명명 파라미터를 씁니다. 실무 팁: 인자가 2개를 넘거나 같은 타입이 반복되면 망설이지 말고 명명 파라미터로 가세요. 콜백처럼 한 줄짜리 함수는 익명 함수를 =>로 짧게 쓰는 게 정석입니다.
React 개발자라면: 위젯 생성자의 {required this.title}는 컴포넌트에 props를 넘기는 것과 같습니다. 명명 파라미터 = props 객체로 생각하면 자연스러워요. 익명 함수 (n) => n.isEven는 JS 화살표 콜백과 동일하고, makeCounter 같은 클로저는 useState가 리렌더 사이에 값을 기억하는 것과 같은 "변수 가두기(capture)" 원리입니다.
함정 — {}와 []는 한 함수에 같이 못 씁니다: 명명 파라미터 그룹 {}와 선택 위치 파라미터 그룹 []는 한 함수 시그니처에 동시에 선언할 수 없어요(둘 중 하나만). 선택 인자가 필요하면 거의 항상 명명 파라미터를 고르는 게 안전합니다. 또 화살표 =>는 "단일 표현식" 전용이라 그 뒤에 if 문이나 여러 줄을 넣으면 컴파일 에러 — 이럴 땐 { } 본문으로 풀어 쓰세요.

🏗️클래스와 생성자 — 기본 / named / factory

개념: 클래스는 데이터(필드)와 동작(메서드)을 한 덩어리로 묶는 설계도이고, 생성자는 그 설계도로 실제 인스턴스를 찍어내는 출입구입니다. Dart는 같은 클래스에 출입구를 여러 개 둘 수 있어요 — 기본 생성자(unnamed), 이름표를 단 named 생성자, 그리고 인스턴스를 직접 골라 돌려주는 factory 생성자. 객체를 매번 새로 만들지(generative), 아니면 캐시·검증을 거쳐 돌려줄지(factory)를 골라야 할 때 이 구분이 결정적입니다.

user.dart
class User {
  // 필드 — final이면 생성 후 재할당 불가(불변 객체)
  final String name;
  final int age;

  // 기본(unnamed) 생성자 — this.name은 '초기화 형식 매개변수':
  // 받은 인자를 동명의 필드에 곧바로 꽂아줌(본문·: 없이 끝)
  User({required this.name, required this.age});

  // named 생성자 — '초기화 리스트'(: 필드 = 값)로 필드를 채움.
  // 여전히 generative(매번 새 인스턴스 생성), factory 아님
  User.guest() : name = '손님', age = 0;

  String describe() => '$name ($age)';
}

final u = User(name: '창한', age: 30); // 기본 생성자
final g = User.guest();                    // named 생성자
구분generative (기본·named)factory
인스턴스 생성항상 새로 만듦직접 만들지 않음 — 무엇을 돌려줄지 결정
return쓰지 않음(암묵적으로 새 객체)반드시 인스턴스를 return
캐시·기존 객체 재사용불가가능(캐시·싱글턴·하위타입 반환)
초기화 리스트(: x = ...)사용 가능사용 불가(본문에서 계산 후 return)
this 접근가능불가(아직 객체가 없음)

🔍 factory 쓸 때 vs 안 쓸 때 — 같은 색을 매번 새 객체로 찍어내며 검증 로직이 호출부마다 흩어지느냐, 캐시·검증을 생성자 안에 가두느냐의 차이.

❌ 안 쓰면 — 중복 인스턴스 + 검증 산재
class Color8 {
  final int r, g, b;
  Color8(this.r, this.g, this.b);
}

// 검증을 호출하는 쪽마다 직접 복붙해야 함
int clamp(int v) => v < 0 ? 0 : (v > 255 ? 255 : v);

// 같은 검정(0,0,0)을 부를 때마다 새 객체 생성
final a = Color8(clamp(0), clamp(0), clamp(0));
final b = Color8(clamp(0), clamp(0), clamp(0));
// 💥 identical(a, b) == false — 메모리 낭비 + 검증 깜빡 위험
✅ 쓰면 — 캐시 + 검증을 생성자에 캡슐화
class Color8 {
  final int r, g, b;

  // private generative 생성자(앞의 _) — factory만 호출
  Color8._(this.r, this.g, this.b);

  static final _cache = <int, Color8>{};

  // factory — 검증·캐시를 거쳐 인스턴스를 'return'
  factory Color8(int r, int g, int b) {
    int c(int v) => v.clamp(0, 255); // 검증 한곳
    final key = (c(r) << 16) | (c(g) << 8) | c(b);
    return _cache[key] ??= Color8._(c(r), c(g), c(b));
  }
}

final a = Color8(0, 0, 0);
final b = Color8(0, 0, 0);
// ✅ identical(a, b) == true — 같은 객체 재사용
차이: factory는 return 문으로 "무엇을 돌려줄지"를 직접 정하니, 캐시된 객체를 재사용하거나(??=) 검증을 한 곳에 모을 수 있습니다. 반면 generative 생성자는 호출될 때마다 무조건 새 객체를 만들죠. 실무에선 int.parse·DateTime.now 같은 표준 API, 그리고 JSON 역직렬화 factory User.fromJson(Map<String, dynamic> json) 패턴에서 factory를 끝없이 만납니다. 캡슐화 핵심은 검증·캐시 같은 "생성 정책"을 생성자 안에 가둬 호출부를 단순하게 유지하는 것.
함정: factory 안에서는 this를 쓸 수 없습니다 — 아직 객체가 만들어지기 전이라 가리킬 대상이 없거든요(필드 초기화는 generative 생성자나 초기화 리스트의 몫). 또 factory는 반드시 인스턴스를 return 해야 하고, generative 생성자는 반대로 return 문을 쓰지 않습니다.

📚컬렉션 리터럴 · cascade(..) · spread · collection-if/for · late

개념: 위젯 트리를 조립할 때 가장 자주 등장하는 문법 묶음입니다. List·Map·Set 리터럴로 데이터를 담고, spread(...)로 펼쳐 합치고, collection-if/for로 리스트 "안에서" 분기·반복하고, cascade(..)로 한 객체에 설정을 연쇄하고, late로 초기화를 잠시 미룹니다. 임시 변수와 삼항·.map().toList() 떡칠을 걷어내고 UI를 선언적으로 쓰게 해주는 도구들이에요.

collections.dart
// List / Map / Set 리터럴(앞에 <타입>으로 원소 타입 지정)
final nums = <int>[1, 2, 3];
final user = <String, dynamic>{'name': '창한', 'age': 30};
final tags = <String>{'a', 'a', 'b'};   // Set → {a, b} (중복 제거)

// ① spread(...) — 리스트를 펼쳐 합치기 / ...? 는 null이면 건너뜀
List<int>? extra;
final all = [0, ...nums, ...?extra, 4];      // [0, 1, 2, 3, 4]

// ② collection-if / for — children 리스트 안에서 바로 분기·반복
final isLoggedIn = true;
final widgets = [
  const Header(),
  if (isLoggedIn) const Profile(),       // 조건부 포함
  for (final n in nums) Item(n),         // 반복 생성
];

// ③ cascade(..) — 같은 객체에 연속 설정(..는 메서드 반환값이 아니라
//    '그 객체 자신'을 돌려줌 → 끝에서 paint를 그대로 받음)
final paint = Paint()
  ..color = Colors.red
  ..strokeWidth = 4;

// ④ late — 선언은 지금, 할당은 나중에(단, 사용 전엔 반드시)
late final AnimationController controller;   // initState에서 할당

🔍 cascade 쓸 때 vs 안 쓸 때 — 같은 객체를 가리키는 임시 변수를 줄줄이 반복하느냐, ..로 객체 이름 한 번에 연쇄하느냐.

❌ 안 쓰면 — 임시 변수 + 이름 반복
// 객체 이름(p)을 줄마다 다시 적어야 함
final p = Paint();
p.color = Colors.red;
p.strokeWidth = 4;
p.style = PaintingStyle.stroke;
// 한 줄만 다른 변수로 잘못 적어도 컴파일은 통과 → 버그 유발
✅ 쓰면 — .. 로 연쇄, 식 하나로
// 객체를 한 번만 적고 .. 로 연달아 설정
final p = Paint()
  ..color = Colors.red
  ..strokeWidth = 4
  ..style = PaintingStyle.stroke;
// 전체가 'p를 돌려주는' 하나의 식 → final 초기화에 바로 사용
차이: ..는 메서드/세터의 반환값을 무시하고 수신 객체 자신을 돌려줘서, 설정을 연쇄한 결과를 그대로 final p = ...에 담을 수 있습니다(임시 변수·재대입 불필요). 객체 이름을 한 번만 쓰니 "다른 변수에 잘못 설정"하는 실수도 원천 차단되죠. 참고로 한 단계가 null일 수 있으면 ?..(null-aware cascade)로 안전하게 건너뜁니다.

🔍 collection-if/for 쓸 때 vs 안 쓸 때 — 삼항과 .map().toList()·...로 떡칠하느냐, 리스트 리터럴 안에서 선언적으로 분기·반복하느냐.

❌ 안 쓰면 — 삼항 + map().toList() 중첩
final children = [
  const Header(),
  // 조건부 한 개: 삼항 + spread + 빈 리스트
  ...(isLoggedIn ? [const Profile()] : []),
  // 반복: map → toList → 다시 spread로 펼침
  ...nums.map((n) => Item(n)).toList(),
];
// 읽기 어렵고 빈 [] / toList() 같은 군더더기가 가득
✅ 쓰면 — if / for 를 리스트 안에 직접
final children = [
  const Header(),
  if (isLoggedIn) const Profile(),   // 분기
  for (final n in nums) Item(n),     // 반복
];
// 빈 [] · toList() 없이 의도가 그대로 드러남
차이: collection-if/for는 리스트를 만드는 과정 자체에 제어 흐름을 넣어, 중간 리스트([])나 .toList() 변환 없이 원소를 곧바로 끼워 넣습니다. Flutter의 children: [ ... ]를 선언적으로 읽히게 하는 핵심이라, 실무 위젯 코드의 가독성이 확 올라가요. late는 StatefulWidget의 AnimationController처럼 "생성자 시점엔 못 만들지만 build 전엔 반드시 채워질" 필드에 단골로 씁니다.
함정: late 변수를 할당하기 전에 읽으면 컴파일이 아니라 런타임에 터집니다(LateInitializationError). "사용 전 초기화"를 개발자가 책임진다는 약속이라, initState에서 빠짐없이 할당하세요. 또 collection-for는 for (final x in list)(요소 순회)와 for (var i = 0; i < n; i++)(C식) 둘 다 리터럴 안에서 쓸 수 있습니다.
React 매핑: spread ...는 JS 스프레드 그대로, collection-if/for는 JSX의 {cond && <X/>} / {arr.map(...)}를 언어 차원에서 더 깔끔하게 제공하는 셈입니다. cascade(..)는 JS엔 없는 Dart 고유 문법이고요.

🔁컬렉션 고차함수 — map · where · fold · any · every · firstWhere

개념: 리스트를 함수를 인자로 받아 변환·필터·집계하는 메서드들입니다. for 루프로 직접 돌리는 대신 "무엇을 할지"만 선언하면 되니, Flutter에서 데이터를 위젯 리스트로 바꾸거나(map) 조건에 맞는 항목만 추리는(where) 일을 한 줄로 끝냅니다. 모두 Iterable에 정의돼 있어 List·Set에서 똑같이 쓸 수 있어요.

higher_order.dart
// Flutter에서 매일 쓰는 6가지. 모두 Iterable에 정의돼 있습니다.
final nums = <int>[1, 2, 3, 4, 5];

// ① map — 각 요소를 변환해 새 Iterable 생성
final doubled = nums.map((n) => n * 2).toList();   // [2, 4, 6, 8, 10]

// ② where — 조건을 만족하는 요소만 거름
final evens = nums.where((n) => n.isEven).toList();  // [2, 4]

// ③ fold — 누적해 하나의 값으로 접기(초기값 0)
final sum = nums.fold<int>(0, (acc, n) => acc + n);  // 15

// ④ any / ⑤ every — 조건 검사 결과는 bool
final hasNeg = nums.any((n) => n < 0);    // false (하나라도 음수?)
final allPos = nums.every((n) => n > 0);  // true  (전부 양수?)

// ⑥ firstWhere — 조건에 맞는 첫 요소(없으면 orElse 반환)
final firstBig = nums.firstWhere((n) => n > 3, orElse: () => -1);  // 4
메서드받는 함수돌려주는 것한 줄 용도
map(e) => 새값Iterable<R>각 요소를 변환
where(e) => boolIterable<E>조건으로 필터링
fold(acc, e) => acc누적값 R하나의 값으로 집계(합·연결 등)
any(e) => boolbool하나라도 만족하나?
every(e) => boolbool전부 만족하나?
firstWhere(e) => bool요소 E조건 맞는 첫 요소(없으면 orElse, 그것도 없으면 예외)

🔍 고차함수 쓸 때 vs 안 쓸 때 — "거른다 → 바꾼다 → 더한다"는 의도가 코드에 그대로 보이느냐의 차이.

❌ 안 쓰면 — for 루프로 변환·필터·합산
// 임시 리스트와 인덱스 i가 산재 → 의도가 안 드러남
final prices = <int>[1000, 2000, 3000];
final result = <int>[];
for (var i = 0; i < prices.length; i++) {
  if (prices[i] >= 2000) {        // 2000원 이상만
    result.add(prices[i] ~/ 1000);  // 천원 단위로
  }
}
var total = 0;
for (var i = 0; i < result.length; i++) {
  total += result[i];                // 합산 로직이 또 따로
}
// result = [2, 3], total = 5
✅ 쓰면 — where·map·fold 체인 한 줄씩
// 의도가 그대로 읽힘: 거른다 → 바꾼다 → 접는다
final prices = <int>[1000, 2000, 3000];

final result = prices
    .where((p) => p >= 2000)   // 2000원 이상만
    .map((p) => p ~/ 1000)     // 천원 단위로
    .toList();                    // [2, 3]

final total = result.fold<int>(0, (acc, v) => acc + v);  // 5
차이: 두 코드의 결과는 [2, 3]·5로 똑같지만, 오른쪽은 임시 변수·인덱스·재할당이 0개라 "무엇을 하는 코드인지"가 메서드 이름에 그대로 드러납니다. 버그가 끼어들 틈(off-by-one, 빈 result 초기화 누락)도 사라지죠. 실무에선 이 체인이 곧 products.where(재고있음).map(상품카드).toList() 형태로 위젯 리스트를 만드는 데 그대로 쓰입니다.
함정 — lazy(지연 평가): map·where는 즉시 실행되지 않고 Iterable을 돌려줄 뿐입니다. 실제 변환은 순회할 때 일어나요. 그래서 children: list.map(...)처럼 List가 필요한 자리(위젯 children, ListView 등)에선 끝에 .toList()를 붙여 materialize해야 합니다. 반대로 fold·any·every·firstWhere는 값을 바로 돌려주니 .toList()가 필요 없습니다. 또 firstWhere는 조건에 맞는 게 하나도 없고 orElse도 안 주면 StateError 예외를 던지므로, 없을 수 있는 상황이면 orElse를 꼭 지정하세요.
React/JS 매핑: map≈Array.map, where≈filter, fold≈reduce, any≈some, every≈every, firstWhere≈find. 단 JS의 map은 곧바로 배열을 주지만 Dart는 lazy Iterable이라 .toList()가 추가로 필요한 점이 핵심 차이입니다.

🧬제네릭 — <T>로 타입 안전 재사용

개념: 제네릭(Generics)은 "타입을 나중에 채워 넣는 빈칸 <T>"입니다. 같은 자료구조·로직을 int, String, User 등 어떤 타입에도 재사용하되, 그 타입 정보를 컴파일 단계까지 그대로 유지하는 게 목적이에요. List<int>의 <int>가 바로 그 빈칸을 채운 모습입니다. 덕분에 "담을 때의 타입"과 "꺼낼 때의 타입"이 어긋나는 사고를 IDE가 빨간 줄로 막아줍니다.

generics.dart
// ① 컬렉션의 타입 빈칸 — 가장 자주 보는 제네릭

🏷️enum — 특히 enhanced enum

개념: enum은 "정해진 값들의 집합"을 하나의 타입으로 만드는 문법입니다(요일·등급·상태 등). 문자열 상수와 달리 오타가 컴파일 단계에서 막히고, switch 망라성도 검사돼요. Dart 2.17+의 enhanced enum은 여기서 한발 더 나아가, 각 값에 필드와 메서드를 묶을 수 있습니다 — 즉 "이 값에 딸린 색·라벨·동작"을 enum 안에 캡슐화해, 여기저기 흩어진 switch 분기를 통째로 없앱니다.

enum_basic.dart
// 기본 enum — 값들의 집합. 오타 불가, switch 망라성 체크 가능
enum Direction { north, east, south, west }

// 모든 enum이 공짜로 갖는 멤버들
const d = Direction.north;
print(d.name);                  // 'north'  (값의 이름 문자열)
print(d.index);                 // 0        (선언 순서)
print(Direction.values.length); // 4        (전체 값 리스트)

① enhanced enum — 값에 필드·메서드를 묶기 (Dart 2.17+)

각 값이 생성자 인자를 받아 필드를 채우고, enum 본문에 메서드·게터를 둘 수 있습니다. 생성자는 반드시 const여야 하고, this.x(초기화 형식 매개변수)로 필드를 채웁니다.

enum_enhanced.dart
// enhanced enum: 각 값에 색·라벨·적립률을 묶는다
enum Grade {
  bronze(0xFFCD7F32, '브론즈', 1.0),   // 각 값이 생성자 인자를 가짐
  silver(0xFFC0C0C0, '실버', 1.2),
  gold(0xFFFFD700, '골드', 1.5);   // 마지막 값 뒤 ; 필수(메서드 선언 시작)

  // 반드시 const 생성자 — this.x(초기화 형식 매개변수)로 필드 채움
  const Grade(this.colorValue, this.label, this.pointRate);

  final int colorValue;
  final String label;
  final double pointRate;

  // 메서드·게터도 가질 수 있다 → 데이터와 로직을 한곳에
  int pointsFor(int amount) => (amount * pointRate).round();
  bool get isPremium => pointRate >= 1.5;
}

// 사용: 값 + 데이터 + 동작이 전부 Grade 안에 캡슐화됨
final pts = Grade.gold.pointsFor(10000);  // 15000
print(Grade.gold.label);                  // '골드'
print(Grade.gold.isPremium);              // true

각 값에 데이터(필드)없음(이름만)필드+생성자로 부착(색·라벨·수치 등)
인자 받는 생성자없음(암묵 const)값마다 const 생성자 인자
메서드·게터·implements멤버가 없을 뿐, 붙이면 가능자유롭게 추가(pointsFor·isPremium 등)

🔍 enhanced enum 쓸 때 vs 안 쓸 때 — 값에 딸린 데이터가 한곳에 모이느냐, switch로 사방에 흩어지느냐의 차이.

❌ 안 쓰면 — String 상수 + switch 산재
// 색·라벨·적립률이 String + switch로 사방에 흩어짐
const tier = 'gold';  // 오타 나도 컴파일 통과 → 런타임 버그

int colorOf(String t) {
  switch (t) {
    case 'bronze': return 0xFFCD7F32;
    case 'silver': return 0xFFC0C0C0;
    case 'gold':   return 0xFFFFD700;
    default:       return 0xFF000000;
  }
}

// 라벨용·적립률용 switch가 또 따로… 같은 분기가 곳곳에 복제
// String labelOf(String t) { ...라벨용 switch가 또... }
// int rewardOf(String t) { ...적립률용 switch가 또... }
// → 같은 'tier' 분기가 색·라벨·적립률마다 복제됨
✅ 쓰면 — enum에 필드로 캡슐화
// 색·라벨·적립률을 enum 필드로 — 분기 없이 점 하나로 꺼냄
enum Grade {
  bronze(0xFFCD7F32, '브론즈', 1.0),
  silver(0xFFC0C0C0, '실버', 1.2),
  gold(0xFFFFD700, '골드', 1.5);
  const Grade(this.color, this.label, this.rate);
  final int color;
  final String label;
  final double rate;
}

// 호출부: switch 0개. 새 등급도 enum 한 곳만 고치면 끝
final g = Grade.gold;
print(g.color);  // 0xFFFFD700
print(g.label);  // '골드'
차이: 왼쪽은 색·라벨·적립률마다 switch가 따로라 같은 분기가 복제되고, 'gold' 오타는 런타임에야 터집니다. 오른쪽은 데이터가 Grade 한 곳에 모여 g.color·g.label로 바로 꺼내고, 새 등급(platinum) 추가도 enum에 한 줄만 더하면 끝입니다. 실무 팁: switch (grade) { ... }를 자주 쓰게 된다면, 그 분기 로직을 enum의 메서드·게터로 끌어올릴 신호예요. 단, 화면 표시 문자열은 다국어(i18n)가 필요하면 enum 필드에 한국어를 박기보다 라벨 키만 두고 번역 레이어에서 매핑하는 편이 낫습니다.
예상 꼬리질문: "enum과 sealed class, 언제 뭘 쓰나요?" → "케이스가 유한·고정이고 각 케이스가 같은 모양의 데이터(필드)만 가지면 enhanced enum이 간결합니다. 반대로 케이스마다 담는 데이터의 종류가 다르면(예: Success는 데이터, Failure는 에러 메시지) sealed class가 적합해요. 둘 다 switch 망라성을 컴파일러가 보장한다는 공통점이 있습니다."
React/TS 매핑: 기본 enum ≈ TS enum/유니온 리터럴, enhanced enum ≈ 값마다 메타데이터를 든 as const 객체 맵 + 메서드를 언어 차원에서 타입 안전하게 묶은 형태입니다.

🧩extension — 기존 타입에 메서드 추가

개념: extension은 내가 고칠 수 없는 남의 타입(String·int·SDK 클래스 등)에 메서드·게터를 덧붙이는 문법입니다. 소스를 상속하거나 수정하지 않고도 'hi'.capitalized처럼 그 타입의 원래 기능인 것처럼 호출할 수 있어요. 자주 쓰는 유틸을 capitalize(s) 같은 자유 함수로 흩어 두면 발견이 어려운데, 확장으로 묶으면 점(.) 자동완성에 바로 떠서 찾을 필요가 없어집니다.

extension_basics.dart
// String에 기능을 '확장' — on 뒤에 대상 타입을 적는다
extension StringCasing on String {
  // 게터: 첫 글자만 대문자로
  String get capitalized =>
      isEmpty ? this : '${this[0].toUpperCase()}${substring(1)}';

  // 메서드도 가능 — this 는 확장 대상(여기선 String)
  bool isPhone() => RegExp(r'^\d{2,3}-\d{3,4}-\d{4}$').hasMatch(this);
}

// 마치 String이 원래 갖고 있던 멤버처럼 호출 → '.' 자동완성에 뜬다
print('hi'.capitalized);          // Hi
print('010-1234-5678'.isPhone()); // true

멤버 결정그 이름의 함수 하나로 정적 바인딩(오버라이드 없음)정적 — 변수의 정적 타입으로 결정(런타임 타입 무시)

❌ 안 쓰면 — 유틸 함수가 흩어져 발견이 어려움
// 어딘가 util.dart 에 박혀 있는 자유 함수

    s.isEmpty ? s : '${s[0].toUpperCase()}${s.substring(1)}';

// 호출부: 함수 이름·위치를 외워서 import 해야 한다
// 'hi'. 까지 쳐도 자동완성엔 절대 안 뜸
final title = capitalize(name);
// 중첩되면 안에서 바깥으로 읽혀 더 장황:
final t2 = capitalize(name.trim());
✅ 쓰면 — 타입에 붙어 자동완성에 등장
// 한 번 정의해 두면 String 전체가 능력을 얻는다
extension Cap on String {
  String get capitalized =>
      isEmpty ? this : '${this[0].toUpperCase()}${substring(1)}';
}

// 호출부: name. 만 찍어도 capitalized 가 보인다
final title = name.capitalized;
// 체이닝이 왼→오로 자연스럽게 읽힘
final t2 = name.trim().capitalized;
차이: 두 코드의 로직은 같지만, 확장은 기능을 타입 위에 얹어 IDE 자동완성·체이닝으로 끌어올립니다. 함수 이름을 기억하거나 어느 파일에 있는지 찾을 필요가 없어요. 실무 팁 — 확장은 import한 파일 범위에서만 보이므로 extensions/string_x.dart처럼 모아 두고, 충돌이 나면 StringCasing('hi').capitalized로 확장 이름을 명시해 해소합니다. 단, 확장은 필드(상태)를 추가할 수 없고 게터·메서드만 가능합니다.
함정 ① 정적 디스패치: 확장 메서드는 변수의 정적 타입으로 고른다 — 다형성이 아닙니다. Object o = 'hi'; o.capitalized;는 컴파일 에러예요(Object엔 확장이 없음). 런타임 타입이 String이어도 소용없습니다. 함정 ② null 확장: on String 확장은 String? 값엔 안 붙습니다. nullable에 쓰려면 extension on String?로 따로 선언하고 본문에서 this == null을 직접 처리하세요(이때만 null에서 메서드 호출이 안전합니다).

🧬mixin — with로 기능 조합

개념: mixin은 여러 클래스가 공유할 기능 묶음을 한 곳에 정의해 두고, with로 끼워 넣는 문법입니다. Dart는 클래스 다중 상속을 금지하는데, mixin이 그 빈자리를 메워 코드 재사용을 가능하게 해요. 같은 메서드를 클래스마다 복붙하는 대신 mixin 하나로 모으고, 필요한 클래스에 with로 조합합니다. Flutter의 SingleTickerProviderStateMixin(애니메이션 ticker 제공)이 대표적인 예입니다.

mixin_basics.dart
// 재사용할 기능 묶음을 mixin으로 정의(직접 인스턴스화 X)
mixin Swimmer {
  void swim() => print('헤엄친다');
}
mixin Walker {
  void walk() => print('걷는다');
}

// with로 두 기능을 한 클래스에 조합 — 다중 상속의 대체
class Duck with Swimmer, Walker {}

final duck = Duck();
duck.swim(); // 헤엄친다  ← Swimmer에서 옴
duck.walk(); // 걷는다    ← Walker에서 옴

// on으로 적용 대상을 제한할 수도 있다(이 mixin은 Animal에만 with 가능)
class Animal {}
mixin Logger on Animal {
  void log() => print('[$runtimeType]'); // Animal 멤버 접근 가능
}

🔍 같은 기능을 복붙할 때 vs mixin으로 조합할 때 — 헤엄 기능을 클래스마다 똑같이 적느냐, 한 번 정의해 with로 나눠 쓰느냐.

❌ 안 쓰면 — 같은 코드를 클래스마다 복붙

class Fish  with Swimmer {}
class Otter with Swimmer {}
// ✅ swim 규칙은 mixin 한 곳만 고치면 전부 반영
차이: 복붙은 같은 코드를 N벌로 늘려 수정 시 누락·불일치를 부르지만, mixin은 단일 출처(single source)라 한 곳만 고치면 끝입니다. 상속과 달리 with는 여러 개를 조합할 수 있어 "수직 계층"이 아닌 "수평 기능 단위"로 재사용해요. 실무 팁 — 여러 mixin이 같은 이름 메서드를 가지면 with A, B에서 뒤쪽(B)이 이김(선형화 순서). 충돌을 피하려면 mixin마다 책임을 좁게 나누세요.

함정: with는 구현까지 가져오지만 implements는 시그니처만 강제합니다 — class X implements Swimmer {}는 swim()을 직접 작성하지 않으면 컴파일 에러예요. 또 mixin은 생성자를 가질 수 없습니다(상태 초기화가 필요하면 late 필드나 on으로 제한한 상위 타입의 생성자에 맡기세요). 순서도 중요 — extends A with B, C는 "A → B → C" 순으로 쌓여, 같은 멤버는 가장 오른쪽이 최종 우선합니다.

🏷️typedef — 복잡한 타입에 이름 붙이기

개념: typedef는 길고 반복되는 타입에 별명(alias)을 붙이는 도구입니다. 특히 void Function(int, String) 같은 함수 타입은 콜백 인자로 여기저기 등장하는데, 매번 풀어 쓰면 길고 한 글자만 틀려도 안 맞아요. 이름을 한 번 정해 두면 의미가 드러나고, 시그니처가 바뀔 때 정의 한 곳만 고치면 됩니다.

typedef.dart
// ① 함수 타입에 이름 붙이기 (가장 흔한 용도)
typedef IntCallback = void Function(int value);

// 이제 콜백 인자를 짧고 의미 있게 선언
void onTapEach(List<int> ids, IntCallback handler) {
  for (final id in ids) handler(id);
}

onTapEach([1, 2, 3], (id) => print('tap $id'));

// ② 반환값·명명 파라미터가 있는 함수 타입도 OK
typedef Validator = String? Function(String input);

String? notEmpty(String v) => v.isEmpty ? '필수 항목' : null;
Validator rule = notEmpty;        // 타입이 정확히 일치

// ③ 일반 타입의 별명 (제네릭 포함)
typedef Json = Map<String, dynamic>;
Json user = {'name': '창한', 'age': 30};  // Map<String, dynamic> 그대로

🔍 typedef 쓸 때 vs 안 쓸 때 — 같은 함수 타입을 매번 풀어 쓰는 대신, 이름 한 번으로 의미를 드러내고 변경을 한 곳에 모읍니다.

❌ 안 쓰면 — 긴 타입을 곳곳에 반복
// 같은 시그니처를 매번 풀어 씀
void register(
    void Function(int a, String b) cb) {}

void remove(
    void Function(int a, String b) cb) {}

List<void Function(int, String)> all = [];

// 시그니처에 매개변수 하나 추가하면
// 위 세 곳을 전부 손으로 고쳐야 함(누락 위험)
✅ 쓰면 — 이름 한 번, 변경도 한 곳
// 한 번만 정의
typedef Listener =
    void Function(int a, String b);

void register(Listener cb) {}
void remove(Listener cb) {}
List<Listener> all = [];

// 시그니처 변경은 typedef 한 줄만 수정
// → 쓰는 곳 전부 자동 반영
차이: ❌는 같은 함수 타입이 세 군데 흩어져, 인자 하나만 바뀌어도 모두 찾아 고쳐야 하고 한 곳만 빠뜨리면 타입 불일치가 납니다. ✅는 Listener라는 이름 자체가 의도를 설명하고, 정의 한 줄만 바꾸면 사용처가 전부 따라옵니다. 실무 팁: 콜백·검증 함수·이벤트 핸들러처럼 "같은 모양의 함수"가 반복되면 typedef가 제격이에요. 다만 단순 타입의 별명(typedef Json = ...)은 가독성에 도움이 될 때만 쓰고 남발하지 마세요 — 원래 타입이 가려질 수 있습니다.
참고: Dart 2.13+부터 typedef는 함수 타입뿐 아니라 일반 타입의 별명으로도 쓸 수 있습니다(위 Json 예). Flutter 콜백 이름인 ValueChanged<T>, VoidCallback도 실은 프레임워크가 정의해 둔 typedef예요.

🆕Dart 3 — 보일러플레이트를 줄이는 최신 문법

Dart 3(2023~)부터 표준이 된 기능들입니다. 핵심 목적은 두 가지 — 여러 값을 가볍게 다루기(records·패턴 매칭)와 상태를 타입으로 안전하게 모델링하기(switch 표현식·sealed class)예요. 예전이라면 클래스를 따로 만들거나 if-else를 길게 늘어놓던 코드가 한두 줄로 줄고, 빠뜨린 경우(case)를 컴파일러가 대신 잡아줍니다. 면접에서 "최신 Dart 아세요?"라는 질문에 구체적 예시로 답할 수 있도록 네 가지를 정리했습니다.

① records — 여러 값 가볍게 묶기

개념: record(레코드)는 여러 값을 클래스 선언 없이 하나로 묶는 익명 타입입니다. 함수가 두세 개의 값을 한꺼번에 돌려줘야 하는데 그것만을 위한 클래스를 만들기는 번거로울 때 씁니다. 필드에 순서로 접근하는 위치 기반(.$1, .$2)과 이름으로 접근하는 이름 기반((code: 200, msg: 'OK')) 두 형태가 있어요.

records.dart
// 위치 기반 record — 필드 순서대로 .$1, .$2 로 접근
(double, double) center() => (12.5, 8.0);
final c = center();
print('${c.$1}, ${c.$2}');     // 12.5, 8.0

// 이름 기반 record — 필드에 이름을 붙여 가독성↑
({int code, String msg}) status() => (code: 200, msg: 'OK');
final s = status();
print('${s.code} ${s.msg}');   // 200 OK

🔍 record 쓸 때 vs 안 쓸 때 — "두 값을 반환"하려고 전용 클래스를 만드느냐, 그 자리에서 묶어 돌려주느냐의 차이.

❌ 안 쓰면 — 일회용 클래스를 따로 선언
// 좌표 두 개 반환하려고 클래스를 통째로 만듦
class Point {
  final double x, y;
  Point(this.x, this.y);
}

Point center() => Point(12.5, 8.0);
// 이 함수 하나 때문에 타입 정의·파일이 늘어남
✅ 쓰면 — record로 즉시 묶어 반환
// 선언 없이 그 자리에서 두 값을 묶음
(double, double) center() => (12.5, 8.0);

final (x, y) = center();   // 구조분해까지 한 줄
print('$x, $y');            // 12.5, 8.0
차이: 전용 클래스는 "이 값들에 행동(메서드)·정체성을 부여하고 여러 곳에서 재사용"할 때 가치가 있습니다. 단지 함수가 값 몇 개를 한 번 돌려주는 용도라면 record가 군더더기를 없애요. 실무에서는 위젯 크기 (w, h), 페이징 결과 (items, hasMore)처럼 "이 함수만을 위한 일회용 묶음"에 record를 쓰고, 도메인 모델이 되면 클래스로 승격하는 식으로 나눕니다.
실전: record는 불변이고 필드 값이 모두 같으면 ==가 true입니다(값 동등성). 그래서 "여러 값을 키로 쓰고 싶을 때"나 비교가 필요한 임시 묶음에 특히 편합니다.

② 패턴 매칭 · 구조분해

개념: 패턴(pattern)은 값의 "모양"을 검사하면서 동시에 내부 값을 꺼내는 문법입니다. record·리스트·맵을 한 줄로 분해해 변수에 꽂고(구조분해, destructuring), switch에서는 JSON 같은 데이터의 형태별로 분기까지 합니다. JS의 구조분해와 발상은 같되, 타입을 붙인 변수 패턴(final num r)으로 꺼낸 값의 타입까지 좁혀준다는 점이 강력해요.

patterns.dart
// record · 리스트 구조분해 — 한 줄로 여러 변수에 분해
final (id, name) = (1, '창한');
final [first, _, third] = [10, 20, 30];  // _ 는 무시(건너뜀)

// 맵 패턴 + switch 표현식 — JSON 모양 그대로 분기
final Map<String, dynamic> json = {'type': 'circle', 'r': 4};
final area = switch (json) {
  // 값에 num 타입을 붙이면 r 이 num 으로 타입되고, num 일 때만 이 가지가 매칭
  {'type': 'circle', 'r': final num r} => 3.14 * r * r,
  {'type': 'square', 'a': final num a} => a * a,
  _ => 0,                // 그 외 모양은 0
};

🔍 패턴 쓸 때 vs 안 쓸 때 — 중첩 if + 수동 캐스팅이냐, 형태 검사·추출을 패턴 한 줄로 합치느냐의 차이.

❌ 안 쓰면 — 중첩 if + 수동 as 캐스팅
double areaOf(Map<String, dynamic> j) {
  if (j['type'] == 'circle') {
    // as 로 직접 캐스팅 — 틀리면 런타임에 터짐
    final r = j['r'] as num;
    return 3.14 * r * r;
  } else if (j['type'] == 'square') {
    final a = j['a'] as num;
    return (a * a).toDouble();
  }
  return 0;
}
✅ 쓰면 — 패턴으로 형태 검사·추출 동시에
double areaOf(Map<String, dynamic> j) => switch (j) {
  // 키 존재·값 타입 검사 + r 추출이 한 줄에
  {'type': 'circle', 'r': final num r} => 3.14 * r * r,
  {'type': 'square', 'a': final num a} => (a * a).toDouble(),
  _ => 0,
};
차이: 왼쪽은 "키가 있나? → 값을 꺼내 → 타입을 캐스팅"을 사람이 일일이 나눠 쓰고, as가 틀리면 런타임에서야 터집니다. 오른쪽 맵 패턴은 키 존재·값 타입 매칭·변수 바인딩을 한 번에 처리해, 매칭에 성공한 가지에서는 r이 이미 num으로 타입돼 있고, r이 숫자가 아니면 이 가지는 매칭되지 않고 다음 case로 넘어갑니다. 실무 팁: final num r처럼 타입을 붙이면 그 타입일 때만 매칭되는 런타임 타입 검사가 함께 걸립니다. 반면 final r처럼 타입을 빼면 맵이 Map<String, dynamic>이라 r이 dynamic으로 잡혀 타입 검사 없이 무엇이든 통과하므로, 잘못된 값이 들어와도 런타임에서야 터집니다. 꺼내 쓸 값에는 타입을 적는 습관을 들이세요.
함정: 리스트 패턴 [a, b, c]는 길이가 정확히 3일 때만 매칭됩니다. 길이가 다르면 그 가지를 건너뛰니(switch면 다음 case로), 가변 길이는 [first, ...rest]처럼 rest 패턴(...)을 써야 해요. 또 구조분해 변수로 _를 쓰면 "안 쓰는 값"을 명시적으로 버리는 의미입니다.

③ switch 표현식 — 값을 돌려주는 switch

개념: 기존 switch가 "문장(statement)"이라 case·break로 동작을 수행했다면, switch 표현식(expression)은 각 가지가 =>로 값을 반환합니다. break가 없고 가지를 ,로 구분하며, 결과를 바로 변수에 대입하거나 함수에서 돌려줄 수 있어요. 상태에 따라 위젯·문자열을 "고르는" 코드에서 특히 깔끔합니다.

switch_expr.dart
enum Status { loading, success, error }

// 상태 → 라벨. 모든 가지가 String 값을 반환
String label(Status s) => switch (s) {
  Status.loading => '불러오는 중…',
  Status.success => '완료',
  Status.error   => '오류',
};

// 관계 패턴(>=, <)으로 값의 범위에 따라 분기
String grade(int score) => switch (score) {
  >= 90 => 'A',
  >= 80 => 'B',
  _    => 'C',
};

🔍 switch 표현식 쓸 때 vs 안 쓸 때 — 장황한 if-else 체인으로 변수를 채우느냐, 한 표현식으로 값을 곧장 반환하느냐의 차이.

❌ 안 쓰면 — if-else 체인 + 가변 변수
String label(Status s) {
  // late + 분기마다 재대입 — 누락하면 미초기화 위험
  late String text;
  if (s == Status.loading) {
    text = '불러오는 중…';
  } else if (s == Status.success) {
    text = '완료';
  } else {
    text = '오류';
  }
  return text;
}
✅ 쓰면 — switch 표현식으로 곧장 반환
String label(Status s) => switch (s) {
  Status.loading => '불러오는 중…',
  Status.success => '완료',
  Status.error   => '오류',
};
// 가변 변수·break 없음 → 분기 누락을 컴파일러가 점검
차이: if-else 체인은 임시 변수를 만들고 분기마다 대입해야 해서, 한 갈래를 빠뜨리면 값이 안 채워질 수 있습니다. switch 표현식은 "입력 → 값" 매핑이 한눈에 들어오고, enum·sealed처럼 경우가 유한한 대상에선 한 가지라도 빠뜨리면 컴파일 오류로 막아줍니다(default _ 없이 썼을 때). 실무 팁: 위젯을 고를 때 삼항(? :)을 중첩하지 말고 child: switch (state) { ... }로 쓰면 가독성이 크게 올라가요. 범위 분기는 >= 90 같은 관계 패턴으로 처리합니다.
팁: 표현식이므로 final msg = switch (...) { ... };처럼 곧바로 대입하거나, build()의 return 자리에 그대로 넣을 수 있습니다. 마지막 _ => ...는 "그 외 전부"를 받는 와일드카드입니다.

④ sealed class — 망라성 보장

개념: sealed는 클래스의 하위 타입을 "같은 라이브러리(보통 한 파일) 안의 것들로 봉인"하는 키워드입니다. 컴파일러가 가능한 하위 타입 전체를 알게 되므로, switch에서 한 경우라도 빠뜨리면 컴파일 에러가 납니다. 화면 상태(로딩·성공·에러)를 타입으로 모델링하면, 나중에 상태를 하나 추가했을 때 "처리 안 한 곳"을 컴파일러가 전부 찾아줘 누락을 원천 차단해요.

sealed.dart
// 하위 타입을 봉인 — 외부에서 임의 상속 불가
sealed class Result {}
class Loading extends Result {}
class Success extends Result { final String data; Success(this.data); }
class Failure extends Result { final String err; Failure(this.err); }

// 객체 패턴으로 분기 + 필드 구조분해. default(_)가 없어도 OK
String render(Result r) => switch (r) {
  Loading()             => '불러오는 중…',
  Success(:final data) => data,        // data 필드를 바로 추출
  Failure(:final err)  => '에러: $err',
};

🔍 sealed 쓸 때 vs 안 쓸 때 — 새 상태를 추가했을 때 누락이 런타임에 조용히 새는가, 컴파일이 막아주는가의 차이.

❌ 안 쓰면 — 일반 class + default로 누락이 샘
// 봉인 없음 → 컴파일러가 전체 경우를 모름
class Result {}
class Loading extends Result {}
class Success extends Result {}
class Failure extends Result {}

String render(Result r) => switch (r) {
  Loading() => '불러오는 중…',
  Success() => '완료',
  // 새 상태 Failure 를 깜빡 → _ 가 조용히 삼킴
  _ => '알 수 없음',
};
✅ 쓰면 — sealed로 컴파일이 누락을 강제
sealed class Result {}
class Loading extends Result {}
class Success extends Result {}
class Failure extends Result {}

// _ 없이 모든 타입을 나열. Failure 빼면 컴파일 에러!
String render(Result r) => switch (r) {
  Loading() => '불러오는 중…',
  Success() => '완료',
  Failure() => '오류',
};
차이: 왼쪽은 Result가 평범한 클래스라 컴파일러가 "하위 타입이 몇 개인지" 모릅니다. 그래서 _(default)를 넣게 되고, 나중에 Failure 같은 새 상태가 추가돼도 처리 누락이 _로 조용히 흘러가 버그가 됩니다. 오른쪽 sealed는 하위 타입이 봉인돼 있어 _ 없이 전부 나열할 수 있고, 하나라도 빠지면 컴파일이 거부합니다. 실무 팁: 상태를 새로 추가하면 컴파일 에러가 "여기도, 저기도 처리해"라며 모든 switch를 가리켜 주니, 리팩터링이 안전해집니다. 그래서 default(_)를 일부러 쓰지 않는 것이 핵심이에요.
예상 꼬리질문: "상태 관리에서 sealed class가 왜 좋나요?" → "로딩·성공·에러를 sealed로 모델링하면 switch 망라성을 컴파일러가 강제해, 새 상태를 추가했을 때 처리 누락을 컴파일 단계에서 잡아줍니다. default로 뭉뚱그리지 않으니 UI가 모든 상태를 반드시 다루게 되죠. Riverpod의 AsyncValue(data·loading·error)도 같은 발상입니다."
React/TS 매핑: sealed class + 망라적 switch는 TypeScript의 판별 유니온(discriminated union)을 never로 exhaustive 체크하는 패턴과 같습니다. type Result = Loading | Success | Failure를 switch로 좁히고, 빠진 경우를 never 할당으로 컴파일 타임에 잡는 그 기법을, Dart는 언어 차원에서 기본 제공하는 셈이에요.

⏳비동기 첫걸음 — Future · async · await

개념: 네트워크 요청·파일 읽기처럼 "결과가 나중에 오는" 작업은 즉시 값을 줄 수 없습니다. 그 "나중에 올 값의 약속"이 Future이고, async/await는 그 약속이 풀릴 때까지 기다린 결과를 마치 동기 코드처럼 받아 쓰게 해 줍니다. 기다리는 동안 UI가 멈추지 않도록(스레드를 막지 않도록) 해 주는 게 핵심이에요. 여기서는 맛보기만 보고, 깊은 내용은 뒤 비동기 섹션에서 다룹니다.

async_intro.dart
// Future<T> → "나중에 T 타입 값을 주겠다"는 약속
Future<String> fetchUser() async {
  // 서버 호출을 흉내 (2초 뒤 응답)
  await Future.delayed(Duration(seconds: 2));
  return '창한';
}

// async 함수 안에서 await → 결과를 동기처럼 받음
Future<void> main() async {
  print('불러오는 중…');
  String name = await fetchUser();  // 여기서 2초 기다림(UI는 안 멈춤)
  print('안녕, $name');            // 결과가 온 뒤 실행

  // 실패할 수 있으면 try/catch로 감쌈
  try {
    final u = await fetchUser();
    print('ok: $u');
  } catch (e) {
    print('에러: $e');
  }
}
키워드역할
Future<T>나중에 도착할 T 값(또는 에러)을 담는 약속 객체
async이 함수 안에서 await를 쓰겠다는 표시(반환은 자동으로 Future)
awaitFuture가 풀릴 때까지 기다렸다가 알맹이 값을 꺼냄

🔍 async/await 쓸 때 vs 안 쓸 때 — .then() 콜백을 중첩하면 단계가 깊어질수록 읽기 어려운 "콜백 지옥", async/await는 위에서 아래로 읽히는 동기 코드 모양이 됩니다.

❌ 안 쓰면 — then 중첩(콜백 지옥)
// 단계마다 콜백 안으로 들어가 우측으로 밀림
fetchUser().then((name) {
  fetchPosts(name).then((posts) {
    fetchComments(posts).then((c) {
      print(c);          // 본문이 3겹 안쪽
    }).catchError((e) {
      print('에러: $e');  // 에러 처리도 흩어짐
    });
  });
});
// 순서·에러 흐름이 한눈에 안 들어옴
✅ 쓰면 — async/await로 평탄하게
Future<void> load() async {
  try {
    final name  = await fetchUser();
    final posts = await fetchPosts(name);
    final c     = await fetchComments(posts);
    print(c);              // 위→아래로 그대로 읽힘
  } catch (e) {
    print('에러: $e');      // 한 곳에서 일괄 처리
  }
}
차이: ❌의 .then() 중첩은 단계가 늘수록 들여쓰기가 오른쪽으로 밀리고 에러 처리(catchError)가 곳곳에 흩어져, 실행 순서를 따라가기 어렵습니다. ✅는 await 한 줄씩 위에서 아래로 읽히고, try/catch 하나로 모든 단계의 에러를 모아 잡아요. 실무 팁: 서로 의존하지 않는 작업은 굳이 줄줄이 await 하지 말고 await Future.wait([a(), b()])로 동시에 기다리면 더 빠릅니다.
더 자세히는 뒤 '비동기' 섹션에서: 여기서는 Future·async·await 맛보기만 봤습니다. 여러 값이 시간차로 흘러오는 Stream, UI에 비동기 결과를 꽂는 FutureBuilder/StreamBuilder, 그리고 "한 줄 한 줄 어떤 순서로 실행되는가"(이벤트 루프)는 뒤 비동기 처리 섹션에서 깊이 다룹니다.

레이아웃 — Row · Column · Flex

part 1 · 기초

Flutter 레이아웃의 90%는 Row와 Column. CSS Flexbox를 알면 직관적입니다.

주축(main) vs 교차축(cross)

Row는 가로가 주축, Column은 세로가 주축입니다. 정렬은 두 축으로 따로 지정해요.

layout.dart
Row(
  // 주축(가로) 정렬: 양끝+가운데 균등 배치
  mainAxisAlignment: MainAxisAlignment.spaceBetween,
  // 교차축(세로) 정렬: 가운데
  crossAxisAlignment: CrossAxisAlignment.center,
  children: [
    Icon(Icons.star),
    // Expanded → 남는 공간 다 차지 (flex:1)
    Expanded(child: Text('제목')),
    Icon(Icons.more_vert),
  ],
)
Expanded / Flexible: 남는 공간을 비율대로 나눠 가질 때 씁니다. CSS의 flex-grow와 같아요. Expanded는 꽉 채우고, Flexible은 필요한 만큼만.
면접 빈출 — RenderFlex overflow: Row 안에 긴 Text를 넣으면 화면 밖으로 넘쳐 노란/검정 줄무늬 에러가 납니다. 원인은 "무한 너비 경쟁". 해결은 넘치는 위젯을 Expanded나 Flexible로 감싸기. 실무 단골 이슈라 자주 물어봅니다.

Stateless vs Stateful

part 1 · 기초

위젯의 가장 근본적인 분류. "스스로 변하는 상태를 가지느냐"가 기준입니다.

🖼️ 일상 비유 — 인쇄된 사진 vs 화이트보드: Stateless는 인쇄된 사진입니다. 한 번 인화되면 내용이 바뀌지 않아요(이름표, 로고). Stateful은 화이트보드입니다. 지우고 다시 쓸 수 있죠(좋아요 수, 입력창, 타이머). 화이트보드 내용을 바꿨으면 "여기 새로 썼어요!" 하고 알려야 사람들이 다시 보는데, 그 외침이 바로 setState입니다.

StatelessWidget

받은 값(props)만으로 그림. 스스로 바꿀 내부 상태가 없어, 새 값을 받아야(부모 리빌드 등) 다시 그려짐.

  • 외부 데이터만 표시
  • 아이콘, 라벨, 정적 카드
  • React의 props-only 컴포넌트

StatefulWidget

내부 상태를 갖고, 그 상태가 바뀌면 다시 그림.

  • 카운터, 폼 입력, 토글
  • 애니메이션, 체크박스
  • React의 useState 가진 컴포넌트
counter.dart
// ── Stateful: 내부 count가 바뀌면 화면 갱신 ──
class Counter extends StatefulWidget {
  const Counter({super.key});
  @override
  State<Counter> createState() => _CounterState();
}

class _CounterState extends State<Counter> {
  int count = 0;          // 👈 이게 "상태"

  void increment() {
    setState(() {        // 👈 State를 dirty로 표시 → build 재예약(리렌더 트리거)
      count++;
    });
  }

  @override
  Widget build(BuildContext context) {
    return Column(children: [
      Text('$count'),
      ElevatedButton(onPressed: increment, child: Text('+1')),
    ]);
  }
}
가장 흔한 실수: count++만 하고 setState를 안 부르면 → 값은 바뀌지만 화면은 그대로입니다. setState가 Flutter에게 "build를 다시 호출하라"고 알리는 신호이기 때문이죠. 면접에서 거의 100% 확인하는 포인트입니다.
React 매핑: setState = useState의 setter. 둘 다 "리렌더 트리거"입니다. 차이는 React가 가상 DOM diff를 하고, Flutter는 위젯 트리를 재구성한다는 점.
예상 꼬리질문: "setState 안에서 await(비동기) 해도 되나요?" → 안 됩니다. setState 콜백은 동기로 짧게 유지하고, 비동기 작업은 밖에서 한 뒤 결과만 setState로 반영해야 합니다.

3-트리 렌더링 모델 ⭐

part 2 · 핵심

"Flutter는 왜 빠른가?"의 정답. 면접에서 가장 깊이 파고드는 주제입니다.

Flutter는 화면을 3개의 트리(Widget·Element·RenderObject)로 관리합니다. 각 트리의 역할 분담이 성능의 비밀이에요. (엄밀히는 RenderObject 트리는 Element 트리의 부분집합 — 레이아웃·페인팅을 맡는 Element만 RenderObject를 갖고, 구조·상태만 담당하는 Element엔 없습니다.)

🏗️ 일상 비유 — 건축 현장: 집을 짓는 과정으로 생각하면 한 번에 이해됩니다.
• Widget = 설계도면 📄 — 종이라서 다시 그려도 비용이 거의 없음. "방을 파란색으로" 같은 요구사항일 뿐.
• Element = 현장 감독 👷 — 도면과 실제 건물을 대조하며 "이번엔 벽 색만 바뀌었네, 벽돌은 그대로 두고 페인트만 새로 칠하자"고 판단.
• RenderObject = 실제 벽돌·콘크리트 🧱 — 진짜로 쌓고 칠하는 작업이라 가장 비쌈.
도면(Widget)을 100번 새로 그려도, 감독(Element)이 "실제로 바뀐 부분"만 골라 인부에게 시키므로 건물 전체를 부수고 다시 짓지 않습니다. 이것이 Flutter가 빠른 이유예요.
트리역할특징비유
Widget"이렇게 그려라" 설정·설계도불변(immutable), 매 build마다 새로 생성, 가벼움📄 설계도
ElementWidget↔Render 연결 + 상태 보관재사용됨, diff 수행의 주체👷 현장감독
RenderObject실제 측정·배치·그리기무거움, 최대한 재사용🧱 실제 벽돌
왜 빠른가 (면접 정답): "Widget은 설계도일 뿐이라 매번 새로 만들어도 비용이 거의 없습니다. 비싼 작업(레이아웃·페인팅)을 담당하는 RenderObject는 Element가 diff를 통해 실제로 바뀐 부분만 골라 갱신합니다. 그래서 build를 자주 호출해도 성능에 문제가 없는 구조입니다."
예상 꼬리질문: "build가 자주 불리면 느리지 않나요?" → "아닙니다. Widget 생성은 싸고, 무거운 RenderObject는 재사용됩니다. 오히려 const 위젯을 쓰면 Element가 '동일 인스턴스'임을 즉시 판단해 그 서브트리의 재빌드를 건너뛸 수 있습니다."
React 매핑(발상 비교용): Widget 트리 ≈ 가상 DOM, RenderObject 트리 ≈ 실제 DOM. "diff 후 바뀐 것만 반영"하는 발상이 비슷합니다. Element 트리는 React의 Fiber에 대응한다고 보면 이해하기 쉽습니다 — 다만 Flutter는 트리 전체 diff가 아니라 자식 리스트 단위 재조정(reconciliation)이라 내부 메커니즘은 동일하지 않습니다.

🔑Key — 위젯의 신원 확인 (면접 빈출)

Element가 "이 위젯이 이전의 그 위젯과 같은가?"를 판단할 때, 보통은 타입과 위치로 비교합니다. 그런데 같은 타입의 위젯이 여러 개 있고 순서가 바뀌면 Element가 헷갈려 상태가 엉킵니다. 이때 신원을 못박아주는 게 Key예요.

🎫 일상 비유 — 콘서트 좌석표 vs 이름표: 관객을 좌석 위치로만 구분하면(키 없음), 사람들이 자리를 바꿔 앉는 순간 누가 누군지 알 수 없습니다. 각자 이름표(Key)를 달면, 자리를 옮겨도 "아, 창한님이 3번에서 1번으로 이동했구나" 하고 정확히 추적할 수 있죠. 리스트 항목을 재정렬·삭제할 때 Key가 바로 이 이름표 역할을 합니다.
key.dart
// ❌ Key 없음: 항목 삭제 시 체크 상태가 엉뚱한 항목에 남음
items.map((item) => TodoTile(item)).toList();

// ✅ Key 부여: 각 위젯의 신원이 고정됨
items.map((item) => TodoTile(
  key: ValueKey(item.id),  // 고유 id로 신원 확인
  item,
)).toList();
예상 꼬리질문: "리스트에서 항목을 지웠는데 체크박스 상태가 이상하게 남습니다. 왜죠?" → "같은 타입 위젯들이라 Element가 위치로만 매칭해서 상태가 어긋난 겁니다. 각 항목에 ValueKey(고유id)를 주면 해결됩니다." (React의 key prop과 정확히 같은 개념)

화면 전환 — Navigation

part 2 · 핵심

앱은 여러 화면으로 이뤄집니다. 화면을 쌓고 되돌아오는 방법, 면접에서 기본으로 묻습니다.

📚 일상 비유 — 책상 위 서류 쌓기(Stack): 새 화면으로 가는 push는 책상에 서류를 한 장 올려놓는 것입니다. 뒤로 가는 pop은 맨 위 서류를 치우는 것이고요. 항상 맨 위 화면만 보이며, 치우면 바로 아래 화면이 다시 드러납니다. 이 "쌓기/치우기" 구조가 네비게이션 스택이에요.
navigation.dart
// 새 화면 올리기 (push)
Navigator.push(
  context,
  MaterialPageRoute(builder: (_) => DetailScreen(id: 7)),
);

// 이전 화면으로 (pop)
Navigator.pop(context);

🏨 일상 비유 — 호텔 투숙: initState는 체크인입니다(딱 한 번, 짐 풀고 와이파이 연결). build는 방에서 지내는 동안 계속 정돈하는 것(여러 번). dispose는 체크아웃이에요 — 켜둔 에어컨 끄고, 빌린 물건 반납하고 떠나야 합니다. 체크아웃하면서 정리를 안 하면(=dispose 누락) 다음 손님에게 요금이 계속 청구되는 셈이라, 이게 곧 메모리 누수입니다.
메서드호출 시점용도

비동기 · Future · Stream

part 2 · 핵심

API 호출처럼 시간이 걸리는 작업과 UI를 잇는 방법. 백엔드 연동의 핵심.

📳 일상 비유 — 식당 진동벨: 주문하면 음식이 지금 당장 나오지 않죠. 점원이 진동벨을 주고("음식이 미래에 도착할 거예요"), 그게 바로 Future입니다. 벨을 들고 자리에 앉아 다른 일을 할 수 있는 게 async/await(기다리는 동안 앱이 멈추지 않음)예요. 벨이 울리기 전엔 "조리 중" 표시, 울리면 음식 받기, 주방 사고가 나면 "품절" 안내 — 이 세 상태를 자동 처리하는 게 FutureBuilder입니다.

Future = 미래에 도착할 단일 값

future.dart
// async 함수는 Future를 반환
Future<User> fetchUser() async {
  final res = await http.get(url);  // 결과 기다림
  return User.fromJson(res.body);
}

FutureBuilder = Future 결과로 UI 자동 분기

로딩 → 성공 → 에러 상태를 알아서 처리해주는 위젯입니다.

future_builder.dart
FutureBuilder<User>(
  future: _userFuture,   // ⚠️ State에 담아둔 것 (build에서 직접 호출 X)
  builder: (context, snapshot) {
    if (snapshot.connectionState == ConnectionState.waiting) {
      return CircularProgressIndicator();   // 로딩
    } else if (snapshot.hasError) {
      return Text('에러: ${snapshot.error}'); // 실패
    }
    return Text(snapshot.data!.name);        // 성공
  },
)
치명적 실수: future:에 fetchUser()를 build 안에서 직접 호출하면, 위젯이 리빌드될 때마다 API가 재호출됩니다. → initState에서 한 번 호출해 State 변수에 담고, 그 변수를 참조하세요.

에러 처리 — try/catch + 사용자 피드백

네트워크는 언제든 실패합니다. 에러를 잡아 사용자에게 친절히 알리고 복구 경로를 주는 것까지가 프론트엔드의 책임이에요. 리드 면접에서 자주 확인합니다.

error_handling.dart
Future<void> loadData() async {
  try {
    setState(() => isLoading = true);
    final data = await api.fetch();
    if (!mounted) return;          // 화면 살아있는지 확인
    setState(() => _data = data);
  } on SocketException {        // 네트워크 끊김 — 구체적 처리
    _showSnack('인터넷 연결을 확인해 주세요');
  } catch (e) {                    // 그 외 모든 에러
    _showSnack('잠시 후 다시 시도해 주세요');
  } finally {
    if (mounted) setState(() => isLoading = false); // 항상 로딩 해제
  }
}
💬 일상 비유 — 식당의 매끄러운 응대: 주문한 메뉴가 품절이어도 좋은 식당은 손님을 방치하지 않죠. "죄송합니다, 대신 이건 어떠세요?"라고 대안을 줍니다. 앱도 에러 화면에서 멈추지 말고 "다시 시도" 버튼이나 안내 메시지로 사용자를 다음 행동으로 이끌어야 합니다. finally는 성공·실패와 무관하게 "로딩 스피너는 반드시 끈다"를 보장하는 안전장치예요.
예상 꼬리질문: "API 호출이 실패하면 화면을 어떻게 처리하나요?" → "try/catch로 에러 유형을 구분해(네트워크 끊김 vs 서버 오류) 각기 다른 메시지를 보여주고, '다시 시도' 액션을 제공합니다. finally에서 로딩 상태를 정리해 스피너가 멈추지 않는 일을 방지합니다."

상태관리 — Riverpod ⭐

part 3 · 심화

setState는 위젯 하나 안에서만 통합니다. 앱 전역 상태(로그인·스트릭 데이터)는 상태관리 도구가 필요해요.

📺 일상 비유 — 유튜브 구독: ref.watch는 채널 구독입니다. 채널에 새 영상이 올라오면(상태 변경) 구독자에게 자동으로 알림이 가죠(위젯 자동 리빌드). ref.read는 지금 한 번만 확인하는 것 — 구독은 안 하고 "현재 구독자 수만 잠깐 볼게"처럼, 버튼을 누르는 순간에만 값을 읽습니다. 그리고 Provider는 그 영상이 올라가는 채널(중앙 저장소) 자체예요.

왜 필요한가 — Prop Drilling 문제

상위 위젯의 데이터를 깊은 하위 위젯까지 넘기려면, 중간 위젯들이 쓰지도 않는 값을 계속 전달해야 합니다(prop drilling). 상태관리 도구는 이 사슬을 끊고 어디서든 직접 접근하게 합니다.

🪣 일상 비유 — 양동이 릴레이 vs 수도관: Prop drilling은 불을 끄려고 사람들이 일렬로 서서 양동이를 손에서 손으로 넘기는 것과 같습니다. 중간 사람들은 정작 물이 필요 없는데 계속 전달만 해야 하죠. 상태관리 도구는 건물에 수도관을 설치하는 것 — 물이 필요한 곳에서 수도꼭지만 열면 됩니다. 중간 사람들은 더 이상 양동이를 나를 필요가 없어요.

// 1) 전역 상태 정의 — Notifier + NotifierProvider (Riverpod 3 표준)
class Counter extends Notifier<int> {
  @override
  int build() => 0;          // 초기 상태
  void increment() => state++;   // 변경 로직을 notifier에 캡슐화
}
final counterProvider = NotifierProvider<Counter, int>(Counter.new);

// 2) 구독해서 사용 (ConsumerWidget)
class CounterView extends ConsumerWidget {
  @override
  Widget build(BuildContext ctx, WidgetRef ref) {
    final count = ref.watch(counterProvider); // 구독 → 자동 갱신
    return Column(children: [
      Text('$count'),
      ElevatedButton(
        // 이벤트에선 read로 notifier의 메서드 호출
        onPressed: () => ref.read(counterProvider.notifier).increment(),
        child: Text('+1'),
      ),
    ]);
  }
}

그 밑바탕 — InheritedWidget (꼬리질문 대비)

Provider 패키지는 사실 Flutter 내장의 InheritedWidget을 감싼 것입니다. 이건 "트리 위쪽에 데이터를 매달아두면, 아래 위젯들이 .of(context)로 효율적으로 꺼내 쓰는" 기본 메커니즘이에요. Theme.of(context), MediaQuery.of(context)가 바로 이 방식으로 동작합니다. 단, Riverpod은 다릅니다 — 상태를 위젯 트리·BuildContext에 묶지 않고 ProviderContainer/Ref로 관리하며, ProviderScope만 InheritedWidget으로 컨테이너를 트리에 노출합니다(그래서 context 없이도 상태 접근·테스트가 쉬움).

📡 일상 비유 — 천장에 단 공용 와이파이 공유기: 집 천장(트리 상단)에 공유기를 하나 달아두면, 각 방(하위 위젯)이 선을 끌어올 필요 없이 어디서든 신호를 잡습니다. InheritedWidget이 그 공유기예요. 그리고 공유기 설정이 바뀌면(데이터 변경) 연결된 기기만 자동으로 갱신됩니다 — 이게 구독한 위젯만 리빌드되는 원리입니다.
예상 꼬리질문: "Provider는 내부적으로 어떻게 동작하나요?" → "Flutter 내장 InheritedWidget을 감싸 사용하기 쉽게 만든 것입니다. 트리 상단에 상태를 두고, 의존하는 위젯이 .of(context)로 구독하면 변경 시 그 위젯만 다시 빌드됩니다." → 원리까지 답하면 깊이 있는 지원자로 평가됩니다.

리드 포지션이라면 반드시 묻습니다. "불필요한 리빌드를 어떻게 줄이나요?"

⚡핵심 5원칙

  • const 생성자 적극 사용 — 변하지 않는 위젯은 const로. Element가 즉시 동일 판정해 재빌드를 건너뜁니다.
  • setState 범위 최소화 — 거대한 위젯 전체가 아니라, 바뀌는 작은 부분만 별도 위젯으로 분리해 거기서만 setState.
  • ListView.builder 사용 — 긴 리스트는 화면에 보이는 항목만 지연 생성(lazy). 전체를 한 번에 만들지 않음.
  • build 안에서 무거운 연산 금지 — 정렬·필터·객체 생성은 build 밖(initState/메모이즈)에서.
  • RepaintBoundary — 자주 다시 그려지는 영역(애니메이션)을 격리해 주변 페인팅 비용 차단.

// ❌ 한 번에 1만 개 위젯 생성 → 메모리 폭발
ListView(children: items.map((e) => Tile(e)).toList());

// ✅ 보이는 것만 그때그때 생성 (지연 렌더)
ListView.builder(
  itemCount: items.length,
  itemBuilder: (ctx, i) => Tile(items[i]),
);

⚡ 한 줄 요약 모음

  • Flutter: OS 위젯 안 쓰고 자체 엔진(Skia/Impeller)으로 직접 그림 → 플랫폼 무관 동일 UI
  • Everything is a Widget: 패딩·정렬·화면까지 전부 위젯, 중첩이 곧 위젯 트리
  • Stateless vs Stateful: 내부 상태 유무. setState = State를 dirty 표시 → 리렌더(build 재예약)
  • 3-트리: Widget(설계도·쌈) → Element(상태보관·재사용·diff) → RenderObject(그리기·비쌈). 그래서 build 자주 해도 빠름
  • Key: 위젯의 이름표. 같은 타입 위젯 재정렬·삭제 시 신원 유지 → ValueKey(id)
  • Navigation: 화면 스택에 push(올리기)/pop(치우기). 규모 커지면 go_router
  • 생명주기: initState(1회 초기화) → build(N회) → dispose(반드시 정리·누수 방지)
  • BuildContext: 트리에서 내 위치(Element). .of(context)로 조상 접근. async 뒤엔 mounted 체크
  • Future: 미래의 단일 값 + FutureBuilder(로딩/에러/성공 자동 분기). build에서 직접 호출 금지
  • Stream: 연속 값 + StreamBuilder (채팅·실시간)
  • 에러 처리: try/catch로 유형 구분 → 사용자 메시지 + 재시도. finally에서 로딩 해제
  • Riverpod: watch=구독, read=1회. 전역 상태, prop drilling 해결. 상태는 ProviderContainer/Ref 기반(트리 비종속)
  • 성능: const 적극 사용 · setState 범위 최소화 · ListView.builder · build 안 무거운 연산 금지
