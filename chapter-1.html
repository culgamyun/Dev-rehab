Chapter 01: 모던 자바 핵심 (Java 8 람다/스트림 ~ Java 21)

자바 8의 영원한 기반인 람다·함수형 인터페이스·Stream API부터, var·Record·Pattern Matching·Sealed Classes 같은 모던 문법, 그리고 스레드 기초와 Java 21 Virtual Threads까지 — 복귀 개발자가 가장 먼저 손에 익혀야 할 11개 핵심 스펙을 완벽히 정복합니다.

1. 레거시 자바 8에 갇혀있던 우리들의 자화상

자바 8(2014년)은 함수형 프로그래밍(Lambda, Stream) 도입으로 각광받았으나, 현대적인 객체 설계 관점에서는 치명적인 생산성 장애물을 갖고 있었습니다.

💡 비유로 이해하기: 수동 재봉틀 vs 원터치 자동 재단기

레거시 자바 8은 "옷 한 벌(객체 하나)을 만들기 위해 100번 넘게 수동 나사를 쪼여야 하는(Getter/Setter) 수동 재봉틀"입니다. 반면 자바 17/21은 "치수만 입력하면 단 1초 만에 옷이 튀어나오는(Record) 원터치 자동 재단기"와 같습니다.

2. 'var' 키워드 — 타입 추론 (Java 10+)

자바도 이제 자바스크립트나 파이썬처럼 로컬 변수의 타입을 생략할 수 있습니다. 컴파일러가 우변을 보고 알아서 타입을 추론합니다.

로컬 변수 타입 추론 
// ❌ 과거: 중복된 타입 선언
Map<String, List<String>> userMap = new HashMap<String, List<String>>();

// ✅ 현대: 컴파일러가 알아서 추론 (가독성 향상)
var userMap = new HashMap<String, List<String>>();
var name = "Antigravity"; // String으로 추론
var price = 10000;        // int로 추론

// 주의: 클래스의 멤버 변수(필드)나 메서드 파라미터로는 사용할 수 없으며 지역 변수에만 사용 가능!

3. 컬렉션 팩토리 메서드 (Java 9+)

불변(Immutable) 리스트나 맵을 만들 때 Arrays.asList()나 new ArrayList<>()를 남발하던 시절은 끝났습니다.

List.of, Map.of 
// 1. 불변 리스트 생성 (수정 불가능, Thread-Safe)
var colors = List.of("Red", "Green", "Blue");
// colors.add("Yellow"); // UnsupportedOperationException 발생!

// 2. 불변 Set 생성
var roles = Set.of("ADMIN", "USER");

// 3. 불변 Map 생성
var errorCodes = Map.of(
    400, "Bad Request",
    404, "Not Found",
    500, "Internal Server Error"
);

4. 친절한 NullPointerException (Java 14+)

과거에는 a.b.c.getName()에서 NPE가 나면 정확히 a, b, c 중 어디가 null인지 알 수 없었습니다. 모던 자바는 정확한 원인을 로그에 찍어줍니다.

🔍 개선된 에러 메시지

Exception in thread "main" java.lang.NullPointerException:
Cannot invoke "Address.getCity()" because "user.getAddress()" is null
at Main.main(Main.java:5)

5. Boilerplate 브레이커, 'Record' 문법 (Java 14+)

데이터 전달용 객체(DTO)를 만들 때 수십 줄의 Getter/Setter/생성자/equals/hashCode를 단 1줄로 압축합니다.

Modern Record (초경량 불변 데이터 객체) 
// 단 1줄로 끝! (모든 필드는 내부적으로 private final로 선언됨)
public record ProductRecord(Long id, String name, int price) {
    // 필요 시 생성자 유효성 검증만 추가 가능
    public ProductRecord {
        if (price < 0) throw new IllegalArgumentException("가격은 0 이상이어야 합니다.");
    }
}

// 사용법
var product = new ProductRecord(1L, "셔츠", 30000);
System.out.println(product.name()); // getName()이 아님! 필드명 자체가 메서드명!

6. Switch 식과 instanceof 패턴 매칭 (Java 17, 21+)

타입 검사(instanceof)와 강제 형변환(Casting)을 한 줄로 합치고, switch를 변수에 담을 수 있는 '식(Expression)'으로 진화시켰습니다.

Pattern Matching 
public String getBillingSummary(Object input) {
    // switch '문(Statement)'이 아닌 리턴값이 있는 '식(Expression)'
    return switch (input) {
        // instanceof 검사와 캐스팅 변수(p) 바인딩이 한 줄로 해결!
        case ProductRecord p -> "상품: " + p.name() + " (" + p.price() + "원)";
        case OrderRecord o   -> "주문 총액: " + o.total() + "원";
        case null            -> "입력 값이 비어 있습니다 (Null Safe)";
        default              -> "알 수 없는 타입입니다.";
    }; // 세미콜론 필수!
}

7. 도메인 한계선 봉인: Sealed Classes (Java 17+)

특정 클래스를 상속받을 수 있는 하위 클래스를 명시적으로 제한하여, 무분별한 상속과 해킹을 컴파일 수준에서 차단합니다.

Sealed Interface 
// permits 뒤에 적힌 2개의 클래스만 이 인터페이스를 구현할 수 있음!
public sealed interface Payment permits CardPayment, BankPayment {
    void process();
}

// 상속받는 하위 클래스는 반드시 final(상속 끝) 또는 non-sealed(봉인 해제)를 명시
public final class CardPayment implements Payment {
    public void process() { System.out.println("카드 결제"); }
}

8. 멀티라인 Text Blocks (Java 15+)

SQL이나 JSON을 + "\n" +로 이어붙이던 끔찍한 코드 대신, 파이썬처럼 """를 사용하여 눈에 보이는 그대로 문자열을 정의합니다.

Text Blocks 
String modernSql = """

String jsonPayload = """

9. 람다 · 함수형 인터페이스 · Stream API (자바 8의 영원한 핵심)

❗ 오해 주의: 자바 8의 람다와 Stream은 "옛날 것"이 아닙니다. Record·Virtual Threads 같은 최신 문법도 이 위에서 돌아가며, 실무 코드의 절반 이상이 Stream 파이프라인입니다. 복귀 개발자가 가장 먼저 손에 다시 익혀야 할 1순위 — 안 쓰는 게 아니라 "기본기"가 됐습니다.

💡 비유로 이해하기: 컨베이어 벨트 가공 라인

for문이 "작업자가 박스를 하나씩 꺼내 직접 가공"하는 것이라면, Stream은 "컨베이어 벨트에 원료를 올리면 필터 → 가공 → 포장 단계를 자동으로 거쳐 완제품이 나오는 것"입니다. 람다는 각 단계에서 "무엇을 할지" 적은 작업 지시서입니다.

① 람다 표현식 — 함수를 값처럼 전달

람다는 "이름 없는 일회용 함수"입니다. 메서드 하나짜리 인터페이스(함수형 인터페이스)를 짧게 구현합니다.

익명 클래스 → 람다 진화 
// 🪨 자바 8 이전: 익명 클래스 (장황함)
Runnable oldWay = new Runnable() {
    @Override
    public void run() { System.out.println("주문 처리"); }
};

// ✅ 람다: (파라미터) -> { 본문 }
Runnable lambda = () -> System.out.println("주문 처리");

// 파라미터가 있을 때
Comparator<Product> byPrice = (a, b) -> a.price() - b.price();

// 본문이 여러 줄이면 중괄호 + return
Comparator<Product> byName = (a, b) -> {
    System.out.println("비교 중...");
    return a.name().compareTo(b.name());
};

② 함수형 인터페이스 4대장

람다가 대입될 수 있는 인터페이스. 매번 직접 만들 필요 없이 java.util.function 패키지에 표준 제공됩니다.

인터페이스 시그니처 용도
Function<T,R>T → R입력을 받아 변환 (map)
Predicate<T>T → boolean조건 판별 (filter)
Consumer<T>T → void소비, 부수효과 (forEach)
Supplier<T>() → T생산, 지연 생성 (orElseGet)
 
Predicate<Product> isPremium = p -> p.price() >= 100000;
Function<Product, String> toName = p -> p.name();
Consumer<String> printer = name -> System.out.println(name);
Supplier<Product> defaultProduct = () -> new Product("기본상품", 0);

System.out.println(isPremium.test(product));  // true/false

③ 메서드 참조 — 람다의 축약형

람다가 "기존 메서드를 그대로 호출"만 한다면 ::로 더 짧게 씁니다.

// 람다           →  메서드 참조
p -> p.name()       ProductRecord::name        // 인스턴스 메서드 참조
s -> System.out.println(s)   System.out::println  // 특정 객체의 메서드
s -> Integer.parseInt(s)     Integer::parseInt    // 정적 메서드 참조
name -> new Product(name)    Product::new         // 생성자 참조

④ Stream 파이프라인 — 소스 · 중간연산 · 최종연산

Stream은 ① 소스(컬렉션) → ② 중간 연산(filter/map, 0개 이상, 게으름) → ③ 최종 연산(collect/forEach, 1개, 실행 트리거)의 3단계입니다. 최종 연산이 호출되기 전엔 아무것도 실행되지 않습니다(지연 평가).

의류 쇼핑몰 — Stream 실전 패턴 
// 1. 필터 → 변환 → 수집 (가장 흔한 패턴)
List<String> premiumNames = products.stream()      // ① 소스
    .filter(p -> p.price() >= 100000)                // ② 중간: 조건
    .map(ProductRecord::name)                         // ② 중간: 변환
    .toList();                                        // ③ 최종 (Java 16+)

// 2. 정렬 + 개수 제한
List<Product> top3Cheapest = products.stream()
    .sorted(Comparator.comparingInt(Product::price))
    .limit(3)
    .toList();

// 3. 집계 — reduce / sum
int totalPrice = products.stream()
    .mapToInt(Product::price)
    .sum();

// 4. 그룹핑 — 카테고리별 상품 묶기 (Map 반환)
Map<String, List<Product>> byCategory = products.stream()
    .collect(Collectors.groupingBy(Product::category));

// 5. 카테고리별 평균 가격
Map<String, Double> avgByCategory = products.stream()
    .collect(Collectors.groupingBy(
        Product::category,
        Collectors.averagingInt(Product::price)
    ));

// 6. 조건 매칭 (boolean 반환)
boolean hasOutOfStock = products.stream().anyMatch(p -> p.stock() == 0);
boolean allInStock     = products.stream().allMatch(p -> p.stock() > 0);

⚠️ 자주 하는 실수:

  • Stream 재사용 불가: 한 번 최종 연산한 Stream은 다시 못 씀 (IllegalStateException). 매번 .stream()으로 새로 시작.
  • 중간 연산만 쓰면 실행 안 됨: .filter()만 하고 최종 연산이 없으면 코드가 아예 안 돌아감 (지연 평가).
  • 병렬 스트림 남용 금지: .parallelStream()은 데이터가 매우 크고 연산이 무거울 때만. 작은 컬렉션엔 오버헤드만 큼.

⑤ Optional — null 안전 처리

// Optional: null일 수도 있는 값을 감싸는 상자
String userName = Optional.ofNullable(user)
    .map(User::getName)
    .filter(name -> !name.isBlank())   // isBlank(): Java 11+ (공백만 있는 문자열도 빈 값으로 취급)
    .orElse("익명 사용자");      // 없으면 기본값

// orElseThrow — 없으면 예외 (Repository.findById 패턴)
Product product = productRepository.findById(id)
    .orElseThrow(() -> new EntityNotFoundException("상품 없음"));

10. 스레드 기초 — 프로세스, 스레드, 동시성 제어

Virtual Threads(다음 섹션)를 제대로 이해하려면 먼저 "스레드가 무엇이고 왜 비싼가"를 알아야 합니다. 복귀 개발자가 면접에서 가장 자주 막히는 영역이기도 합니다.

① 프로세스 vs 스레드

💡 비유로 이해하기: 회사(프로세스)와 직원(스레드)

프로세스는 독립된 "회사 건물"입니다 — 각자 자기 메모리(사무실)를 갖고, 다른 회사와 자원을 공유하지 않습니다.
스레드는 한 회사 안의 "직원들"입니다 — 같은 건물(힙 메모리)을 공유하며 일하지만, 각자 자기 책상(스택)은 따로 갖습니다.
그래서 스레드끼리는 데이터 공유가 빠르지만(같은 힙), 동시에 같은 자원을 건드리면 충돌(race condition)이 납니다.

구분 프로세스 스레드
메모리독립 (Heap/Stack 모두 별도)Heap 공유, Stack만 개별
생성 비용무거움가벼움 (그래도 OS 스레드는 ~1MB 스택)
통신IPC 필요 (느림)공유 메모리 (빠름, 단 동기화 필요)
장애 전파독립 (한 프로세스 죽어도 무관)한 스레드 폭주가 프로세스 전체 영향

② 스레드 생성 4가지 방법

Thread 상속 → Runnable → 람다 → ExecutorService 
// 1. Thread 상속 (비추 — 자바는 단일 상속이라 확장성 떨어짐)
class OrderThread extends Thread {
    public void run() { System.out.println("주문 처리"); }
}
new OrderThread().start();   // start()! run() 직접 호출하면 새 스레드 안 생김

// 2. Runnable 구현 (인터페이스라 유연)
Runnable task = new Runnable() {
    public void run() { System.out.println("주문 처리"); }
};
new Thread(task).start();

// 3. 람다 (Runnable은 함수형 인터페이스 → 섹션 9 람다와 연결!)
new Thread(() -> System.out.println("주문 처리")).start();

// 4. ExecutorService (실무 표준 — 스레드 풀로 재사용 관리)
ExecutorService executor = Executors.newFixedThreadPool(10);
executor.submit(() -> System.out.println("주문 처리"));
Future<Integer> future = executor.submit(() -> calculateTotal());  // 결과 반환
executor.shutdown();

실무에선 직접 new Thread()를 거의 안 합니다. ExecutorService(스레드 풀)로 스레드를 재사용하여 생성 비용을 절감하는 것이 표준입니다.

③ 스레드 생명주기 (Lifecycle)

NEW → RUNNABLE ⇄ BLOCKED / WAITING / TIMED_WAITING → TERMINATED

생성(NEW) → start() 호출로 실행 대기(RUNNABLE) → 락 대기나 sleep 시 멈춤(BLOCKED/WAITING) → 작업 완료(TERMINATED). BLOCKED/WAITING 상태에서 OS 스레드가 놀고 있는 게 바로 Virtual Threads가 해결하려는 비효율입니다.

④ Race Condition과 동기화 (synchronized)

재고 차감 — 동시성 버그와 해결 
// ❌ 동시성 버그: 두 스레드가 동시에 stock=10을 읽고 둘 다 9로 차감 → 1개만 줄어듦
class Inventory {
    private int stock = 10;
    public void decrease() {
        stock = stock - 1;   // 읽기-수정-쓰기가 원자적이지 않음!
    }
}

// ✅ 해결 1: synchronized — 한 번에 한 스레드만 진입 (락)
class SafeInventory {
    private int stock = 10;
    public synchronized void decrease() {   // 메서드 전체 락
        stock = stock - 1;
    }
}

// ✅ 해결 2: AtomicInteger — 락 없이 원자적 연산 (CAS 기반, 더 빠름)
class AtomicInventory {
    private final AtomicInteger stock = new AtomicInteger(10);
    public void decrease() {
        stock.decrementAndGet();
    }
}

// ✅ 해결 3: ReentrantLock — synchronized보다 유연 (tryLock, 타임아웃 등)
// ⚠️ Virtual Threads 환경에서는 synchronized보다 ReentrantLock 권장 (pinning 회피)

⛓️ 동시성 심화(synchronized vs ReentrantLock, ThreadLocal 위험, 데드락 4조건)는 부록 B — Q19/Q20 동시성 면접 주제에서 다룹니다.

🌉 다음 섹션으로의 연결: 전통 OS 스레드는 1개당 ~1MB 스택을 먹고, 컨텍스트 스위칭 비용도 큽니다. 그래서 스레드 풀로 수백 개 정도만 운영하는데, 각 스레드가 DB 응답을 기다리며(BLOCKED) 놀고 있으면 처리량이 떨어집니다. 바로 이 비효율을 해결하는 것이 다음 섹션의 Virtual Threads입니다.

11. 자바 21의 진정한 혁신: Virtual Threads (가상 스레드)

과거의 자바(OS 스레드 1:1 매핑)는 스레드를 생성하는 비용이 비싸(스레드당 ~1MB 스택) 동시 처리량에 한계가 있었습니다. Virtual Thread는 OS 스레드 위에 매우 가벼운 가상 스레드를 올려, 블로킹 I/O 대기(DB·외부 API)가 병목인 워크로드에서 동기 코드 그대로 많은 동시 작업을 처리하게 해줍니다.

🚀 Spring Boot 3.2+ 에서의 적용

application.yml에 spring.threads.virtual.enabled: true 단 한 줄이면 톰캣 요청이 가상 스레드로 처리됩니다. 코드는 전통적인 동기(Synchronous) 방식으로 읽기 쉽게 짜면서, 블로킹 I/O 대기가 많은 워크로드의 동시 처리량을 끌어올릴 수 있습니다(리액티브 코드 없이).

⚠️ 과신 금지 — 실제 처리량의 한계: "수백만 동시 접속자"는 과장입니다. Virtual Threads의 실제 처리량은 아래에 묶입니다:
  • 블로킹 I/O 대기가 병목일 때만 빛납니다. CPU-bound 작업은 더 빨라지지 않습니다.
  • DB 커넥션 풀 크기가 여전히 상한입니다(스레드가 10만 개여도 커넥션이 20개면 거기서 막힘).
  • 외부 API 지연/레이트 리밋, 메모리, 컨테이너 CPU 설정도 제약.
  • synchronized 블록 내 블로킹은 캐리어 스레드를 pinning시켜 이점을 깎습니다 → ReentrantLock 권장.
  • 실제 수치는 반드시 부하 테스트로 측정하세요.

⛓️ 본 챕터는 Virtual Threads의 언어/JVM 측 도입부를 다룹니다. Spring Boot 3.4+ 환경에서 실제 컨트롤러/서비스에 적용하는 실전 활용 예제(블랙프라이데이 대량 주문 처리)는 Chapter 2 — Virtual Threads 섹션 13에서 본격적으로 다룹니다.

📚 01챕터 헷갈리는 용어 사전

Boilerplate (보일러플레이트): 기능 변화 없이 자바 문법을 충족하기 위해 무지성으로 반복해 쓰던 기계형 코드(Getter/Setter 등).
var (타입 추론): 컴파일러가 대입되는 값을 보고 타입을 알아서 맞춰주는 지역 변수 키워드.
Record (레코드): 데이터를 보관하는 데 특화된 자바의 초경량 불변(Immutable) 데이터 클래스.
Pattern Matching: 객체 타입 검사(instanceof)와 강제 형변환(캐스팅)을 한 줄로 압축해 주는 기법.
Sealed Classes (봉인 클래스): 무분별한 상속을 막기 위해 자신을 상속받을 자식 클래스를 미리 지정해 두는 보안 설계.
람다 (Lambda): 이름 없는 일회용 함수. (파라미터) -> 본문 형태로 함수형 인터페이스를 짧게 구현. 자바 8 도입, 여전히 핵심.
함수형 인터페이스: 추상 메서드가 1개뿐인 인터페이스. Function/Predicate/Consumer/Supplier가 표준 4대장. 람다가 대입되는 타입.
Stream API: 소스 → 중간 연산(filter/map) → 최종 연산(collect)의 선언적 데이터 파이프라인. 최종 연산 전엔 실행 안 됨(지연 평가).
메서드 참조 (::): 람다가 기존 메서드만 호출할 때 ClassName::method 로 축약. Static/Instance/Constructor 참조 종류.
프로세스 vs 스레드: 프로세스는 독립 메모리(회사 건물), 스레드는 Heap 공유 + Stack 개별(직원). 스레드는 공유가 빠르지만 동기화 필요.
Race Condition: 여러 스레드가 공유 자원을 동시에 수정할 때 발생하는 충돌. synchronized, AtomicInteger, ReentrantLock으로 해결.
ExecutorService: 스레드 풀로 스레드를 재사용 관리하는 실무 표준. 직접 new Thread() 대신 사용하여 생성 비용 절감.
Virtual Threads (가상 스레드): OS 스레드에 묶이지 않고 JVM이 자체 관리하는 매우 가벼운 스레드. 블로킹 I/O 대기가 많은 워크로드의 동시 처리량을 높임(단 DB 풀·CPU 등이 실제 상한).
