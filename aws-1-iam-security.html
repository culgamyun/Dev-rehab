AWS 자격증 > A1. 보안·자격증명

A1. SAA① 보안 · 자격증명 (IAM · KMS · 위협 방어)

SAA-C03(2026 기준) 4개 도메인 중 가장 비중이 큰 도메인 1 「보안 아키텍처 설계」(30%)를 통째로 다룹니다. IAM 정책 평가 로직과 JSON 해부, IAM 역할·STS, Organizations·SCP 거버넌스, KMS 암호화와 봉투 암호화, Secrets Manager vs Parameter Store, 그리고 Cognito·WAF·Shield·GuardDuty 같은 엣지·탐지 서비스의 역할 구분까지 — "키워드를 보면 정답 서비스가 떠오르는" 수준으로 정리합니다.

1. IAM 평가 로직 — 누가 무엇을 할 수 있는가

AWS 보안의 출발점은 IAM(Identity and Access Management)입니다. 모든 API 요청은 "이 주체(Principal)가 이 리소스에 이 액션을 해도 되는가?"라는 질문으로 환원되고, IAM이 그 판정을 내립니다. 시험에서 가장 자주 나오는 건 이 평가 순서입니다.

💡 비유로 이해하기: 출입 통제 보안요원

건물 보안요원에게는 규칙이 있습니다. ① 블랙리스트(명시적 Deny)에 이름이 있으면 무조건 돌려보냅니다 — VIP 패스가 있어도 소용없습니다. ② 블랙리스트에 없으면 출입 허가 명단(명시적 Allow)을 확인합니다. ③ 허가 명단에도 없으면? 기본은 "모르는 사람은 못 들어감"(묵시적 Deny)입니다. 그래서 아무 정책도 없는 새 사용자는 아무 것도 못 합니다.

핵심 구성요소 4가지를 구분하세요. 시험 보기에서 "어떤 것을 EC2에 붙여야 하나?" 같은 질문으로 변형됩니다.

구성요소무엇인가핵심 포인트
사용자(User)사람 또는 개별 자격증명. 장기 자격증명(비밀번호·액세스 키) 보유루트 사용자는 일상 사용 금지, MFA 필수
그룹(Group)사용자 묶음. 정책을 그룹에 붙이면 소속 사용자에 일괄 적용권한 관리 단위 — 그룹은 다른 그룹에 중첩 불가
역할(Role)"임시로 빌려 쓰는" 권한 꾸러미. 장기 키가 없음EC2·Lambda·교차 계정·페더레이션에 권한 부여
정책(Policy)권한을 정의한 JSON 문서위 셋에 "붙여서(attach)" 권한을 부여

✅ 핵심 정리: 평가 순서는 외워라

명시적 Deny > 명시적 Allow > 묵시적 Deny(기본 거부). 단 하나의 정책이라도 Deny를 내리면, 다른 모든 Allow를 무시하고 거부됩니다. "Deny가 항상 이긴다"가 한 줄 요약입니다.

📝 시험에 이렇게 나온다

"사용자에게 S3 전체 권한 Allow 정책과, 특정 버킷 Deny 정책이 동시에 붙어 있다. 그 버킷에 접근할 수 있는가?" → 불가. 명시적 Deny가 명시적 Allow를 항상 무력화합니다. 키워드 "deny" + "allow" 충돌 = Deny 승리.

2. IAM 정책 JSON 해부 — Effect · Action · Resource · Condition

IAM 정책은 JSON 문서입니다. 시험은 정책을 읽고 "이게 무엇을 허용/거부하는가"를 묻습니다. 핵심 4요소만 알면 대부분 읽힙니다.

  • Effect: Allow 또는 Deny
  • Action: 허용/거부할 API 동작 (예: s3:GetObject, ec2:*)
  • Resource: 대상 리소스의 ARN (Amazon 리소스 이름)
  • Condition(선택): 조건. 특정 IP·MFA·태그일 때만 적용 등 세밀 제어
자격증명 기반 정책 — S3 특정 버킷 읽기 + IP 조건
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadShopBucketFromOffice",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:ListBucket"
      ],
      "Resource": [
        "arn:aws:s3:::shop-assets",
        "arn:aws:s3:::shop-assets/*"
      ],
      "Condition": {
        "IpAddress": { "aws:SourceIp": "203.0.113.0/24" }
      }
    }
  ]
}

⚠️ "Version": "2012-10-17"은 정책 언어 버전이라 날짜가 옛날이어도 현행 최신입니다(고정값). 버킷 자체(ListBucket)와 객체(GetObject)는 ARN을 따로 써야 합니다 — 객체에는 /*가 붙습니다.

정책은 "어디에 붙느냐"로 두 종류로 나뉩니다. 이 구분이 시험 단골입니다.

구분자격증명 기반 정책
(Identity-based)		리소스 기반 정책
(Resource-based)
붙는 곳User · Group · Role리소스 자체(S3 버킷, SQS, KMS 키 등)
Principal 필드없음(주체가 곧 붙은 대상)있음 — "누가" 접근 가능한지 명시
대표 예IAM 정책S3 버킷 정책, KMS 키 정책
교차 계정역할 위임으로 처리다른 계정 Principal을 직접 허용 가능

⚠️ 자주 헷갈리는 함정

리소스 기반 정책에는 Principal이 있고, 자격증명 기반 정책에는 없습니다. "Principal 필드가 보이는가?"로 둘을 즉시 구분하세요. S3 버킷 정책에서 다른 계정을 허용하면, 역할(AssumeRole) 없이도 교차 계정 접근이 됩니다.

3. IAM 역할과 STS — 액세스 키를 코드에 박지 마라

가장 흔한 실무 사고는 EC2 안에 액세스 키를 하드코딩하는 것입니다. 키가 유출되면 끝장입니다. 정답은 IAM 역할(Role)입니다. EC2·Lambda에 역할을 붙이면, AWS가 STS(Security Token Service)로 자동 교체되는 임시 자격증명을 발급해 주입합니다. 키를 코드에 둘 이유가 사라집니다.

💡 비유로 이해하기: 마스터키 복사 vs 임시 방문증

액세스 키를 코드에 박는 건 건물 마스터키를 복사해 책상 위에 붙여두는 것과 같습니다. 누가 사진만 찍어도 영구히 위험합니다. IAM 역할은 안내데스크에서 받는 임시 방문증 — 몇 시간 뒤 자동 만료되고, 잃어버려도 곧 무효가 됩니다. 그래서 키 유출 리스크가 근본적으로 줄어듭니다.

AssumeRole과 교차 계정 접근: A 계정의 사용자가 B 계정의 리소스에 접근해야 할 때, B 계정에 역할을 만들고 "A 계정이 이 역할을 맡을 수 있다"는 신뢰 정책(Trust Policy)을 설정합니다. A 계정 주체가 sts:AssumeRole을 호출하면 B 계정 권한의 임시 토큰을 받습니다.

신뢰 정책 — EC2 서비스가 이 역할을 맡도록 허용
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "Service": "ec2.amazonaws.com" },
      "Action": "sts:AssumeRole"
    }
  ]
}
방식자격증명 수명적합한 상황
IAM 사용자 액세스 키장기(영구) — 수동 교체AWS 외부의 레거시 도구 등 불가피한 경우만
IAM 역할 + STS임시(자동 만료·교체)EC2·Lambda·ECS·교차 계정·SSO (권장)

📝 시험에 이렇게 나온다

"EC2의 애플리케이션이 S3에 접근해야 한다. 가장 안전한 방법은?" → IAM 역할을 EC2 인스턴스 프로파일로 부여. "액세스 키를 환경변수에 저장" / "키를 코드에 포함" 보기는 전부 오답입니다. 키워드 "EC2 + 접근 + 안전/보안" = IAM Role.

4. 멀티 계정 거버넌스 — Organizations와 SCP 가드레일

회사가 커지면 계정 하나로는 부족합니다(운영·개발·결제 분리, 폭발 반경 격리). AWS Organizations는 여러 계정을 묶어 일괄 관리하고 결제를 통합(Consolidated Billing)합니다. 그 위에서 권한의 상한선을 거는 도구가 SCP(Service Control Policy, 서비스 제어 정책)입니다.

💡 비유로 이해하기: 회사 지출 한도(상한선)

팀장이 팀원에게 "이 카드 마음껏 써"라고 권한(IAM Allow)을 줘도, 회사 차원의 지출 한도(SCP)가 "월 100만원까지"라면 그 위로는 절대 못 씁니다. SCP는 권한을 부여하지 않습니다 — 오직 상한(가드레일)만 정합니다. 실제 권한은 여전히 IAM 정책으로 줘야 합니다.

이 "교집합" 개념이 핵심입니다. 최종 권한 = SCP가 허용한 범위 ∩ IAM이 허용한 범위. 어느 한쪽이라도 막으면 차단됩니다.

질문SCPIAM 정책
적용 대상멤버 계정(또는 OU) 전체개별 User·Group·Role
권한을 부여하나?아니오 — 상한만 설정예 — 실제 Allow를 부여
루트 사용자에 적용?예 — 멤버 계정 루트도 제한아니오 — 루트는 IAM으로 못 막음
비유회사 지출 한도개인에게 준 카드 권한

⚠️ 자주 헷갈리는 함정

SCP는 멤버 계정에만 적용되며, 조직의 관리(management) 계정에는 적용되지 않습니다 — 관리 계정의 사용자·역할·루트는 SCP로 제한할 수 없습니다. 그래서 관리 계정은 워크로드 없이 조직 관리용으로만 쓰는 것이 모범 사례입니다.

📝 시험에 이렇게 나온다

"모든 멤버 계정에서 특정 리전 사용을 금지하거나, 멤버 계정의 루트 사용자조차 특정 행동을 못 하게 하라." → SCP. "여러 계정의 권한 상한을 중앙에서 통제" 키워드 = Organizations + SCP. IAM 정책으로는 계정 단위·루트 제한이 불가능합니다.

5. 암호화와 KMS — 전송 중 · 저장 중 · 봉투 암호화

보안 도메인의 또 다른 축은 암호화입니다. 두 종류를 구분하세요. 전송 중 암호화(in transit)는 네트워크를 오가는 데이터를 보호(TLS/SSL/HTTPS)하고, 저장 중 암호화(at rest)는 디스크에 놓인 데이터를 보호합니다. AWS에서 저장 중 암호화의 중심이 KMS(Key Management Service)입니다.

💡 비유로 이해하기: 봉투 암호화 = 금고 속 작은 열쇠

큰 데이터를 KMS 마스터키로 직접 암호화하면 느립니다. 그래서 봉투 암호화(Envelope Encryption)를 씁니다: ① 빠른 데이터 키(DEK)로 실제 데이터를 암호화하고, ② 그 데이터 키 자체를 KMS 마스터키(KEK)로 암호화해 데이터 옆에 봉인합니다. 마치 방 열쇠(DEK)는 데이터와 함께 두되, 그 열쇠를 금고(KMS)에 넣어 잠그는 셈입니다. 금고를 못 열면 방 열쇠도 못 꺼냅니다.

S3 서버측 암호화(SSE) 옵션은 "키를 누가 관리하느냐"로 갈립니다. 비교 표가 시험 단골입니다.

방식키 관리 주체핵심 특징 · 언제
SSE-S3AWS가 전부 관리가장 간단. 키 제어 불필요한 기본 암호화
SSE-KMSAWS KMS 키(고객 관리 가능)감사 로그(CloudTrail)·키 접근 제어·교체가 필요할 때
SSE-C고객이 키를 직접 제공·관리키를 AWS에 맡기기 싫을 때(요청마다 키 전달)

✅ 핵심 정리: 키 감사·제어가 필요하면 KMS

"누가 언제 이 키를 썼는지 추적(CloudTrail)"하거나 "키 사용 권한을 IAM/키 정책으로 제어"해야 하면 SSE-KMS. 아무 것도 신경 쓰기 싫으면 SSE-S3. 키를 외부에서 갖고 오면 SSE-C.

📝 시험에 이렇게 나온다

"규정 준수를 위해 키 사용 내역을 감사하고 키 교체·접근을 통제해야 한다." → SSE-KMS(또는 KMS 고객 관리 키). 키워드 "감사/audit/CloudTrail/키 회전" = KMS. 단순 "저장 중 암호화만" 하면 SSE-S3로 충분.

6. 비밀 관리 — Secrets Manager vs Parameter Store

DB 비밀번호·API 키 같은 비밀(Secret)을 코드나 환경변수에 평문으로 두면 안 됩니다. AWS는 두 가지 보관소를 제공하는데, 시험은 "둘 중 무엇?"을 묻습니다. 결정적 차이는 자동 교체(rotation)입니다.

구분Secrets ManagerSystems Manager Parameter Store
자동 교체(rotation)내장 지원(Lambda로 DB 비번 주기 교체)기본 없음(직접 구현 필요)
비용비밀당 유료(종량제)표준 파라미터는 무료
주 용도교체가 중요한 DB·API 자격증명설정값·환경변수, 비교적 단순한 비밀
RDS 연동RDS·Aurora와 긴밀 통합(자동 교체)SecureString으로 KMS 암호화 저장

✅ 핵심 정리: "자동 교체"가 키워드면 Secrets Manager

DB 비밀번호를 주기적으로 자동 교체해야 하면 Secrets Manager. 단순 설정값 저장이나 비용 최소화가 목적이면 Parameter Store(SecureString). 둘 다 평문 환경변수보다 안전하며, 애플리케이션은 IAM 역할로 접근합니다(섹션 3).

📝 시험에 이렇게 나온다

"RDS 자격증명을 30일마다 자동으로 교체하라." → Secrets Manager(rotation). "수백 개의 설정값을 비용 없이 계층적으로 저장하라." → Parameter Store. 키워드 "rotation/자동 교체" = Secrets Manager가 거의 항상 정답.

7. 엣지 · 위협 방어 개요 — 인증 · L7/DDoS · 탐지

마지막으로 도메인 1에 자주 섞여 나오는 보안 서비스들의 역할 구분입니다. 이름이 비슷해 헷갈리지만, "무엇을 막거나 탐지하는가"로 나누면 깔끔합니다. 각 서비스의 한 줄 역할만 확실히 외우면 보기에서 바로 골라낼 수 있습니다.

서비스분류한 줄 역할
Cognito인증·자격증명웹·모바일 앱의 사용자 로그인/가입, 소셜·SAML 페더레이션
WAFL7 방어HTTP(애플리케이션 계층) SQL 인젝션·XSS 등 웹 공격 필터링
ShieldDDoS 방어DDoS 공격 완화(Standard 자동 무료, Advanced 유료 고급)
GuardDuty위협 탐지로그(VPC·CloudTrail·DNS) 분석으로 이상 행위 탐지(에이전트 불필요)
Inspector취약점 평가EC2·컨테이너 이미지의 알려진 취약점(CVE) 스캔

⚠️ 자주 헷갈리는 함정

WAF(웹 공격 차단·예방) vs GuardDuty(이상 행위 탐지)를 섞지 마세요. WAF는 들어오는 요청을 막고(prevent), GuardDuty는 이미 일어난 위협을 알아챕니다(detect). Inspector(소프트웨어 취약점 스캔) vs GuardDuty(악성 행위 탐지)도 다릅니다 — Inspector는 "구멍이 있나", GuardDuty는 "누가 침입 중인가".

📝 시험에 이렇게 나온다

"애플리케이션 계층의 SQL 인젝션·XSS를 차단" → WAF. "대규모 DDoS로부터 보호" → Shield. "계정에서 비정상 API 호출·암호화폐 채굴 등 위협을 탐지" → GuardDuty. "모바일 앱 사용자 인증/가입 관리" → Cognito.
