핵심 — 그라데이션 + 글래스모피즘 카드

화면 전체를 덮는 부드러운 그라데이션 배경 위에, 반투명 카드를 얹는 게 시그니처입니다. Flutter에선 위젯 조합만으로 이걸 그립니다.

ContainerBoxDecoration LinearGradientBackdropFilter GestureDetector
reflectly_card.dart
// 그라데이션 배경 — CSS의 linear-gradient에 해당
Container(
  decoration: BoxDecoration(
    gradient: LinearGradient(
      begin: Alignment.topCenter,
      end: Alignment.bottomCenter,
      colors: [Color(0xFF6D5DD3), Color(0xFFB89BF0)],
    ),
  ),
  child: GestureDetector(            // 탭 감지
    onTap: () => _openJournal(),
    child: ClipRRect(             // 모서리 둥글게 자르기
      borderRadius: BorderRadius.circular(20),
      child: BackdropFilter(       // 반투명 블러(글래스 효과)
        filter: ImageFilter.blur(sigmaX: 8, sigmaY: 8),
        child: Text('오늘의 저널 쓰기'),
      ),
    ),
  ),
)
React 매핑: BoxDecoration + LinearGradient = CSS background: linear-gradient(), BackdropFilter.blur = CSS backdrop-filter: blur(), GestureDetector = onClick 핸들러.
면접 활용: "Reflectly 스타일의 글래스모피즘 카드를 BackdropFilter와 BoxDecoration 조합으로 구현해봤습니다" — 시각적 완성도를 어필할 수 있는 포인트.

StreamBuilderTweenAnimationBuilder CardCustomPaintfl_chart

// 실시간 통계 — 서버 스트림을 구독해 자동 갱신
StreamBuilder<Stats>(
  stream: adsRepo.liveStats(),     // 실시간 데이터 흐름
  builder: (context, snap) {
    final imp = snap.data?.impressions ?? 0;
    // 숫자가 0 → 목표값으로 부드럽게 카운트업
    return TweenAnimationBuilder<int>(
      tween: IntTween(begin: 0, end: imp),
      duration: Duration(milliseconds: 900),
      builder: (_, value, __) => Text(
        '$value',
        style: TextStyle(fontSize: 24, fontWeight: FontWeight.bold),
      ),
    );
  },
)
React 매핑: StreamBuilder = WebSocket/SSE 구독 + 상태 갱신, TweenAnimationBuilder = react-spring/framer-motion의 숫자 애니메이션, fl_chart = recharts/chart.js.
면접 활용: "이탈 지점 분석 대시보드를 StreamBuilder로 실시간 갱신하고, 지표 변화를 TweenAnimationBuilder로 시각화해 사용자가 변화를 직관적으로 인지하게 만들 수 있습니다."

핵심 — 상태 동기화 + 디바이스 연동

차량(IoT)에서 오는 실시간 상태(배터리·위치)를 앱에 반영하고, 앱에서 차량으로 명령을 보냅니다. 전역 상태관리가 필수예요.

bmw_vehicle.dart
// 차량 상태를 전역 관리 (여러 화면이 공유) — Notifier (Riverpod 3 표준)
final vehicleProvider = NotifierProvider<
    VehicleNotifier, VehicleState>(VehicleNotifier.new);

class VehicleNotifier extends Notifier<VehicleState> {
  @override
  VehicleState build() => VehicleState.initial();

  // 차량에 잠금 명령 전송 → 응답으로 상태 갱신
  Future<void> lockDoors() async {
    state = state.copyWith(isLocking: true);
    await api.sendCommand(Command.lock);
    state = state.copyWith(isLocked: true, isLocking: false);
  }
}

// UI에서 구독 → 배터리 변화 시 자동 리빌드
final battery = ref.watch(vehicleProvider).batteryLevel;
React 매핑: NotifierProvider = Redux store + 액션, copyWith = 불변 상태 업데이트({...state, isLocked:true}), ref.watch = useSelector.
면접 활용: "여러 화면이 공유하는 상태는 Riverpod의 Notifier로 단방향 관리하고, 비동기 명령은 로딩→성공 상태를 명시적으로 전이시킵니다." — 아키텍처 설계 역량 어필.

레슨 완료 시 XP가 튀어오르고, 노드가 잠금 해제되는 성취감의 시각화가 생명입니다. 면접에서 이 화면을 "이렇게 만들겠다"고 설명할 수 있어야 해요.

streak_lesson.dart
// 스트릭 상태 — 자정 리셋 로직 포함, 전역 관리 (Notifier · Riverpod 3 표준)
final streakProvider = NotifierProvider<StreakNotifier, int>(
  StreakNotifier.new);

class StreakNotifier extends Notifier<int> {
  @override
  int build() { _loadAndCheck(); return 0; }

  // 마지막 학습일이 어제면 연속, 그 전이면 0으로 리셋
  void completeToday() {
    final last = _prefs.lastStudyDate;
    if (_isYesterday(last)) state = state + 1;  // 스트릭 +1
    else if (!_isToday(last)) state = 1;       // 끊김 → 재시작
    _prefs.lastStudyDate = DateTime.now();
  }
}

// 레슨 노드 — 완료 시 통통 튀는 보상 애니메이션
AnimatedScale(
  scale: isCompleted ? 1.0 : 0.85,
  duration: Duration(milliseconds: 300),
  curve: Curves.elasticOut,        // 탄성 효과(통통)
  child: LessonNode(icon: Icons.star),
)
React 매핑: AnimatedScale + Curves.elasticOut = framer-motion spring 애니메이션, Lottie = lottie-react(보상 폭죽 효과), Notifier = Redux/Zustand 스토어.
⭐ 면접 결정타: "스트릭은 자정 리셋·연속 판정 로직을 Notifier에 캡슐화하고 로컬에 영속화하며, 레슨 완료 보상은 AnimatedScale의 elasticOut 커브나 Lottie로 성취감을 극대화합니다. 오프라인 학습 후 서버 동기화도 큐로 처리합니다." → 이 한 단락이면 게이미피케이션 이해도를 완벽히 증명합니다.

핵심 — PageView 단계 전환 + 진행 상태

여러 단계를 좌우로 넘기고, 각 단계의 선택을 모아 마지막에 서버로 보냅니다. 진행 표시줄로 "거의 다 왔다"는 동기를 부여하는 게 포인트.

PageViewPageController AnimatedSwitcherStepperRiverpod
onboarding_flow.dart
// 온보딩 단계를 좌우로 넘기는 PageView
final _controller = PageController();

PageView(
  controller: _controller,
  physics: NeverScrollableScrollPhysics(),  // 버튼으로만 이동
  onPageChanged: (i) => ref.read(onboardingProvider.notifier).setStep(i),
  children: [
    MotivationStep(),   // 1. 동기 질문
    GoalStep(),         // 2. 일일 목표(5분/10분/15분)
    PlacementStep(),    // 3. 레벨 진단(건너뛰기 가능)
    FirstRewardStep(),  // 4. 첫 보상 → 가입 유도
  ],
);

// "계속" 버튼 → 다음 단계로 부드럽게 이동
void next() => _controller.nextPage(
  duration: Duration(milliseconds: 350),
  curve: Curves.easeOutCubic,
);
React 매핑: PageView + PageController = 스텝 캐러셀(react-swipeable-views), onPageChanged로 단계별 선택을 전역 상태에 누적하는 건 멀티스텝 폼의 상태 관리와 동일합니다.
면접 활용: "온보딩은 PageView로 단계를 구성하고 선택값을 Riverpod에 누적해 마지막에 한 번에 제출합니다. 진행 표시줄과 '건너뛰기' 옵션으로 이탈을 줄이고, A/B 테스트로 단계 순서를 최적화합니다."

UI는 Repository만 알면 됨 (관심사 분리)

설계 핵심: UI가 HTTP를 직접 부르지 않습니다. Repository 패턴으로 "데이터를 어디서 가져오는지"를 UI에서 숨겨, 서버가 REST든 GraphQL이든 UI 코드는 그대로예요. 백엔드를 아는 사람이 설계하는 방식입니다.

핵심 — Dio + Repository + 토큰 인터셉터

api_client.dart
// 모든 요청에 토큰 자동 첨부 + 401 시 갱신 (인터셉터)
dio.interceptors.add(InterceptorsWrapper(
  onRequest: (options, handler) {
    options.headers['Authorization'] = 'Bearer $token';
    handler.next(options);
  },
  onError: (e, handler) async {
    if (e.response?.statusCode == 401) {
      await _refreshToken();        // 토큰 갱신 후 재시도
      return handler.resolve(await _retry(e.requestOptions));
    }
    handler.next(e);
  },
));

// Repository — UI는 이것만 호출 (출처를 모름)
class LessonRepository {
  Future<List<Lesson>> getLessons() async {
    final res = await _api.get('/lessons');
    return (res.data as List).map(Lesson.fromJson).toList();
  }
}
graphql_query.dart
// GraphQL — 필요한 필드만 골라 요청 (오버페칭 방지)
const q = '''
  query GetProgress(\$userId: ID!) {
    user(id: \$userId) {
      streak
      xp
      lessons { id title completed }
    }
  }
''';
final result = await client.query(QueryOptions(document: gql(q)));
React 매핑: Dio + Interceptor = axios 인터셉터, Repository = API 서비스 레이어/커스텀 훅, graphql_flutter = Apollo Client. 토큰 자동 갱신 로직은 양쪽이 동일합니다.
⭐ 면접 결정타: "Spring으로 REST·GraphQL API를 직접 설계·구현해봤기 때문에, 프론트에서 Repository 패턴으로 관심사를 분리하고 인터셉터로 인증·에러를 일괄 처리합니다. 오버페칭이 문제면 GraphQL로, 단순 CRUD면 REST로 — 백엔드 트레이드오프를 알고 프론트를 설계할 수 있습니다." → 백엔드+프론트를 잇는 유일한 강점.

프론트에서 각 단계 진입/이탈을 이벤트로 기록하고, 분석 도구로 보냅니다. 이 데이터가 곧 개선의 근거.

// 각 온보딩 단계 진입을 이벤트로 기록
void logStep(String step) {
  analytics.logEvent(

// 화면 전환을 자동 추적하는 RouteObserver
class AnalyticsObserver extends RouteObserver<PageRoute> {
  @override
  void didPush(Route route, Route? prev) {
    super.didPush(route, prev);
    analytics.setCurrentScreen(screenName: route.settings.name);
  }
}

// 이탈률 = 1 − (다음단계 진입 / 현재단계 진입)

React 매핑: Firebase Analytics/Amplitude는 웹과 동일 SDK, RouteObserver = React Router의 페이지뷰 추적 미들웨어. 퍼널 차트는 recharts와 같은 발상입니다.
면접 활용: "각 단계에 이벤트 로깅을 심어 퍼널을 집계하고, 이탈이 큰 구간에 가설을 세워 A/B 테스트로 검증합니다. 예를 들어 동기 선택 단계 이탈이 높으면 질문을 가볍게 바꾸거나 순서를 뒤로 미뤄 비교합니다." → "데이터 기반 반복" 문화에 정확히 부합.

// 너비에 따라 레이아웃을 분기 (반응형의 핵심)
LayoutBuilder(
  builder: (context, constraints) {
    if (constraints.maxWidth >= 600) {
      // 태블릿: 사이드바 + 그리드
      return Row(children: [
        NavigationRail(destinations: _navItems),  // 좌측 메뉴
        Expanded(child: LessonGrid(columns: 2)),
      ]);
    }
    // 폰: 하단 탭 + 1열
    return Scaffold(
      body: LessonGrid(columns: 1),
      bottomNavigationBar: NavigationBar(destinations: _navItems),
    );
  },
)
React 매핑: LayoutBuilder = CSS 미디어 쿼리 / useMediaQuery 훅, NavigationRail↔NavigationBar 전환 = 반응형 사이드바↔하단바. 같은 데이터로 레이아웃만 바꾸는 발상이 동일합니다.
면접 활용: "LayoutBuilder로 600dp 브레이크포인트를 잡아 폰은 NavigationBar, 태블릿은 NavigationRail로 전환하고 그리드 열 수를 조정합니다. 로직은 공유하고 레이아웃 위젯만 분기해 유지보수성을 지킵니다."

Q. 기획자·디자이너와 의견이 충돌하면 어떻게 푸나요?▶
협업 · 갈등 해결

"먼저 충돌의 층위를 구분합니다. 취향 문제인지, 데이터로 답할 수 있는 문제인지요. 데이터로 답할 수 있으면 A/B 테스트나 사용성 지표로 결정하자고 제안합니다. 취향·방향성 문제면 각자의 의도와 우려를 명확히 한 뒤, 사용자 가치 기준으로 좁힙니다. 기술적 제약(성능·일정)이 있으면 대안을 2~3개 만들어 트레이드오프를 같이 보게 합니다. 제 역할은 '안 된다'가 아니라 '이 방향이면 이 비용, 저 방향이면 저 비용'을 투명하게 보여주는 것이라 생각합니다."

Q. 디자이너가 Flutter로 구현하기 어려운 디자인을 요청하면?▶
기술 협업

"무조건 거절하지 않습니다. 먼저 구현 난이도와 성능 비용을 솔직히 공유하고, 의도(왜 이 효과가 필요한지)를 묻습니다. 의도가 '생동감'이라면, Rive나 Lottie로 더 가볍게 같은 느낌을 낼 대안을 제시합니다. Flutter는 커스텀 페인팅(CustomPaint)으로 거의 모든 디자인이 가능하지만, 60fps를 깨지 않는 선을 함께 정하는 게 중요합니다. 디자인 시스템을 공통 위젯/토큰으로 컴포넌트화해두면 이런 협의 자체가 줄어듭니다."

Q. 데이터 기반으로 개선한 경험을 말해주세요.▶
데이터 기반 반복

"개선은 측정 → 가설 → 실험 → 검증 사이클로 접근합니다. 예를 들어 학습 앱에서 '온보딩 완료율이 낮다'는 지표를 봤다면, 퍼널을 쪼개 어느 단계 이탈이 큰지 특정합니다. 동기 선택 단계 이탈이 높다는 가설이 서면, 질문을 가볍게 바꾼 버전과 원본을 A/B로 돌려 완료율을 비교합니다. 통계적으로 유의미하면 적용하고, 아니면 다음 가설로 넘어갑니다. 한 번에 하나씩 바꿔 인과를 명확히 하는 게 핵심입니다."

Q. 프론트엔드 리드로서 코드 품질과 일정을 어떻게 균형 잡나요?▶
리더십 · 아키텍처

"전부 완벽하게 갈 수 없으니 핵심 경로와 주변부를 구분합니다. 결제·학습 플로우 같은 핵심은 테스트와 리뷰를 엄격히, 실험적 기능은 빠르게 내보고 데이터로 검증합니다. 기술 부채는 숨기지 않고 가시화해 백로그로 관리하고, 스프린트마다 일정 비율을 상환에 배정합니다. 또 공통 위젯·아키텍처 컨벤션(폴더 구조, 상태관리 규칙)을 문서화해두면 팀 전체 속도가 올라가 장기적으로 일정도 지켜집니다."

Q. React 경험은 있지만 Flutter 리드는 처음인데, 괜찮을까요?▶
⭐ 약점 정면 돌파

★ "프론트엔드 설계 원칙은 프레임워크를 초월합니다. 상태 관리, 컴포넌트 합성, 리렌더 최적화, 관심사 분리 — 이 사고방식은 React에서 충분히 단련했고, Flutter에 1:1로 매핑됩니다(useState↔setState, Context↔Riverpod, 가상DOM↔위젯트리). 문법은 학습 곡선이 짧고, 실제로 토이 프로젝트로 검증했습니다. 게다가 Spring 백엔드를 직접 만들어본 경험은 API 설계까지 이해한 프론트 리드라는 흔치 않은 강점이라, 팀의 프론트-백엔드 협업을 매끄럽게 만들 수 있습니다."
