A3. SAA③ 스토리지·데이터베이스

SAA-C03(2026 기준) 시험에서 가장 문항이 많이 쏟아지는 영역입니다. S3·EBS·EFS 같은 스토리지와 RDS·Aurora·DynamoDB 같은 데이터베이스를 "어떤 요구사항엔 어떤 서비스"라는 선택 기준으로 정리합니다. 주로 고성능 아키텍처(24%)와 비용 최적화(20%) 도메인에 직결되며, 내구성·동기/비동기 복제 같은 단골 함정도 함께 짚습니다.

1. S3 기초와 내구성

Amazon S3는 파일을 폴더 트리가 아니라 객체(object) 단위로 저장하는 객체 스토리지입니다. 각 객체는 버킷(bucket) 안에 키(key, 파일 경로처럼 보이는 이름)와 값(데이터), 메타데이터로 들어갑니다. 용량은 사실상 무제한이고 단일 객체는 최대 5TB까지 저장됩니다. EBS·EFS처럼 서버에 마운트하는 게 아니라 HTTP API로 접근한다는 점이 핵심 차이입니다.

💡 비유로 이해하기: 무한 셀프 보관함

EBS가 "내 책상에 붙은 서랍"(한 서버에 붙는 디스크)이라면, S3는 "주소만 알면 누구나 택배로 물건을 넣고 빼는 무한 보관 창고"입니다. 서랍은 책상(인스턴스)에 종속되지만, 창고는 인터넷 주소(URL)만 있으면 어디서든 접근합니다. 그래서 정적 파일·백업·로그·데이터 레이크의 기본 저장소로 쓰입니다.

내구성(durability)은 데이터가 소실되지 않을 확률입니다. S3는 데이터를 한 리전의 여러 가용 영역(AZ)에 자동 복제해 99.999999999%(11 9s) 내구성을 제공합니다(One Zone 클래스는 단일 AZ라 AZ 장애에 약함). 내구성과 가용성(availability, 지금 읽을 수 있는가)은 다른 지표라는 점을 시험에서 자주 구분시킵니다.

보안은 기본적으로 비공개입니다. 실수로 인터넷에 노출되는 사고를 막기 위해 계정·버킷 수준의 S3 블록 퍼블릭 액세스(Block Public Access)가 기본 활성화되어 있고, 접근 제어는 IAM 정책·버킷 정책·(레거시) ACL로 합니다. 버저닝(Versioning)을 켜면 같은 키에 덮어써도 이전 버전이 보존되어 실수 삭제·랜섬웨어 복구에 대비할 수 있습니다.

📝 시험에 이렇게 나온다

"실수로 객체를 덮어쓰거나 삭제해도 복구하고 싶다" → 버저닝 활성화(+ 강제 삭제 방지엔 MFA Delete·Object Lock). "버킷이 의도치 않게 공개되지 않게" → 블록 퍼블릭 액세스. "S3의 내구성은?" → 11 9s(여러 AZ 복제).

2. S3 스토리지 클래스와 수명주기

같은 S3여도 접근 빈도에 따라 더 싼 클래스로 옮기면 비용이 크게 줄어듭니다. 자주 읽는 데이터는 Standard, 가끔 읽는 데이터는 IA, 거의 안 보는 장기 보관은 Glacier 계열입니다. 클래스가 저렴해질수록 저장 비용은 내려가지만 꺼내는 비용·복원 지연이 붙는다는 트레이드오프를 기억하세요.

클래스AZ적합 용도특징
S3 Standard다중자주 접근하는 활성 데이터기본값, 꺼내기 비용 없음
Standard-IA다중가끔 접근, 즉시 필요저장↓·검색(retrieval) 비용 발생
One Zone-IA단일재생성 가능한 보조 사본더 저렴하나 AZ 장애에 취약
Intelligent-Tiering다중접근 패턴이 들쭉날쭉/예측 불가AWS가 자동으로 계층 이동, 모니터링 요금
Glacier Instant Retrieval다중분기 1회 접근 아카이브, 즉시 필요밀리초 검색
Glacier Flexible Retrieval다중장기 보관, 분~시간 대기 가능분~시간 단위 복원
Glacier Deep Archive다중규정상 수년 보관(거의 안 읽음)최저가, 복원 수 시간(~12h)
S3 Express One Zone단일지연 민감 고빈도 액세스한 자릿수 ms, 단일 AZ 고성능

수명주기(Lifecycle) 정책은 "객체가 N일 지나면 자동으로 더 싼 클래스로 옮기거나 삭제"하는 규칙입니다. 예를 들어 로그를 30일 후 Standard-IA, 90일 후 Glacier로 보내고 365일 후 만료(삭제)시킬 수 있습니다. 사람이 수동으로 옮기지 않아도 되므로 비용 최적화 도메인의 단골 정답입니다.

수명주기 규칙 예시 (로그 자동 강등·만료)
{
  "Rules": [
    {
      "ID": "log-archive-then-expire",
      "Filter": { "Prefix": "logs/" },
      "Status": "Enabled",
      "Transitions": [
        { "Days": 30,  "StorageClass": "STANDARD_IA" },
        { "Days": 90,  "StorageClass": "GLACIER" }
      ],
      "Expiration": { "Days": 365 }
    }
  ]
}

📝 시험에 이렇게 나온다

"접근 패턴을 예측할 수 없는데 비용은 최적화" → Intelligent-Tiering. "규정상 7년 보관, 거의 안 꺼냄, 최저가" → Glacier Deep Archive. "오래된 객체를 자동으로 더 싼 계층으로" → 수명주기 정책. "재생성 가능한 썸네일을 가장 싸게" → One Zone-IA.

3. 블록·파일 스토리지 (EBS · EFS · FSx)

S3가 객체 스토리지라면, 서버에 디스크처럼 붙이는 것은 블록 스토리지, 여러 서버가 동시에 공유하는 것은 파일 스토리지입니다.

  • EBS(Elastic Block Store): EC2 한 대에 붙는 네트워크 블록 볼륨. OS·DB 데이터 디스크로 쓰며, 기본적으로 한 AZ에 종속되고 보통 한 인스턴스에 부착(io1/io2 Multi-Attach 예외)됩니다. 범용 기본 권장 타입은 gp3(IOPS·처리량을 용량과 독립적으로 설정), 초고성능·고내구가 필요하면 io2입니다.
  • EFS(Elastic File System): NFS 기반 공유 파일 시스템. 여러 AZ의 여러 EC2가 동시에 마운트해 같은 파일을 읽고 씁니다(리눅스). 용량 자동 확장.
  • FSx: 특정 워크로드용 관리형 파일 시스템 — FSx for Windows File Server(SMB·윈도우 공유), FSx for Lustre(HPC·머신러닝 초고성능) 등.
  • 인스턴스 스토어(Instance Store): 호스트에 물리적으로 붙은 임시 디스크. 매우 빠르지만 인스턴스를 중지/종료하면 데이터가 사라지는 휘발성이라 캐시·스크래치 용도로만.

💡 비유로 이해하기: 외장 SSD vs 공유 NAS vs 책상 위 메모지

EBS는 내 노트북에만 꽂는 외장 SSD(한 번에 한 대), EFS는 사무실 모두가 동시에 접근하는 공유 NAS, 인스턴스 스토어는 컴퓨터 끄면 사라지는 책상 위 임시 메모지입니다. "동시에 여러 서버가 같은 파일"이 키워드면 EFS, "한 서버의 디스크"면 EBS입니다.

구분EBSEFS인스턴스 스토어
유형블록파일(NFS)블록(로컬)
동시 부착보통 1개 인스턴스다수 인스턴스·다수 AZ해당 호스트만
범위단일 AZ리전(다중 AZ)인스턴스 수명
지속성영속(스냅샷은 S3)영속휘발성(중지 시 소실)

스냅샷(Snapshot)은 EBS 볼륨의 시점 백업으로 내부적으로 S3에 증분 저장됩니다. 스냅샷으로 다른 AZ·리전에 볼륨을 복원하거나 AMI를 만들 수 있어, 단일 AZ에 묶인 EBS의 가용성·이동성 한계를 보완합니다.

📝 시험에 이렇게 나온다

"여러 EC2가 동시에 같은 파일 시스템 공유(리눅스)" → EFS. "비용·성능 균형의 범용 EBS 기본" → gp3. "EBS를 다른 AZ로 옮기거나 백업" → 스냅샷. "윈도우 SMB 공유" → FSx for Windows, "ML/HPC 초고속" → FSx for Lustre.

4. RDS 핵심 — Multi-AZ vs Read Replica

Amazon RDS는 MySQL·PostgreSQL·MariaDB·Oracle·SQL Server를 완전관리형으로 돌려주는 관계형 DB 서비스입니다. 백업·패치·장애 복구를 AWS가 맡아 운영 부담이 줄어듭니다. 시험에서 가장 중요한 함정은 Multi-AZ와 Read Replica를 혼동시키는 것입니다 — 둘은 복제하지만 목적이 정반대입니다.

구분Multi-AZ 배포Read Replica(읽기 전용 복제본)
목적고가용성(장애 대비)읽기 성능 확장
복제 방식동기(synchronous)비동기(asynchronous)
대기 인스턴스 사용평시 접근 불가(대기)읽기 쿼리 직접 처리
장애 시자동 장애 조치(failover)(수동 승격 가능)
위치다른 AZ같은/다른 AZ·리전

Multi-AZ는 다른 AZ에 동기 복제된 Standby를 두고, 기본(primary)에 장애가 나면 자동으로 Standby로 전환(failover)합니다. 평소 Standby는 읽기에도 쓰이지 않고 오직 가용성을 위해 대기합니다. 반면 Read Replica는 비동기 복제로 읽기 전용 사본을 여러 개 만들어 읽기 트래픽을 분산합니다(약간의 복제 지연 존재). "읽기 부하가 많다"면 Read Replica, "다운타임을 줄이고 싶다"면 Multi-AZ입니다. 둘은 함께 쓸 수도 있습니다.

⚠️ 자주 틀리는 함정

"Read Replica가 고가용성을 제공한다"는 오답입니다. Read Replica는 비동기라 약간 뒤처질 수 있고 자동 장애 조치 대상이 아닙니다. 가용성·자동 failover는 Multi-AZ(동기)의 몫입니다. 반대로 "Multi-AZ로 읽기 성능을 늘린다"도 오답입니다.

📝 시험에 이렇게 나온다

"읽기 쿼리가 폭증, DB 부하 분산" → Read Replica. "DB 장애 시 다운타임 최소화·자동 복구" → Multi-AZ. "저장 데이터 암호화" → KMS 기반 암호화 활성화(스냅샷·Replica도 함께 암호화).

5. Aurora — 클라우드 네이티브 RDB

Amazon Aurora는 MySQL·PostgreSQL과 호환되면서 AWS가 클라우드에 맞게 재설계한 관계형 DB 엔진입니다. 데이터는 3개 AZ에 6벌로 복제되는 공유 스토리지에 저장되고, 스토리지가 자동으로 확장(최대 128 TiB, 최신 엔진 버전은 그 이상)되어 디스크 용량을 미리 잡을 필요가 없습니다. 같은 워크로드에서 표준 RDS보다 높은 처리량을 목표로 합니다.

  • 읽기 복제본을 최대 15개까지 두고, 장애 시 그중 하나로 빠르게 승격합니다(빠른 failover).
  • Aurora Serverless v2: 트래픽에 따라 용량(ACU)을 잘게 자동 확장/축소합니다. 사용량이 들쭉날쭉하거나 예측이 어려운 워크로드에 적합합니다(v1이 아니라 v2가 현행).
  • Aurora Global Database: 한 리전을 주(primary)로 두고 여러 리전에 저지연으로 복제해, 글로벌 읽기와 리전 장애 시 재해 복구(DR)에 대응합니다.

💡 비유로 이해하기: 알아서 늘어나는 물탱크

일반 RDS가 "처음에 정한 크기의 물탱크"라면, Aurora 스토리지는 "물이 차오르면 벽이 알아서 늘어나는 탱크"입니다. 용량 부족을 걱정하며 미리 크게 잡을 필요가 없죠. 여기에 Serverless v2를 더하면 "수도꼭지(컴퓨트)도 사용량에 맞춰 자동으로 굵어졌다 가늘어졌다" 합니다.

📝 시험에 이렇게 나온다

"MySQL 호환 + 고성능 + 스토리지 자동 확장" → Aurora. "트래픽이 들쭉날쭉, 용량 자동 조절" → Aurora Serverless v2. "여러 리전 저지연 읽기·리전 DR" → Aurora Global Database.

6. DynamoDB — 완전관리 NoSQL

Amazon DynamoDB는 서버를 신경 쓸 필요 없는(서버리스) 키-값/문서형 NoSQL입니다. 어떤 규모에서도 한 자릿수 밀리초 지연을 목표로 하며, 자동으로 여러 AZ에 복제됩니다. 테이블은 파티션 키(partition key)로 데이터를 분산 저장하므로, 키 설계가 성능을 좌우합니다 — 특정 키에 트래픽이 몰리면(핫 파티션) 성능이 떨어지므로 값이 골고루 퍼지는 키를 골라야 합니다.

  • GSI(Global Secondary Index): 기본 키가 아닌 다른 속성으로 조회하게 해주는 인덱스(파티션 키까지 새로 지정 가능). LSI(Local Secondary Index): 같은 파티션 키에 정렬 키만 다르게 두는 인덱스(테이블 생성 시에만 정의).
  • DAX(DynamoDB Accelerator): DynamoDB 앞단의 완전관리 인메모리 캐시로, 읽기를 마이크로초 단위까지 가속합니다(읽기 폭증 시).
  • TTL(Time To Live): 항목에 만료 시각을 지정해 지난 데이터를 자동 삭제(세션·임시 데이터 정리).
  • 용량 모드: 트래픽이 불규칙하면 온디맨드(사용한 만큼), 예측 가능하고 꾸준하면 프로비저닝(미리 용량 지정, Auto Scaling 가능)이 비용 효율적입니다.

⚠️ 자주 틀리는 함정

DynamoDB는 복잡한 조인·집계·트랜잭션 분석에 부적합합니다. "유연한 SQL 조인과 복잡한 쿼리가 필요" → RDS/Aurora가 정답이고, "키 기반 초저지연·대규모 단순 조회·서버리스" → DynamoDB입니다.

📝 시험에 이렇게 나온다

"밀리초 지연·자동 확장·서버 관리 없는 NoSQL" → DynamoDB. "DynamoDB 읽기를 마이크로초로 캐싱" → DAX. "오래된 세션 항목 자동 만료" → TTL. "트래픽 예측 불가, 운영 단순화" → 온디맨드 용량 모드.

7. 캐싱과 데이터베이스 선택 지도

Amazon ElastiCache는 관리형 인메모리 캐시로 DB 앞단에서 반복 조회를 가속하거나 세션을 저장합니다. 두 엔진의 결이 다릅니다 — Redis는 복제·영속성·정렬셋·Pub/Sub 등 기능이 풍부하고(고가용성 캐시·리더보드·세션), Memcached는 단순 키-값 캐시를 멀티스레드로 빠르게 처리합니다(기능은 단순, 수평 분할). "캐시에 고가용성·자료구조가 필요"하면 Redis, "단순 캐시를 가볍게"면 Memcached가 단골 정답입니다.

마지막으로, 요구사항 키워드별 "이 DB를 골라라" 지도를 정리합니다. SAA 시나리오 문제는 결국 이 매핑을 묻습니다.
