Chapter R7: ROS 2 심화 & 시뮬레이션

실제 로봇 없이도 개발하려면 시뮬레이션이 필요합니다. 이 챕터는 여러 좌표계를 트리로 관리하는 TF2(R1의 SE(3) 변환이 그대로 쓰입니다!), 로봇의 몸을 XML로 기술하는 URDF, 그리고 물리 시뮬레이터 Gazebo와 시각화 도구 RViz의 차이를 다룹니다. (ROS·시뮬레이터는 이 환경에서 실행 불가 → 공식 문서 기준 패턴으로 다루되, TF2 변환 트리의 수학은 numpy로 실행 검증합니다.)

1. 왜 시뮬레이션인가

실제 로봇으로만 개발하면 느리고, 비싸고, 위험합니다(망가지면 끝). 시뮬레이션은 가상 환경에서 로봇을 돌려 안전하게·빠르게·무한히 반복해 실험하게 해 줍니다. 시뮬에서 충분히 검증한 뒤 실제 로봇으로 옮기는 것을 sim-to-real이라 합니다(R10).

💡 비유로 이해하기: 비행 시뮬레이터

조종사는 진짜 비행기로 위험한 상황을 연습하지 않습니다 — 시뮬레이터에서 수없이 반복하죠. 로봇도 마찬가지입니다. 이때 Gazebo는 "물리 법칙이 도는 가상 세계(시뮬레이터)"이고, RViz는 "센서·로봇 상태를 들여다보는 계기판(시각화)"입니다 — 둘은 역할이 다릅니다(5절에서 구분).

2. TF2 — 좌표 프레임 트리

로봇엔 좌표계가 많습니다 — 지도(map), 오도메트리 기준(odom), 로봇 몸체(base_link), 센서마다(laser, camera). TF2는 이들을 부모-자식 트리로 관리하고(REP-105 표준 순서 map → odom → base_link → 센서), 임의의 두 프레임 사이 변환을 자동으로 계산해 줍니다. 그 계산이 바로 R1의 동차변환행렬 합성입니다.

고정된 관계(예: 로봇 몸에 볼트로 붙은 라이다)는 정적(static) 변환, 시간에 따라 변하는 관계(예: 움직이는 로봇의 odom→base_link, R4의 오도메트리)는 동적(dynamic) 변환으로 방송합니다. TF2 변환 트리를 numpy로 직접 만들어, "레이저가 잰 점이 map에서는 어디인지" 구해 봅니다.

TF2 변환 트리 — 프레임 사이 좌표 변환 (numpy, 실행 검증) 
import numpy as np

def rot_z(t):
    c, s = np.cos(t), np.sin(t)
    return np.array([[c, -s, 0], [s, c, 0], [0, 0, 1]])
def make_T(R, p):                      # SE(3) 동차변환행렬 (R1)
    T = np.eye(4); T[:3, :3] = R; T[:3, 3] = p; return T
def invert_T(T):
    R, p = T[:3, :3], T[:3, 3]
    Ti = np.eye(4); Ti[:3, :3] = R.T; Ti[:3, 3] = -R.T @ p; return Ti

# TF 트리: 각 프레임 = (부모, '부모에서 본 변환')
tree = {
    "map":       (None,        np.eye(4)),
    "odom":      ("map",       make_T(np.eye(3),             [1.0, 0.0, 0.0])),
    "base_link": ("odom",      make_T(rot_z(np.radians(90)), [2.0, 1.0, 0.0])),  # 동적(R4 오도메트리)
    "laser":     ("base_link", make_T(np.eye(3),             [0.2, 0.0, 0.3])),  # 정적
}

def T_from_map(frame):                 # map에서 본 frame 변환 (루트까지 곱)
    chain = []
    while frame is not None:
        parent, T_pc = tree[frame]; chain.append(T_pc); frame = parent
    T = np.eye(4)
    for T_pc in reversed(chain): T = T @ T_pc
    return T

def lookup(target, source):            # TF2 lookup_transform 과 같은 역할
    return invert_T(T_from_map(target)) @ T_from_map(source)

p_laser = np.array([1.0, 0.0, 0.0, 1.0])          # 레이저가 잰 점
print("레이저 점의 map 좌표:", np.round(T_from_map("laser") @ p_laser, 3)[:3])
print("같은 점의 base_link 좌표:", np.round(lookup("base_link", "laser") @ p_laser, 3)[:3])

✅ 실행 결과 (검증됨)

레이저 점의 map 좌표: [3.  2.2 0.3]
같은 점의 base_link 좌표: [1.2 0.  0.3]

실제 ROS에서는 이 계산을 TF2가 대신합니다 — tf_buffer.lookup_transform("map", "laser", time) 한 줄이면 끝. 내부 원리가 바로 위의 "변환 이어 붙이기"입니다.

3. URDF — 로봇의 몸을 XML로

시뮬레이터·RViz가 로봇을 그리고 TF를 만들려면 "이 로봇이 어떻게 생겼는지"를 알아야 합니다. 그 명세가 URDF(Unified Robot Description Format) — 로봇을 링크(link)와 조인트(joint)로 기술하는 XML입니다.

  • 링크(link): 강체 한 덩어리 — 모양(visual), 충돌 영역(collision), 질량·관성(inertial).
  • 조인트(joint): 두 링크(parent·child)를 연결. 주요 타입 — revolute(각도 한계 있는 회전), continuous(무한 회전, 예: 바퀴), prismatic(직선 이동), fixed(고정). (이 밖에 floating·planar도 있어 총 6종.)
URDF 예시 — 베이스 + 고정된 라이다 
<?xml version="1.0"?>
<robot name="my_robot">
  <!-- 링크: 강체(모양) -->
  <link name="base_link">
    <visual>
      <geometry><box size="0.4 0.3 0.1"/></geometry>
    </visual>
  </link>
  <link name="laser"/>

  <!-- 조인트: base_link 에 laser 를 고정 (TF의 정적 변환이 됨) -->
  <joint name="base_to_laser" type="fixed">
    <parent link="base_link"/>
    <child link="laser"/>
    <origin xyz="0.2 0 0.3" rpy="0 0 0"/>
  </joint>
</robot>

이 <joint>의 origin xyz="0.2 0 0.3"가 바로 2절 TF 트리의 base_link → laser 정적 변환(0.2, 0, 0.3)과 같습니다! robot_state_publisher 노드가 이 URDF와 조인트 각도를 받아 자동으로 TF를 발행합니다. (반복되는 구조는 xacro 매크로로 간결하게 작성합니다.)

4. Gazebo vs RViz — 시뮬레이터와 시각화는 다르다

초심자가 가장 많이 헷갈리는 부분입니다. 둘은 전혀 다른 역할입니다.

🌍 Gazebo — 물리 시뮬레이터

중력·충돌·마찰·관성이 도는 가상 세계. 실제 로봇 없이 모터를 돌리고 센서(시뮬 카메라·LiDAR)가 데이터를 만들어 ROS 토픽으로 발행합니다. "현실을 대신하는 곳".

📺 RViz(RViz2) — 시각화 도구

로봇 모델·TF·센서 데이터·경로를 3D로 보여 주기만 합니다(물리 시뮬 아님!). 실제 로봇이든 Gazebo든, 거기서 나오는 데이터를 들여다보는 계기판·모니터입니다.

⚠️ 한 줄 구분

Gazebo는 "세상을 만든다"(시뮬), RViz는 "세상을 본다"(시각화). Gazebo가 만든 센서 데이터를 RViz로 들여다보는 식으로 함께 씁니다. RViz만으로는 물리가 돌지 않습니다.

Gazebo의 센서 플러그인은 시뮬 환경의 카메라·LiDAR가 실제처럼 ROS 토픽(/scan, /camera/image)을 발행하게 합니다 — 그래서 R6에서 짠 구독자 노드가 코드 수정 없이 시뮬에서도 동작합니다. 이것이 ROS+시뮬의 힘입니다.
